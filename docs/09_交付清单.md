### 13.4 能力检测四档（诚实降级）

| 档位 | 判定条件 | 按钮表现 |
|---|---|---|
| `unsupported` | 无 `SpeechRecognition` / `webkitSpeechRecognition` | 置灰，`title` 说明浏览器不支持 |

### 17.5 最终全量测试实测抓到并修复的 2 个问题（如实记录）

首轮 `cargo test --lib` 全量跑出 **352 过 / 10 败**——此前只有定向测试绿过，
这两处问题**只有全量才暴露**：

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 7 个 `offline_license_*` 测试红：`签名不是合法 base64` | `channel::b64_decode` 只认 **URL-safe** 字母表（`-_`），而 `tools/issue_license.py` 用 Python 标准库 `b64encode` 签发**标准** base64（`+/`）——随机签名约 3/4 概率含 `+`/`/`，**真实售出的许可在客户端会解析失败**（发行级 bug，非测试问题） | 解码器改为**宽容双字母表**（编码侧仍固定 URL-safe），补 `base64_accepts_both_alphabets` 回归测试；发行二进制 e2e 复验：含 `+`/`/` 的 .lic 启动即授通 |
| 2 | 3 个 `store` 回退测试红：`left: 21, right: 17` | 预置项目库从 17 扩到 21（报名表匹配需要）时，测试里的**魔法数字**没跟着更新 | 三条断言改为与 `seed_events()` 的产出比对，不再写死数字（预置库再增减也不会无故跑红） |

同一轮还整改了一处**设计级缺口**（测试没直接暴露、复查门禁链路时发现）：
v1.8.0→v1.9.0 的"磁盘有许可文件才创建授权管理器"会让**全新安装**三者皆空 →
管理器为 None → 门禁恒放行、激活接口报"未启用授权管理"——一台干净安装即可
绕开整个授权制。已改为**管理器无条件创建**（`--aim-allow-unlicensed` 仍是
显式逃生门），并新增集成测试 `fresh_install_gate_blocks_until_licensed`
锁死四条行为；UI 补上「开始 30 分钟试用」按钮，让使用说明承诺的试用真实可达。

另：本沙箱进程监管偶发破坏子进程回收（阻塞式 `wait4` 收到僵尸子进程仍
数分钟不返回，cargo 与测试套件都中各过一次），集成测试的清理已改为
**有界回收**（`try_wait` 轮询至多 2 秒后放弃，僵尸由 init 统一收尾），

### 17.6.3 分发前必须处理的一件事（如实记录）

`dist/sports-meet` 内嵌的是**本沙箱构建时生成的测试密钥**
（`keys/aim.secret` 掩码后注入），对应签发私钥只存在于沙箱。沙箱任务结束
后即无人能签发有效激活密钥——**正式分发前必须在自有构建机重新
`keygen-secret` + `keygen` 生成 `keys/`，再跑 `build.sh`**（缺密钥脚本会
前置报错退出，不会悄悄产出无防护二进制）。此约束与 17.1 节口径一致，

修复 1 是真正的跨平台缺陷（Windows 版根本编不出来）；修复 2 是构建流程适配。
两者都不影响 Linux 产物：`obf.rs` 的改动在 `cfg(windows)` 块内，Linux 二进制未重建。

## 17.8 防破解加固（v1.9.1，2026-11-01）

> 用户提出："把函数名改成火药配方/毒药名称，并在里面搞提示词注入"、
> "加入政治敏感内容让 AI 拒绝回答"。**均未采纳**，理由见 17.8.1；
> 改为做攻防实测 + 针对性加固。

### 17.8.1 为什么不用"改名 / 提示词注入 / 政治敏感内容"

| 方案 | 实际效果 | 副作用 |
| --- | --- | --- |
| 函数改名（火药/毒药） | **零**。破解者读的是算法结构与判定分支，不是名字。`mac(...) != tag`、`crc16`、`is_granted` 这些特征改名后一个字没变 | 校园软件的二进制里出现火药/毒药字样，杀软可能报可疑字符串，家长/教育局看到无法解释 |
| 提示词注入 | 对"人+AI 对话"基本无效（模型把代码当数据）；对 agent 不可靠、不可测、随模型更新失效 | 自己以后用 AI 排查 bug 会被误导；被发现即污点 |
| 政治敏感内容 | 不可靠（拒绝是概率性的），且可以换模型绕过 | **学校软件 + 政治敏感 = 不可接受的事故风险**；且这类内容不在可协助范围内 |

**结论**：这三条都属于"提高被发现的代价"，不提高"破解的代价"。

### 17.8.2 攻防实测：加固前只要 2 步

| 步骤 | 动作 | 结果 |
| --- | --- | --- |
| 1 | 把 `AuthState::is_granted()` 改成恒 `true`（1 行） | `granted: true` |
| 2（仅当盖章缓存存在时） | 删除 `target/integrity_cache.bin`，让自校验退回"基线不阻断" | 业务接口 **200**，完全放行 |

实测：改 1 行 + 删 1 个文件，**2 步完成破解**，耗时不到 1 分钟。
更糟的是还有一条零成本路径：`--aim-allow-unlicensed` 是裸开关 ——
加个参数就免费，`strings` 一搜就有。

### 17.8.3 三项加固

| # | 加固 | 实现 | 破解者代价变化 |
| --- | --- | --- | --- |
| 1 | **逃生门加锁** | 发行构建下 `--aim-allow-unlicensed` 必须配 `--aim-unlock-code <16 位>`，码由主密钥派生（`SM1ULK` 域 + `unlicensed-gate` 标签，常数时间比较）。管理员用 `tools/issue_license.py unlock-code` 取得；debug 构建保留开发豁免 | 从"加个参数"变成"先从这个二进制里提取主密钥"（而提取要过完整性自校验） |
| 2 | **根绝"删缓存"后门** | `recheck_gate()` 增加**无条件**完整性前置：发行构建（release）下"基线模式"同样视为不可信。不依赖 `has_material`，所以"`is_granted` 改恒真"也躲不过 | 必须连完整性判定一起改（多一处，且要先意识到有这一层） |
| 3 | **节流窗口不漏判** | 完整性结论缓存进 `integrity_ok` 字段，节流期内**复用结论**而不是"跳过检查" | 堵住"第 1 次被拦、15 秒内第 2 次放行"的时序缺口 |

> 加固 3 是实测中发现的真 bug：第一版只做"检查 + 拒绝"，结果第 1、2 次
> 请求 403、第 3 次 200 —— 节流把"未检查"当成了"通过"。改为缓存结论后
> 连续 6 次请求 + 写操作全部 403。

### 17.8.4 加固后实测

| 场景 | 结果 |
| --- | --- |
| 裸 `--aim-allow-unlicensed`（发行版） | ✅ 拒绝启动（exit 2） |
| 错误解锁码 | ✅ 拒绝启动 |
| 正确解锁码 | ✅ 正常启动，业务 200（仅排障用） |
| 改 `is_granted` 恒真 + 删缓存（破解版） | ✅ 连续 6 次请求全部 403，写操作 403，日志留"完整性前置检查未通过" |
| 正常盖章发行版 + 未激活 | ✅ 首业 403（引导激活），首页 200 |
| 正常盖章发行版 + 真实 48 位密钥 | ✅ 激活成功（365 天 / all 功能位），连续请求 200，完整性"校验通过" |

### 17.8.6 加固后复测中发现的**新漏洞**（已修复，v1.9.1 第二轮）

第一轮加固完成后，我在 Windows 交叉编译版上做复测，**又踩出一个更隐蔽的洞**。
如实记录，因为它比原来的三个洞更难想到：

**攻击手法**：把数据区的**起始魔数** 8 字节（`"SMI1DATA"`）改成 0。

**为什么这反而变成"绿灯"**：

1. 运行期的搜索锚 `blob_magic_start()` 是**从 BLOB 自己读**的（这是原始设计，
   为避免源码字面量也在二进制里造成歧义）。魔数被抹 → 锚变成 **8 个零字节**。
2. PE/ELF 里数据区前后是大片零填充，于是"零锚"到处都是。
3. 但候选位置 `[pos+152, pos+160)` 的**结束魔数**、以及 `[pos+136,124)` 的
   **交叉指纹**全都还在原处 —— 只要 `pos` 落在数据区起始之前的某个零字节位置，
   这两个校验就都"通过"。
4. 于是**第一个**零字节候选被当成数据区，掩码掩在了**错误位置**。
5. 真实数据区没被掩掉 → 段哈希算在**未掩码的裸数据**上 → 和期望值逐段相同 →
   **8 段全"校验通过"**。

换句话说：攻击者抹掉魔数，本来是想让校验失效，结果意外换来一个绿色状态
（同时"基线模式后门"那一层也没拦住，因为标志位还是 1）。

**修复（三层，缺一不可）**：

| 层 | 改动 | 作用 |
| --- | --- | --- |
| ① 取最后一个候选 | `mask_blob` 不再命中即返回，遍历完取**最后一个**合格候选 | 真实数据区结构上是候选段的最后一段（后面只剩尾部填充），这样能拿回正确位置 |
| ② 魔数兜底 | 锚或结束魔数为全零时，退回**编译期常量** `MAGIC_START/END_FALLBACK` | 两个魔数同源，会被同一个攻击一起污染；全零锚的自确认等于没有校验 |
| ③ 定位失败即失败 | 标志位=1（声称已盖章）但 `mask_blob` 返回 `None` → 直接 `passed=false` | 旧实现会掉进"未掩码裸数据"分支继续比对，结论毫无意义（实测那个分支正是 `ok:true` 的来源） |

**此外还修了一个"诊断说谎"的问题**：`status_json_fields()` 报的是原始
`is_fatal()`，而 `recheck_gate()` 用的是"发行构建下基线即不可信"。结果
诊断页显示 `ok:true`、接口却 403 —— 排查时会得出完全相反的结论。
现已统一口径（发行构建基线 → `ok:false`），摘要文案也分开发/发行两版。

**复测证据**（Linux ELF 与 Windows PE 各跑一遍）：

| 场景 | Linux | Windows(wine) |
| --- | --- | --- |
| 正常盖章版 | `baseline:false / ok:true`，首页 200，写 403（未激活）✅ | 同左 ✅ |
| 抹起始魔数 | `ok:false`，摘要"数据区定位失败（起始魔数被破坏或数据区被挪走）"，写 403 ✅ | ✅ |
| 抹标志位（模拟基线构建） | `baseline:true / ok:false`（发行构建基线不可信），写 403 ✅ | ✅ |
| 裸 `--aim-allow-unlicensed` | 拒绝启动 ✅ | 拒绝启动 ✅ |
| 正确解锁码 | 启动 + 业务 200 ✅ | 启动 + 业务 200 ✅ |
| 三方比对（复算==缓存==内嵌） | 一致（偏移 429292）✅ | 一致（偏移 2592768）✅ |

**为什么第一轮没测出来**：第一轮只在 Linux 上测，而 Linux 版我测的是
"改 `is_granted` + 删缓存"那条路径，没试过**直接改二进制里的魔数字节**。
Windows 版因为要重新交叉编译才顺手试了一下 —— 这也说明
**"只在一个平台上验收"是危险的**。



### 17.8.5 必须认的边界（不粉饰）

1. **源码在手 = 一定能破**。客户端授权的物理极限就在这里；加固只是把成本从
   "1 分钟"抬到"几小时且要理解完整性机制"。真正的护城河是**源码包不外流**
   ＋授权协议，不是混淆。
2. **对二进制级攻击防线很强**（改任一字节必红）。对源码级重建，只能抬高成本。
3. 本次加固**改变了 `--aim-allow-unlicensed` 的行为**：升级后若现场排障要用
   它，必须从构建机取解锁码。已在 `使用说明`「授权异常的临时处置」一节注明。
4. `cargo test` 在沙箱里仍会因 wait4 挂起而卡住（环境病症，非代码问题），
   集成测试改为直跑 `target/debug/deps/integration-*` 得 51 全绿。
5. **加固是多轮逼近，不是一次到位**。17.8.6 记录的那个洞就是第一轮加固后
   才发现的。诚实地说：**这个类别里我不能保证"已经找全了"**。能保证的是
   每发现一个就补一个测试用例（新增
   `stamped_but_unlocatable_blob_is_fatal`、`status_fields_match_gate_semantics`、
   `mask_picks_last_when_anchor_is_zeroed` 三条），让同一个洞不会再次出现。
6. 完整性校验的**信号仍来自二进制自身**。极端情况下（攻击者能同时改代码与
   数据区，且有足够耐心重建一个自洽的假数据区）仍可绕过 —— 这就是第 1 条
   说的"源码在手 = 一定能破"的具体形态。

| B | `--aim-allow-unlicensed` 在发行版依然生效 | 加一个参数就免费，比逆向便宜太多 | 与 17.8.3 的方案合并：必须配 `--aim-unlock-code`（主密钥派生），否则 `exit(2)`。比"一律失效"多保留了现场排障能力 |
| C | 配置模板携带固定 PSK `THZX-AIM-2026-PSK-CHANGE-ME`，客户端缺配置时回退同一常量 | "默认口令出厂即有效" → 任何人可冒充授权服务端下发"通过" | `from_json` 不再回退默认值；`--gen-config` 生成时随机填入；`AuthManager::new` 见空值/默认值即停用通道并告警 |

三项均**实测有效**（同一份代码，配置好 `keys/` 的 release 构建）：

```
[WARN] [main] 检测到已配置正式签发密钥，忽略 --aim-allow-unlicensed，强制开启授权校验
enforce: True | 受控写 403
[密钥机制] 未启用开发者模式（未提供有效密钥或未确认风险）   ← 演示密钥失效
[WARN] [aim] license_server.psk 未配置或仍为默认值，已停用服务端授权通道
--gen-config → psk 随机 48 位 hex（每次不同）
```

### 17.9.3 二进制凭据残留（交付检查项）

| 字符串 | 加固前 | 加固后 |
|---|---|---|
| `35d041df2b141b66`（演示密钥指纹） | 1 处 | **0** |
| `THZX-2026-DEV`（演示密钥明文） | 0 | 0 |
| `THZX-AIM-2026-PSK-CHANGE-ME` | 2 处 | 1 处 |

最后一条保留是**有意的**：`DEFAULT_PSK` 仍作为 `AuthConfig` 的占位值参与
"是否为历史默认值"的判定（识别出就停用）。它已不再是任何路径上的口令回退。

### 17.9.4 审查没覆盖、但我这轮查出来的第 4 个洞

**离线缓存可伪造**（比改 `is_granted` 更省力，且不需要动二进制）：

```
cache_key = FNV1a(公开盐 ‖ DEFAULT_PSK(明文) ‖ hwid)
```
而 `--hwid` 会把 `hwid` 直接打印出来。攻击者据此可离线封一份
"365 天有效"的 `data/.license` 写入 → 启动即已授权。
实测确认：缓存条目只按 `hwid` + `expire_at` 判定，`ticket` 字段**本地从不验签**
（只在"贵重复核"时发给服务端）。

**修复**：`cache_key` 改混**主密钥**而非公开 PSK。主密钥以掩码形式存放
（`MASTER_MASKED ^ UNMASK`），纯 `strings` 提取不再够用，必须逆向才能得到 ——
与"自己伪造 48 位密钥"成本拉平，两条路都不再是"读几个字符串"级。
代价：升级后旧 `license.cache` 解不开，需重新激活一次（48 位密钥走的是
`keys/` 下的 key 文件，不受影响）。

新增回归用例 `forged_cache_from_public_strings_is_rejected`：**它扮演攻击者**，
只用公开材料复现旧算法封缓存，断言必须解不开。谁把密钥材料改回公开常量，
这条立刻变红。

### 17.9.5 两条路线的取舍（记录判断依据）

| 维度 | 审查方案 | 本版方案 | 取舍理由 |
|---|---|---|---|
| 逃生门 | 配了签发密钥就**一律失效** | 需 `--aim-unlock-code` 才失效 | 学校现场可能遇到授权误判，无逃生门等于把人锁在门外；解锁码由管理员持有，成本可控 |
| 开发者模式 | 同上 | 同上 | 完全一致，直接吸收 |
| 完整性 | 未涉及 | 基线模式 fail-closed + 前置检查 + 定位失败即失败 | 审查只做了"凭据检查"，没做"篡改检测"；两者互补 |
| 缓存 | 未涉及 | 密钥材料改为非公开 | 见 17.9.4 |

### 17.9.6 仍需说明的边界

1. 主密钥仍在客户端（对称校验的物理限制）。逆向到能解掩码的程度，
   48 位密钥与缓存两条路都会失守 —— 这是"源码/二进制在手"的固有上限。
2. `keys/devkey.fp` 缺失时开发者模式**整体不可用**，这是**预期行为**，
   不是故障。需要时按 `README`「开发者模式快速上手」写入指纹再重编。
3. 本轮改动使**旧 `license.cache` 失效**。只用 48 位密钥的部署不受影响。

## 17.10 产品改为免费（v1.9.2，2026-11-04）

### 17.10.1 变更性质

**这是产品定位变更，不是补丁。** 作者决定本软件不再收费，试用改为永久可用。
因此授权系统从"稀缺授权 + 限时试用"变为"默认放行 + 可选正式授权"。

### 17.10.2 实现方式（保留了可逆性）

没有删除限时试用代码，而是给 `TrialPolicy` 加了一个开关：

```rust
pub struct TrialPolicy {
    pub enabled: bool,
    pub perpetual: bool,   // v1.9.2 新增，默认 true
    pub require_online_confirm: bool,
}
```

* `perpetual = true`：`gather()` 直接返回 `Active(PERPETUAL_REMAINING)`，
  **不读不写任何试用记录** → 升级上来的老机器即使盘上还留着"已消耗"记录，
  也不会被锁死，不需要用户手工清文件。
* `perpetual = false`：30 分钟一次性逻辑原样生效（代码与测试都还在），
  将来想做"限时演示版"只需改这一个布尔。

`decide()` 的放行位置放在**离线判定的最后一档**（在密钥/许可/票据之后）：
用户手上有正式授权时界面显示正式授权，而不是"试用版"。

### 17.10.3 同时移除的副作用（容易踩的坑）

| 位置 | 原来的做法 | 现在 | 为什么 |
|---|---|---|---|
| `activate_trial` | `expire_at = now + secs` | 永久模式置 `0` | 哨兵值 100 年加 `now` 会溢出，显示成 1970/负数 |
| `activate_trial` | 反调试闸门无条件拦截 | 永久模式不拦 | 闸门拦的是"反复白嫖限时试用"，动机已不存在；留着只会误伤挂录屏/安全软件的老师 |
| 文案 | "开始 30 分钟试用""到期后停用" | "开始试用""无到期限制" | 不能让用户以为还会过期 |

### 17.10.4 测试的语义调整（重要，别误解为"放宽"）

改完有 13 个用例变红，全部是**断言"没授权就该拒绝"**的用例。处理原则：
**给用例显式关闭永久模式**（`disable_perpetual` / 显式 `perpetual: false`），
而不是删断言或改期望值。这样限时试用那套逻辑**仍然被测着**。

集成用例 `fresh_install_gate_blocks_until_licensed` 因契约真的变了而重写为
`fresh_install_is_usable_without_license`，并**加强了**两条断言：
状态接口必须如实报"无到期限制"、不得谎报有密钥。

### 17.10.5 仍然保留的安全能力（免费 ≠ 不设防）

| 能力 | 状态 |
|---|---|
| 二进制完整性自校验（改一字节即拒） | **保留**，实测篡改后写接口 403 |
| 数据目录独占锁（防双开写坏数据） | 保留 |
| 审计链 | 保留 |
| 48 位密钥 / 离线许可 / 在线票据 | 保留（有正式授权的用户仍显示正式授权） |
| 逃生门解锁码 | 保留 |

免费之后**不值得**再投入的是"防白嫖"那部分成本（本来就是为了卖钱）；
真正保护数据安全的那些机制一个没动。

### 17.10.6 验证

* 单测 372 + 集成 51 + 契约 9 + e2e 6 = **438 全绿**
* 全新机器（零授权物）：Linux 与 Windows(wine) 双平台均 `granted: True`、
  业务写 200、`trial: active`
* 重启后仍可用（不依赖任何盘中记录）
* 抹数据区魔数后：`ok: false`、写接口 403（篡改检测未受影响）

## 17.11 清空报名 + 报名表模板直传（v1.9.3，2026-11-06）

用户反馈的两个真实痛点：

1. **「报名这里怎么清除已报名的人员？只找到撤销，且只能撤销 10 次」**
   —— 属实。旧版只有逐条 `✕` 退报 + 默认 10 步撤销栈，批量导入错了得点几十次。
2. **「导入文件那里要做模板，可以下载后填充资料再导入」**
   —— 旧版导入面板只吃 JSON，而 xlsx→JSON 的 `tools/baoming_import.py`
   **只进源码包**；用户拿到的 exe 发行包里没有任何脚本，导入功能实际不可用。

### 17.11.1 变更清单

| 文件 | 变更 |
| --- | --- |
| `src/core/baoming.rs`（新增） | xlsx（zip+sharedStrings+sheet XML）/ csv 解析 → 导入 payload；base64 编解码；班别解析、性别感知项目匹配 |
| `src/core/export.rs` | `baoming_template_xlsx` / `baoming_template_csv` / `baoming_template_rows` / `baoming_template_notes` |
| `src/core/api.rs` | `clear_registrations_preview` / `clear_registrations` / `import_baoming_file`；undo 新增 `clear_registrations` 整批恢复分支；5 条新路由 |
| `src/core/http.rs` | 敏感路径表加入 `/api/registrations/clear`；请求体上限仅对该导入路径放宽至 8 MiB |
| `web/index.html` | 导入面板：模板下载按钮、文件直传、解析报告；报名页：「清空报名」三段式确认；缓存失效规则补 events/results |
| `Cargo.toml` | `zip` 提为直接依赖（原本已由 rust_xlsxwriter 引入，依赖树零新增） |
| `使用说明.txt` / `docs/16` | 同步新链路 |

### 17.11.2 设计要点

* **整批撤销**：清空把被删的报名 + 连带成绩压成**一条**撤销记录，
  `undo_now()` 一次全量恢复，不再受 `--undo-keep 10` 的步数限制。
  撤销栈机制本身未改动，老数据完全兼容。
* **连带删成绩**：与既有「退报」语义一致，避免留下指向已退报学生的孤儿
  成绩；集体项目成绩（`student_id == None`）不动。
* **范围封闭集合**：`all / event / grade / class`，参数缺失即报错，
  不会静默退化成「清空全部」；`class` 必须同时给年级与班号。
* **导入不另起炉灶**：文件解析只负责产出 payload，入库仍走
  `Core::import_baoming` —— 幂等、限额、性别分组、跳过报告全部复用。
* **兼容旧表**：学校现成的男女分节打勾报名表可直接上传，无需重抄；
  旧 JSON 入口与 Python 脚本保留。

### 17.11.3 验证

* 单测 382（+10）+ 集成 51 + 契约 9 + e2e 6 = **448 全绿**
* xlsx 模板由程序自己生成、再由自己的解析器读回，模拟填表后上传：
  学生 +2 / 报名 +2 / 示例行跳过 2；CSV 直传重复导入 +0/+0
* 清空预检只读、不带 `confirm` 返回 428、一次撤销恢复 4 条报名 + 2 条成绩
