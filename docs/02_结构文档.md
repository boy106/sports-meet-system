## 一、运行环境要求

### 生产运行（最终用户）

| 项 | 要求 |
| --- | --- |
| 操作系统 | **Windows 10 / 11 x64**（推荐，直接运行 `.exe`）<br>或 Linux x86_64 |
| 运行库 | **无需安装**（静态链接，仅需系统 CRT） |
| 浏览器 | 任意现代浏览器（Chrome / Edge / Firefox）<br>**语音输入需 Chrome / Edge 且联网**（见第十三节） |
| 网络 | **无需联网**；服务仅监听 `127.0.0.1`（本机） |
| 硬盘 | 约 50 MB（含程序与数据） |

### 源码编译

| 项 | 要求 |
| --- | --- |
| **Rust** | **1.70 或更高**（`Cargo.toml` 已声明 `rust-version = "1.70"`）<br>本次验证环境：**rustc 1.98.1 (2026-09-01)** |
| Edition | 2021 |
| 目标平台 | `x86_64-pc-windows-gnu`（Windows 交叉编译）<br>`x86_64-unknown-linux-gnu`（Linux 原生） |
| 外部依赖 | 仅 `rust_xlsxwriter = "0.79"`（xlsx 导出）<br>首次编译需联网；离线环境可预置 `~/.cargo/registry` |
| 交叉编译额外依赖 | `mingw-w64` 工具链（`x86_64-w64-mingw32-gcc-posix`） |
| 环境变量建议 | `CARGO_INCREMENTAL=0`（若工程位于网络/OSS 挂载盘） |

## 三、模块依赖关系

**依赖单向、无循环**：

```
                       ┌─────────────┐
                       │   main.rs   │  组装层
                       └──────┬──────┘
                 ┌────────────┴────────────┐
                 ▼                         ▼
          ┌────────────┐            ┌──────────────┐
          │    core    │◄───────────│  extensions  │
          │  （核心）   │  单向依赖   │   （扩展）    │
          └────────────┘            └──────────────┘
```

**core 内部层次**（箭头表示"依赖"）：

```
  api ──► ext, http, json, log, model, scoring, store
  export ──► json, model, store, api
  http ──► api, json, log
  store ──► json, model, scoring, log(宏)
  scoring ──► json, model, store
  model ──► json
  ext ──► http, json
  log ──► store::now_string（函数级调用，无类型级循环）
  json ──► （无依赖，纯 std）
```

**关键约束**：

- `core` **绝不** `use crate::extensions::...`（核心对扩展一无所知）
- 扩展之间**互不可见**
- 扩展只能通过 `CoreContext`（即 `Core`）的公开方法访问核心能力

## 四、核心数据结构

### 领域模型（`core/model.rs`）

| 结构 | 字段要点 |
| --- | --- |
| `Settings` | `grades` / `class_count` / `max_individual` / `max_team` / `max_per_class_per_event` / `enforce_gender` / `points_table`（默认 `[7,5,4,3,2,1]`）/ `record_bonus`（7.0）/ `team_multiplier`（2.0） |
| `Event` | `id` / `name` / `category`（径赛/田赛）/ `gender` / `grade` / `is_team` / `unit`（时间/米/个）/ `record`<br>方法 `is_track()` |
| `Student` | `id` / `grade` / `class_no` / `name` / `gender`<br>方法 `class_name()` |
| `Registration` | `id` / `event_id` / `student_id` / `note` |
| `Result` | `id` / `event_id` / `student_id`（集体为 None）/ `grade` / `class_no` / `score_text` / `score_value` / `rank` / `points` / `broke_record` |

### 持久化结构（`core/store.rs`）

```rust
pub struct Data {
    settings: Settings,
    events: Vec<Event>,
    students: Vec<Student>,
    registrations: Vec<Registration>,
    results: Vec<DomainResult>,
    next_event_id / next_student_id / next_reg_id / next_result_id: i64,
    undo_stack: Vec<UndoEntry>,     // v1.2：多步撤销栈
    // ↓↓↓ v1.7.0 赛程编排（缺失字段回退默认，零迁移） ↓↓↓
    venues: Vec<Venue>,             // 场地（for_track/for_field 标记并行能力）
    sessions: Vec<Session>,         // 竞赛单元（天 × 上午/下午）
    slots: Vec<Slot>,               // 已排赛程（项目×单元×场地×时刻）
    schedule_days: i64,             // 赛程天数（默认 2，clamp 1–5）
}

pub struct UndoEntry {
    time: String,
    action: String,                  // delete_event / delete_student / unregister
                                     // clear_results / register_many
    payload: Json,
}
```

**数据格式版本标记**：JSON 顶层 `"version": 2`。
读取时兼容处理：优先读 `undo_stack`，缺失则回退读 v1.1 的 `undo` 字段。

## 七、对外接口（供扩展使用）

扩展可用的 `CoreContext`（即 `Core`）公开方法：

**数据访问**
- `read<R>(f: impl FnOnce(&Data) -> R) -> R` — 只读
- `write<R>(f: impl FnOnce(&mut Data) -> Result<R, ApiErr>) -> Result<R, ApiErr>` — 读写 + 落盘

## 十一、v1.5 新增架构

### 一、SSE 流式响应（`core/http.rs` + `extensions/live_board.rs`）

```
浏览器 EventSource
      │  GET /api/ext/live-board/stream
      ▼
Router::dispatch_inner → 扩展 handler
      │  find_live_board(ctx)              ← 从核心扩展列表按名取回实例
      │  （handler 无法捕获 self，且 core::ext 刻意不提供 as_any()，
      │    故扩展自持 OnceLock<Arc<LiveBoard>> 静态槽位）
      │
      ├─ 观众数 >= MAX_VIEWERS(32) → Err（429 语义，走 400 JSON）
      ├─ 先 tx.send("snapshot")         ← 新观众即时同步，不等下次变动
      ├─ viewers.push(Viewer{tx, since})
      └─ Ok(Response::sse(move |w| pump(w, rx)))

pump()（在独立连接线程内运行）
   loop {
       match rx.recv_timeout(HEARTBEAT=15s) {
           Ok(b)  => w.send(b.event, &b.data)   // event: <kind>\n data: <json>
           Err(Timeout) => w.comment("ping")    // 心跳注释帧，防中间设备掐空闲连接
           Err(Disconnected) => break
       }
       if w.is_closed() { break }               // 客户端断开立即退出，释放线程
   }
   w.finish()                                   // 写 "0\r\n\r\n" 结束 chunked
```

**关键实现点**

| 点 | 做法 | 原因 |
| --- | --- | --- |
| 传输编码 | `Transfer-Encoding: chunked`，每帧 `len(hex)\r\n<data>\r\n` | 长度未知，不能先给 `Content-Length` |
| 超时 | 流式响应用 `STREAM_WRITE_TIMEOUT=3600s` | 套用 30s 普通超时会把大屏掐断 |
| 连接头 | 流式响应发 `Connection: close` | 该 TCP 连接专用于这条流，不复用 |
| 上游读取 | `read_request` 改逐字节 `read_line_bytes` | `BufReader` 会过度缓冲，把 SSE 首批字节一起吞掉 |
| 断连清理 | `broadcast()` 里 `retain(\|v\| v.tx.send(..).is_ok())` | 惰性清理，无需额外连接跟踪线程 |

**事件类型**：`snapshot`（完整赛况）/ `result` / `registration` / `event` / `student` /
`settings`（核心事件转发）+ `ping`（心跳）。前端按事件名分流：
收到 `snapshot` 直接重绘，收到 `result` 等再拉一次快照兜底。

### 二、审计哈希链（`core/audit.rs`）

```
record(actor, action, detail)
   │
   ├─ Mutex<AuditorState> 取锁（无 unsafe：可变状态全在 Mutex 内）
   ├─ seq = head_seq + 1
   ├─ prev_hash = head_hash
   ├─ hash = FNV1a64(prev_hash, [seq, time, actor, action, detail])
   │          每段前插 0x1f 分隔符（防字段拼接碰撞）
   ├─ 追加写 data/audit/audit-YYYY-MM-DD.jsonl（O_APPEND）
   ├─ 更新 head_hash / head_seq / recent(保留 200 条)
   └─ 跨天只换文件名，链头**延续**（prev 仍指上一条）→ 跨天不断链
```

**verify() 三类检出**

| 字段 | 含义 | 触发条件 |
| --- | --- | --- |
| `bad_hash_at` | 某条**内容被改** | 重算 hash ≠ 文件里的 hash |
| `bad_link_at` | **删中间条 / 换序** | 本条 prev_hash ≠ 上一条的 hash |

### 三、鉴权模型（v1.5 升级为两级）

```
启动参数 --password xxx
        │
        ▼
Core.password: Option<String>   Core.token_secret: String（进程内随机，不落盘）
        │
        ▼
Router::dispatch_inner 统一拦截
   ├─ 第一级：写操作（POST/DELETE）鉴权
   │    needs_auth = is_write && password.is_some()
   │                 && path != "/api/auth/token"     ← 例外1：换令牌自身，防鸡生蛋
   │                 && !readonly_post                ← 例外2：纯计算 POST（/api/smart/parse）
   │    校验 Authorization: Bearer <凭证>
   │       ├─ 先比口令（常量时间）      ← v1.4 旧客户端/脚本兼容
   │       └─ 再验令牌签名 + 未过期     ← v1.5 推荐路径
   │    不通过 → 401 {"auth_scheme":"token_or_password"}
   │
   ├─ 第二级：敏感操作二次确认
   │    is_sensitive_path(method, path)：
   │      DELETE /api/events/*   DELETE /api/students/*
   │      POST   /api/results/clear   POST /api/import/json
   │    须在 X-Confirm-Password 头再带一次口令（常量时间比较）
   │    缺失/错误 → 428 Precondition Required
   │
   └─ GET 与只读 POST 一律放行
```

**令牌格式**（三段，`.` 分隔，无 base64 依赖，便于 curl 手工调试）

```
<expire_unix>.<nonce>.<sig>
sig = FNV1a64(secret, [expire, nonce])
```

| 特性 | 说明 |
| --- | --- |
| 密钥来源 | 纳秒 + 栈/堆地址（ASLR）+ pid + tid + 原子计数 → 两轮 FNV-1a → 32 位 hex |
| 密钥持久化 | **不落盘**；服务重启即全部失效（安全 > 便利） |
| TTL | 12 小时（`TOKEN_TTL_SECS = 12 * 3600`），可按需传 `ttl_secs` |
| 吊销 | 无状态，靠过期；改口令需重启（会换密钥） |
| 前端口令 | **只在校验那一刻存在于内存**，写入 localStorage 的是令牌（v1.4 存的是口令） |

**诚实的局限（不隐瞒）**：签名基于 FNV-1a 而非标准 HMAC-SHA256，
**不是密码学意义上的安全 MAC**。它挡得住"局域网抓包重放"和
"随手改 URL 冒充管理员"，挡不住有密码学能力、能本地离线跑碰撞的对手。
若部署环境升级为公网，需替换为 HMAC-SHA256 并引入密钥持久化管理。

## 十二、v1.5.1 新增架构（密钥机制 / 开发者模式 / 数据加密）

### 一、密钥派生（`core/license.rs`）

```
启动参数 --devkey K
  │
  ├── fingerprint(K) = slow_hash(K, 200_000)
  │     slow_hash(input, rounds):
  │         h = FNV1a64_OFFSET
  │         for i in 0..rounds:
  │             h = FNV1a64(h, 盐 ‖ i.to_le_bytes() ‖ input)
  │         return h as 16 位 hex
  │
  ├── 与编译期常量 LICENSE_FINGERPRINT 做 const_time_eq 比较
  │     ├── 相等 → key_ok = true
  │     │         stream_seed = slow_hash(K ‖ "::stream", 1)   ← 换盐，防与指纹呈线性关系
  │     └── 不等 → key_ok = false（**静默**：不 log、不 err、不 exit）
  │
  └── risk_acked = (启动参数里有 --i-know-the-risk)
```

**为什么慢哈希**：单次 FNV-1a 约 1 ns，20 万轮约 30 ms——相差 7 个数量级。
攻击者每猜一个密钥要付 30 ms 代价，且**无预计算表空间可用**（哈希链依赖输入本身，
不像彩虹表能预先算好所有候选）。这**不是** bcrypt/argon2 级别的 KDF，
但相对"源码里明文写密钥"是数量级的提升。

### 二、开发者模式三重条件准入（`core/license.rs` + `core/http.rs` + `core/api.rs`）

```
HTTP 请求进入
  │
  ├── core/http.rs: serve()
  │     stream.peer_addr() → SocketAddr
  │     is_loopback(&addr)          ← 只看 TCP 对端，不读任何请求头
  │         · 127.0.0.0/8
  │         · ::1
  │         · IPv4-mapped ::ffff:127.x.x.x
  │     → dispatch_from(req, from_loopback)
  │
  ├── dispatch_inner 首段计算 dev_mode：
  │     dev_mode = from_loopback && license.mode() == Unlocked
  │     req.from_loopback = from_loopback
  │     req.dev_mode      = dev_mode
  │
  ├── 路径分类（三岔口，必须分清）
  │     ├── /api/dev/**            → is_dev_endpoint，**免口令鉴权**（但解锁本身仍查三重条件）
  │     ├── /api/smart/parse       → readonly_post，免鉴权（v1.5 既有）
  │     └── 其他 POST/DELETE       → 需 Authorization: Bearer <令牌>
  │
  └── 敏感路径二次确认：
        需要确认 = is_sensitive_path && !dev_mode
        ├── dev_mode 为真 → 直接放行（业务层同时收到 confirmed = true），写审计 dev_bypass_confirm
        └── dev_mode 为假 → 走 428 预检（v1.5 既有）
```

**三重条件在 `POST /api/dev/unlock` 中的判定**：

| 条件 | 来源 | 缺省结果 |
| --- | --- | --- |
| ① `key_ok` | `--devkey` 与 `LICENSE_FINGERPRINT` 比较 | 403 |
| ② `from_loopback` | TCP 对端地址（`is_loopback`） | 403 |
| ③ `risk_acked` | 启动参数 `--i-know-the-risk` | 403 |

三者 AND 为真才 `license.unlock()` → `AtomicBool` 置位。**缺任一条都返回 403 且不区分是哪条缺失**（减少信息泄露）。

> **为什么 dev 路由免口令**：开发者模式的意义正是"不必拿口令也能调试"。
> 若 dev 路由也要口令，就会出现"忘记口令 → 进不去诊断页 → 更拿不回口令"的**死锁**（踩坑 #31）。
> 免口令不等于免条件——三重条件 + 审计留痕把风险锁在可控范围内。

### 三、数据保险库（`core/vault.rs`）

```
明文 plain（任意长度）
  │
  ├── 文件头 14 字节：SMEV(4) + version(1) + mode(1) + seed_fingerprint(8)
  │
  └── 分块加密：每 BLOCK_SIZE = 4096 字节明文
        ├── keystream(seed64, block_no, len)
        │     64bit 块号作计数器，类 CTR：逐块生成密钥流后 XOR
        └── 追加 8 字节 MAC（block_mac(seed64, block_no, 密文)）
              用于完整性校验：解出后重算，不符即 Tampered { block }
```

解封 `open()` 时的边界处理（踩坑 #33 的教训）：

```
1. 校验长度 ≥ 14，魔数 = SMEV，版本受支持   → 否则 NotEncrypted / UnsupportedVersion
2. 校验头里的 seed_fingerprint 与当前 seed 一致 → 否则 NoKey
3. body = 头之后的全部字节
4. if !body.is_empty() && body.len() < 8 → Truncated    ← 显式判据（替代原死代码）
5. 逐块：plain_len = min(BLOCK_SIZE, remain - 8)
        remain.checked_sub(8) 兜底          ← 真正守住边界的是这里
        取 8 字节 MAC 校验 → 不符即 Tampered { block }
```

**兼容性**：`read_auto` 先看前 4 字节是否 `SMEV`——
是则解密，否则按明文直接返回。所以**开启加密后仍能读旧明文文件**，切换无痛。

**降级行为**：`--encrypt-data` 但密钥不正确时——
`Store::enable_vault` 拒绝启用（返回 false），退回明文模式，
因此**不会把数据写成无法解开的密文**；重启后 `read_db_bytes` 遇到密文但无密钥，
返回 `Err(VaultError::NoKey)` → 读回 0 条 + ERROR 日志，**原文件不被覆盖**。

# 十四、v1.6.0 新增架构（接口机制 + 前端重构）

> 本次改动集中在**「接口契约层」**与**「前端数据/导航层」**，业务逻辑（计分、报名、导出）
> **一行未动**。核心设计原则：**新增能力尽量放在"接缝"上，而不是散进 47 个 handler 里。**

## 14.1 后端：请求处理管线新增三个环节

改动前，一次请求的处理链路是：

```
accept → 解析 → 鉴权 → 二次确认 → 路由匹配 → handler → 拼响应
```

v1.6.0 插入三个环节（**标 ★**），并新增一个出口环节：

```
accept
  → 解析
  → ★ 限流预检（RateLimiter）
  → 鉴权
  → 二次确认
  → 路由匹配
  → ★ 参数校验（path_id / query_non_empty / query_pos_int）
  → handler（内部可能返回 ApiErr）
  → ★ 统一信封包装（wrap_envelope）
  → ★ 可观测记账（HttpStats.record）
  → 写出
```

**关键取舍：为什么用"分发层包装"而不是"改 47 个 handler"？**

`Router::dispatch_from_ip` 是所有路由的唯一出口。在这个出口处调用
`wrap_envelope()`，就能让**全部 47 个核心路由 + 5 个扩展路由**同时获得信封，
handler 一行不改。代价是需要在出口处判断"这个响应该不该套信封"
（SSE / 下载 / 非 JSON 必须跳过）——用 `envelope_skip(content_type, filename)`
统一判定，比改 47 处安全得多。

## 14.2 响应契约

```jsonc
// 成功
{ "ok": true, "data": <handler 原样返回的负载>, "ts": 1790411584 }

// 失败
{ "ok": false,
  "error": { "code": "E_VALIDATION", "message": "路径参数 id 必须是整数，实际为「abc」" },
  "message": "路径参数 id 必须是整数，实际为「abc」",   // 过渡期扁平文案，非契约
  "ts": 1790411584 }
```

**原负载完整保留在 `data` 内，一个字段都没挪。** 这是"旧测试零改动通过"的原因。

### 「藏在 Ok 里的错误」——本次最值得记住的一处设计

工程中有 handler 不返回 `Err`，而是返回 `200 Ok` + 一个 body 里带 `error` 键的 JSON
（如"学生不存在"这类软失败）。若信封只看"是不是 `Err`"，就会把它们包装成 `ok:true`，
出现**状态码说失败、信封说成功**的矛盾——正是 #40 的同类错误在新代码里的复现。

`wrap_envelope` 因此额外做一步：

```rust
// 非 2xx 状态 + body 含 error 键 → 还原为失败信封，保证 ok 与真实成败永不矛盾
```

## 14.3 错误码（`core::error::ErrCode`）

| 码 | 触发条件 | 典型 HTTP |
| --- | --- | --- |
| `E_VALIDATION` | 参数格式/取值不合法 | 400 |
| `E_NOT_FOUND` | 资源或路由不存在 | 404 |
| `E_CONFLICT` | 唯一性冲突（重名项目/学生） | 409 |
| `E_AUTH` | 需要口令 / 令牌无效 | 401 / 403 |
| `E_CONFIRM` | 敏感操作缺二次确认 | 428 |
| `E_LIMIT` | 触发限流 | 429 |
| `E_PAYLOAD` | 体积超限 / 媒体类型不支持 | 413 / 415 |
| `E_INTERNAL` | 服务端内部错误 | 5xx |

`from_status()` 提供兜底映射，保证**任何**响应都有码可给。
码的字面值由 `error_code_strings_are_stable_contract` 单测**锁定为契约**——
改动会让测试失败，从而迫使改动者显式确认"这是破坏性变更"。

## 14.4 限流（`core::ratelimit`）

三档滑动窗口，窗口统一 **10 秒**：

| 档 | 判定依据 | 本机配额 | 非本机配额 |
| --- | --- | --- | --- |
| `Sensitive` | `/api/auth/token`、`/api/dev/*` | 30 | 5 |
| `Write` | 非 GET 且非敏感路径 | 200 | 40 |
| `Read` | GET、`/api/smart/parse` | 600 | 120 |

- **本机来源聚合**：所有回环地址归一到 `"loopback"` 键，避免 `127.0.0.1` 与 `::1` 各自计数。
- **响应头**：`X-RateLimit-Limit` / `X-RateLimit-Remaining`；被拒时额外带 `Retry-After`。
- **设计目标**：**防误触与脚本风暴，不是防恶意攻击**。单机工具场景下，前端
  切页/刷新产生的正常流量远低于配额（实测连打 50 次读接口全 200）。

```
│ CACHE_TAGS       正则 → 资源标签（读缓存归类）      │
```

### 数据层三件事

1. **缓存**：GET 结果按 `method + path` 缓存，默认 TTL 5000ms。过期即清（不保留陈旧条目）。
2. **并发合并**：同一 key 的 in-flight Promise 被复用，`merged` 计数记录"省下的往返"。
   实测 **5 个并发同一 GET → 只发 1 个网络请求**。
3. **写后失效**：写操作成功后，按 `INVALIDATE_RULES` 清掉相关标签的缓存条目。
   例如 `POST /api/events` → 失效 `events / registrations / results / report`。

**`Data.request()` 签名与原 `api()` 完全兼容**，因此 49 处既有调用点无需改动；
新增 `nocache:true`（跳过缓存）与 `ttl`（自定义有效期）两个可选项。

### 导航层：从 if 链到注册表

改动前 `goPage` 内是 8 个 `if (name === "...")` + 一个独立的 `PAGE_NAMES` 数组，
两处需要手工保持一致——这正是踩坑 #34（`Ctrl+9` 崩溃）的土壤。

改动后页面元信息集中一处：

```js

  enter:  () => { startBoard(); bdStat(); },   // 进入要建 SSE 连接
  leave:  () => { stopBoard(); },              // 离开要断开

```

`auditPageRegistry()` 在启动时校验三类一致性（**这三类不一致都不会自己报错，
只会表现为"点了没反应"**）：

1. 每个注册页都有对应的 `<section id="page-*">`
2. 注册表与导航按钮 `data-page` **双向**一一对应
3. `order` 无重复（重复会让某页永远按不到快捷键）

结果存于 `window.__pageAudit`，诊断页直接展示为「✓ 页面注册表自检通过（8 个页面与 DOM 一致）」。

## 15.2 `core/sync.rs`：毒锁自恢复

```
调用点（37 处）
   store.rs(3) │ api.rs(21) │ main.rs(1) │ live_board.rs(9，仅测试) │ records_feed.rs(3)
        ↓  全部由 .lock().unwrap() 改为 .lock_recover()
```

## 15.3 `core/dirlock.rs`：数据目录独占锁

### 锁文件

路径 `<data_dir>/.sports-meet.lock`，内容为两行文本（**故意用人类可读格式**，
因为它的主要用途是"告诉用户是谁占着"）：

```
<pid>
<启动时间 RFC3339>
```

### 获取流程（两阶段）

```
DirLock::acquire(dir)
  │
  ├─ ① 若锁文件存在：
  │     解析 (pid, since)
  │       ├─ pid 活着        → LockOutcome::Busy { pid, since }   → 调用方拒绝启动
  │       ├─ pid 已死        → remove_file（回收陈旧锁）─────────┐
  │       └─ 内容不可解析    → remove_file（回收损坏锁）─────────┤
  │                                                              │
  └─ ② File::create_new(lock)  ← O_EXCL，原子创建  ←────────────┘
         ├─ Ok(f)   → 写入 (pid, now) → **写完后复查文件内容确为自己的 pid**
         │            复查失败 → 视为竞态，报环境错误
         └─ Err(..) → 说明有人在我 remove 之后抢先创建了 → 复查后如实报错
```

> **步骤 ① 里的 `remove_file` 是修复过程中新增的**（第一版漏了它，
> 导致陈旧锁被 `create_new` 误判为"被占用"——见 `docs/05` #44 的"修复中的二次踩坑"）。

### 为什么不用 `flock` / `LockFileEx`

`std` **没有跨平台文件锁**，要用就得引 `fs2` / `nix` / `winapi` 或写 `unsafe` FFI，
**违反规则 10**。而本项目只需要挡住"人手误操作"（双击两次 exe），
`pid` 探活方案**零依赖、三平台可编译、且能给出人类可读的占用者信息**。

代价（**已如实记录在 README 的"诚实的限制"里**）：Windows 上 PID 可能被复用，
极端情况下会把"死锁"误判为"活锁"。逃生开关即 `--ignore-lock`。

### `pid` 探活的三平台实现

| 平台 | 实现 | 判定 |
| --- | --- | --- |
| Linux | 检查 `/proc/<pid>` 是否存在 | 存在即存活 |
| Windows | `tasklist /FI "PID eq N" /NH` 解析输出 | 输出含该 PID 即存活 |
| 其他 | **保守返回 `true`** | 宁可误报占用，也不误放行导致丢数据 |

### 逃生开关 `--ignore-lock`

`DirLock::disabled()` 构造一个 **pid = 0 的哨兵**。选择 pid=0 作为哨兵的好处：

- `Drop` 里判断 `pid == 0` **直接返回** → 绝不误删别人的锁文件
- `is_disabled()` 可直接用于日志判断
- **不需要引入 `Option<DirLock>`**，接入 `main` 的代码保持线性

## 15.4 接入位置：`main.rs`

```
main()
  ├─ 解析参数（新增 --ignore-lock 分支 → 局部变量 ignore_lock）
  ├─ 获取数据目录锁 ★ 必须在"读数据"之前 ★
  │    let _dir_lock = acquire_data_lock(&dir, ignore_lock);
  │      ├─ None     → std::process::exit(1)（已打印占用者信息）
  │      └─ Some(l)  → 继续
  ├─ Store::load(...)        ← 读数据
  ├─ 启动 HTTP 服务          ← 跑服务
  └─ 退出                    ← 写数据 / 释放锁（Drop）
```

**为什么锁绑定在 `main` 的局部变量上（`let _dir_lock`）而不是塞进 `Store` 或 `Core`**：

锁的生命周期必须覆盖"**读数据 → 跑服务 → 写数据**"的全程。
若绑在 `Store` 上，它会随 `Core` 的移动 / 重建而**提前 `Drop`**——
"什么时候重建 Core"取决于运行路径，这类 bug **极难复现**。
绑在 `main` 栈上则生命周期与进程一致，**语义最直白**。

**错误提示的分情形**（`acquire_data_lock`）：

| 情形 | 提示 |
| --- | --- |
| `Busy { pid, since }` | "数据目录已被另一个进程占用" + 占用 PID + 启动时间 + 锁路径 + `--ignore-lock` 用法 + **说明为什么危险（静默丢数据）** |
| 环境错误（pid 为 0 等） | 如实报"环境问题"，**不谎报占用** |

## 15.5 前端：`TAG_TTL` 与 `ttlFor()`

v1.6.1 前端**只改了一处逻辑**，但它是 P0 级修复：

```
请求路径
  │
  ├─ ttlFor(path)   ★ 新增：标签级 TTL 覆盖
  │    ├─ tags = tagsFor(path)
  │    ├─ best = DEFAULT_TTL (5000)
  │    └─ for t in tags:
  │         if TAG_TTL 有 t: best = min(best, TAG_TTL[t])
  │         └─ TAG_TTL = { system: 0, undo: 0 }   ← 0 表示"不缓存"
  │
  ├─ cacheable = isRead && !nocache && ttl > 0
  │    ├─ cacheable → 查缓存（命中即返回）
  │    └─ 否则      → 走网络（**但仍享受 in-flight 合并**）
  │
  └─ 写入侧
       ├─ 读请求 且 cacheable → cache.set(..., expireAt = now + ttl)
       └─ 写请求             → invalidateForWrite(path)
```

**`ttl=0` 为什么等价于"不缓存"**：`:0` 使 `expireAt = now`，
而命中条件是 `expireAt > now` —— **恒为假**。所以不需要新增 `if (nocache)` 分支，
**判定收敛到唯一一处**，少一个能写错的地方。

**纵深防御**：另在 `INVALIDATE_RULES` 补了一条

```js
{ re: /^\/api\/dev\/(unlock|lock)/, tags: ["system"] },
```

即使将来有人把 `TAG_TTL` 改回去，"解锁/上锁"这类写操作也仍会主动失效 `system` 缓存。

# 十六、v1.7.0 新增架构（赛程编排 / 秩序册）

本次新增「赛程编排」模块，补全校运会积分系统原先缺失的"场地 / 单元 / 分组 / 分道 / 冲突检测"能力。核心原则：**可解释 > 最优**（贪心而非全局优化）、**老数据零迁移**（缺失字段回退默认，规则 20）、**新增不破坏既有契约**。

## 16.1 新增模块一览

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 数据模型 + 算法 | `core/schedule.rs` | `Venue`/`Session`/`Slot`/`LaneAssign`/`Conflict` 模型；`detect_conflicts`（7 类）；`auto_arrange`（贪心）；`assign_lanes`（蛇形分组 + 道次）；`default_venues`/`default_sessions`；`*_to_json`/`from_json`（缺失回退默认） |
| HTTP 接口 | `core/schedule_api.rs` | `get_schedule`/`set_venues`/`set_sessions`/`set_days`/`arrange`/`clear`/`get_lanes` 七个处理器，签名 `fn(&Core, &Request) -> Result<Response, ApiErr>` |
| 持久化 | `core/store.rs` | `Data` 新增 `venues`/`sessions`/`slots`/`schedule_days` 四字段；`from_json` 缺失回退默认 |

> 依赖：**纯 `std` 实现**，不引入图论/调度库（规则 10 不变）。场地并行用 `Vec` 遍历分流到 `for_track`/`for_field`，零新增依赖。

## 16.2 核心数据模型

```rust
pub struct Venue { pub id: i64, pub name: String, pub for_track: bool, pub for_field: bool }
pub struct Session { pub id: i64, pub day: i64, pub name: String, pub start_min: i64, pub duration_min: i64 }
pub struct Slot { pub event_id: i64, pub session_id: i64, pub start_min: i64, pub duration_min: i64, pub venue_id: i64, pub group_count: i64 }
pub struct Conflict { pub severity: Severity, pub kind: String, pub message: String, pub event_ids: Vec<i64>, pub student_id: Option<i64>, pub time_desc: String }
pub struct LaneAssign { pub group_no: i64, pub lane: i64, pub student_id: i64, pub student_name: String, pub class_name: String, pub seed: Option<f64> }
```

- **默认场地** `default_venues()`：`[田径跑道(for_track), 田赛区(for_field)]`——两场地同时开工 = 径赛田赛并行。
- **默认单元** `default_sessions(days)`：`days × {上午 08:00–11:30(210min), 下午 14:00–17:00(180min)}`；`days=2` → 4 单元。
- **时长估算** `estimate_duration_min(ev, n)`：保证随人数单调不减（`.max(per_group)` 修正早期 `.max(6)` 地板压平 bug）。

## 16.3 冲突检测（7 类，实时跑）

`detect_conflicts(events, regs, slots, venues, sessions, students)` 在 `schedule_view` 每次拉取时现场调用：

| 严重度 | kind | 含义 |
| --- | --- | --- |
| Error | `venue_overlap` | 同一场地时间重叠 |
| Error | `event_clash` | 同一学生兼报项目时间冲突（休息不足 30min 才算 Warn，这里指直接重叠） |
| Warn | `short_rest` | 兼项休息不足 30min |
| Warn | `checkin_tight` | 检录时间不足 |
| Error | `venue_type_mismatch` | 项目排到不匹配的场地（径赛排田赛区等） |
| Error | `out_of_session` | 超出单元范围 |
| Info | `no_registration` | 项目未报名（提示，非错误） |

## 16.4 贪心编排（`auto_arrange`）

1. 最长项目优先（LPT），`replace=true` 时清空已有 slots；
2. 按 `is_track()` 把项目分流到 `for_track`/`for_field` 场地（并行铺开）；
3. 每个项目在场地时间轴上找**最早可行空位**，兼项学生检查后推 5min；
4. 排不下的项目如实进 `unplaced: Vec<(i64, String)>`，**不静默丢弃**（规则 20 的反面：容量不足要可见）。

返回 `ArrangeResult { slots, unplaced }`，`arrange` 处理器写入 `d.slots` 并回显 `placed`/`unplaced`。

## 16.5 分组分道（`assign_lanes`）

- **径赛**：蛇形分组（`gc = group_count`，`col = i % gc`），道次按 `[4,5,3,6,2,7,1,8]` 排（好成绩居中）；早期"17 人只排 9 个"的静默丢人 bug 已修，加 `debug_assert_eq!(总人数守恒)`。
- **田赛**：按成绩倒序，出场序 `lane = total - i`（好成绩压轴）。
- 无 `seed` 成绩时退化为报名顺序，结果**稳定可复现**。
