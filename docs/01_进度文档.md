## v1.9.10 迭代（本次）

> 类型：**录入效率 + 产出对齐**。来源：老师提出「把表给 AI，让 AI 帮我录入，
> 最后形成我发给你的那个表格的最后一页的样子」——他要的不是又一个输入框，
> 而是「AI 录完 → 自动得到学校那张团体总分表」。

### 一、AI 表格导入（新入口，与成绩公布表共用一套匹配）

`src/core/ai_table.rs`：把粘贴文本切成 `scoresheet::RawRow`（与 xlsx 入口同构），
再调 `api::import_rows` —— 匹配、班级消歧、自动补报名、落盘**只有一份实现**。

| 输入形态 | 例子 |
|---|---|
| Markdown 表格 | `\| 项目 \| 班级 \| 姓名 \| 成绩 \|` |
| Excel 复制的制表符 | `男子100米\t初二3\t张三\t12"34` |
| 逗号分隔 | `男子100米,初二3,张三,12.34`（中英文逗号） |
| 空格分隔 | `男子100米 初二3 张三 12.34` |

列序不限，按表头定位；「组别：八年级组」存在时纯数字班号自动补年级；
Markdown 分隔行（`---`）、无成绩行、说明行自动跳过；项目列缺失时
报出具体行号而不是静默丢弃。

### 二、AI 助手新增 `import_table` 动作

提示词里给出四列格式与示例，助手把整段原始记录整理成表后输出
`{"type":"import_table","text":"..."}`；前端按钮一键填入粘贴框并预览，
仍需老师点「确认导入」——与 `fill_scores` 的「不直接改库」原则一致。

### 三、团体总分表（`src/core/summary.rs`）

按学校《得分表》最后一页的 14 行顺序聚合 `results.points`：

```
project_row(event_name) → 0..13  （100米 … 摸高）
```

- 同名男女项目合并一行；`avoid` 规则排除「三级跳远」误入「跳远」；
- 班级列取数据里真实出现的班号，不按 `settings.class_count` 铺满；
- 只读 `points`，未算分的项目进 `pending`，界面黄字提示，**不另算一套**；
- 原表外项目（铅球/跳高/三级跳远）仅在确有成绩时追加末尾；
- 名次并列同名次，与 `grade_total_table` 同口径。

导出 `GET /api/export/total_table?grade=初二`：合并标题、表头底色、全表边框、
冻结窗格、整数不带小数点。预览接口 `GET /api/summary/total` 供报表页渲染。

### 四、验证

- 新增单测 12 项（summary 5 + ai_table 7），库测试全绿；
- 实测：真实项目数据下导出 xlsx 用 openpyxl 回读，行序/列/合计/名次与手算一致；
- 粘贴导入用 Markdown、制表符、逗号三种文本各跑一遍，写入条数与匹配报告一致。

## v1.9.9 迭代

> 类型：**录入兼容性修补**。来源：老师反馈「时间只能是 a.b，不能 a"b」——
> 手计时记分习惯写 `12"34`，系统判为「格式不认识」，成绩不进排名。

### 一、时间写法全兼容（`scoring::parse_score`）

| 输入 | 解释 | 结果 |
|---|---|---|
| `12"34` / `12"3` / `12"` | 秒表：引号后是秒的小数位 | 12.34 / 12.3 / 12 |
| `1'23"45` / `1'23` / `1'` | 撇号是分，引号是秒 | 83.45 / 83 / 60 |
| `12秒5` / `1分23秒45` / `12秒` | 中文单位口述 | 12.5 / 83.45 / 12 |
| `1:23.45` / `12.34` | 原有写法 | 不变 |
| `12,34` | 逗号当小数点 | 12.34 |
| `１２．５` / `12”34` / `1′23″45` | 全角数字、中文引号、撇号 | 12.5 / 12.34 / 83.45 |

实现：新增 `normalize_time_text()`，先把全角/中文标点/引号/分秒单位统一成
`分:秒.小数`，再交给原有校验（秒数必须 < 60）。**只在「时间」单位下启用**，
田赛（米）与计数（个）不受影响。

### 二、配套文案

| 位置 | 改动 |
|---|---|
| 成绩录入框 placeholder | `如 12"34 或 12.8` |
| 后端错误提示 `unit_hint` | `如 12"34 或 1:23.45（12.8、12秒5 也认）` |
| AI 提示词 | 提醒模型：JSON 里不能写裸引号，秒表写法改成 `12秒34` |
| 使用说明 | 速查条目补秒表写法 |

存储仍保留老师输入的原文（写 `12"34` 就显示 `12"34`），排名与赋分用解析后的
数值，两者不冲突。

## v1.6.1 迭代（本次）

> 类型：**缺陷修复（无新功能）**。来源：用户先问"你认为还有哪里可以改进"，
> 我给出基于**实测证据**的四项清单；用户随即下达「**现在开始修，修完全部 bug**」。
> 版本定为 **v1.6.1**。

### 〇、方法论：为什么是"自省式修复"

v1.6.0 引入了一整套新机制（缓存、信封、限流、注册表）。v1.6.1 的做法不是"再看看有没有别的新功能"，
而是**逐条反推 v1.6.0 的每个机制"最可能怎么坏"**，并且要求凡是能构造出**真实故障场景**的，
一律先写出能复现的测试、再修——避免修出"看起来很对但没人验证过"的假修复。

四个问题中，**#43 与 #44 是 v1.6.0 亲手引入的缺陷**（前者是缓存机制用错，后者是被"整文件原子写"的原子性表述误导）。

### 一、四项修复（全部落地并行为级验收）

| # | 等级 | 问题 | 根因 | 修复 | 验收证据 |
| --- | --- | --- | --- | --- | --- |
| 43 | **高** | 状态类接口 5 秒内返回**过期状态** | `system` 标签被 `CACHE_TAGS` 打上，但 `INVALIDATE_RULES` **没有任何规则会让它失效**——标签只被"挂上"，从未被"触发"；且 `ttl` 是全局恒定 5 秒 | `TAG_TTL = { system: 0, undo: 0 }` + `ttlFor(path)` 统一判定（TTL=0 即不缓存） | 连续两次 `GET /api/dev/status`，后端计数 **3 → 4**（修复前第二次命中缓存） |
| 44 | **高** | 两进程同写一份数据**静默覆盖** | "整文件原子写"只保证**单文件不写坏**，不保证**两进程不互相覆盖** | 新增 `core/dirlock.rs`（pid 探活 + `O_EXCL` 原子创建）；占用即**拒绝启动并打印 PID**；`--ignore-lock` 逃生 | 真实双进程：第二进程 **退出码 1** + 打印占用 PID；`--ignore-lock` 后 **200** |
| 45 | 中高 | 一处 panic 毒化 Mutex → **全服务永久 500** | 37 处 `.lock().unwrap()`：持锁期间 panic 后锁被标 poisoned，之后**每次** `unwrap()` 都再 panic | `core/sync.rs` 的 `LockExt::lock_recover()`：`into_inner()` 自恢复 + WARN 留痕；**37 处全量替换** | 4 个单测（含 `lock_recover_survives_poisoned_mutex`） |
| 46 | 中 | `store.rs` 是**数据落盘核心路径却 0 单测** | 历史欠账：测试都堆在 `api.rs` 与集成层，`store` 靠集成"顺带覆盖"，边界全没测 | 新增 **11 个单测** | 11/11 通过（含"错误密钥必须丢弃而非乱码"） |

### 二、关键设计决策（及为什么不做另一些事）

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 如何表达"不缓存" | **`TTL=0`**，不是新增 `nocache` 分支 | `expireAt > now` 在 `ttl=0` 时恒不成立，自然走真实请求；判定收敛到 `ttlFor()` **唯一一处**，少一个能写错的开关；且仍享受 in-flight 合并 |
| 毒锁怎么办 | **自恢复**，不是快速失败 | 单机记分工具，内存数据是**完整快照**（非半程提交），写入是整文件原子写 → "继续服务" > "严格一致性"；坏的只是**本次**请求结果 |
| 用什么做进程互斥 | **pid 探活**，不引 `flock`/`LockFileEx` | `std` 无跨平台文件锁，要做得引 `fs2`/`nix`/`winapi` 或写 `unsafe` FFI，**违反规则 10**；本项目只需挡"人手误操作"，pid 方案**零依赖、跨平台、人类可读** |
| 陈旧锁要不要自动清理 | **不自动清理** | 自动清理会让"两进程真在同时写"更隐蔽；宁可让使用者看到提示后**自己决定**是否 `--ignore-lock` |
| 锁挂在哪 | **`main` 栈上**（`let _dir_lock`），不塞进 `Store` | 生命周期必须覆盖"读数据 → 跑服务 → 写数据"全程；绑 `Store` 会随 `Core` 移动/重建而**意外释放**，这类 bug 极难复现 |

### 二、关键设计决策

**① 信封包装放在"分发层唯一出口"，而不是改 47 个 handler**

`Router::dispatch_from_ip` 是所有路由的唯一出口。在此调用 `wrap_envelope()`，
**全部 47 核心路由 + 5 扩展路由**同时获得信封，handler 一行未改。
代价是需判定"是否该跳过"（SSE / 下载 / 非 JSON），用 `envelope_skip()` 统一处理。

**② 识别「藏在 Ok 里的错误」（本次最值得记住的坑）**

部分 handler 用 `200 Ok` + body 里带 `error` 键来表达软失败（如"学生不存在"）。
若信封只看 `Err`，会把它们包成 `ok:true`——**状态码说失败、信封说成功**。
`wrap_envelope` 因此额外检测"非 2xx + body 有 `error` 键" → 还原为失败信封。

**③ 旧测试零改动通过 = 信封非破坏性的证据**

v1.5.2 的 37 个集成用例**一行未改全部通过**——因为信封把 handler 原负载
**完整保留在 `data` 内**，既有的 `body.contains("...")` 断言仍然成立。

**④ 前端 `Data.request()` 签名与原 `api()` 完全兼容**

49 处调用点**零改动**。新增 `nocache` / `ttl` 两个可选参数。

**⑤ 页面注册表 + 启动自检**

`PAGES` 数组取代 `goPage` 内 8 个 `if` + 独立的 `PAGE_NAMES` 数组（后者正是踩坑 #34 的土壤）。
`auditPageRegistry()` 启动时校验三类一致性——**这三类不一致都不会自己报错，只会表现为"点了没反应"**。

> 类型：**小版本优化（密钥机制与防破解）**。来源：用户要求"增加一个密钥机制，可导向到开发者模式，加密各种库"。
> 原则：**向后兼容优先**（规则 12）——不带 `--devkey` 时行为与 v1.5 **完全一致**；

### 一、四项能力落地

**① 密钥机制（慢哈希 KDF）**

- 新增核心模块 `core/license.rs`（约 450 行，12 个单测）
- 源码中**只存密钥指纹的哈希**（`LICENSE_FINGERPRINT`），密钥本身不落盘、不进日志、不出现在任何响应
- `slow_hash(input, rounds)` = `FNV1a(h ‖ 盐 ‖ 轮序号 ‖ 输入)` 迭代 **200,000 轮**（实测 ~30ms）
  - **无预计算表空间**：不像彩虹表那样能预先算好；每多猜一个密钥就要真跑 20 万轮
  - 抗暴力枚举能力远优于单次哈希（单次 FNV 约 1ns，20 万轮约 30ms，相差 7 个数量级）
- `fingerprint(input) = slow_hash(input, KDF_ROUNDS)`；盐为 `sports-meet::license::v1.5.1`
- **错误密钥静默降级**：不打印、不报错、不退出，只是 `key_ok = false`
  - 理由：若给明确报错，攻击者就把"猜密钥"变成了**有反馈的暴力枚举**（错/对是 1 bit 信息）；
    静默让猜测过程**零信息增益**
- `const_time_eq` 常量时间比较，防时序侧信道
- 新增参数 `--devkey <密钥>` 与 `--devkey-fingerprint <密钥>`（后者计算并打印指纹，用于更换密钥）

**② 开发者模式（三重条件准入 + 审计留痕）**

- `License` 状态机：`DevMode::Locked` / `DevMode::Unlocked`，用 `AtomicBool` 承载
- **三重条件 AND 关系，缺一不可**：
  1. `key_ok == true`（`--devkey` 正确）
  2. 请求来自本机回环地址（`--i-know-the-risk` 之外的**独立**条件）
  3. `risk_acked == true`（启动时显式传 `--i-know-the-risk`）
- **本机判定不看任何请求头**：`core/http.rs` 新增 `is_loopback(&SocketAddr)`，
  走 TCP 对端地址（`stream.peer_addr()`），覆盖 `127.0.0.0/8`、`::1`、IPv4-mapped `::ffff:127.x`
  - 不读 `X-Forwarded-For` / `Host`——这些都可伪造；反向代理后面部署时开发者模式**自动失效**（有意设计）
- 新增路由：`GET /api/dev/status`、`POST /api/dev/unlock`、`POST /api/dev/lock`
- **dev 路由免口令鉴权**（但仍受三重条件约束）——否则"忘口令 → 进不去诊断页 → 更拿不回"会死锁
- 解锁后：敏感破坏性操作**跳过二次确认**，并强制写审计：
  `dev_unlock` / `dev_lock` / `dev_bypass_confirm` / `dev_clear_results`，`actor` 标为 `devmode`
- 前端顶栏新增**红色脉冲警示条**，开发者模式生效期间常驻可见

**③ 数据加密（数据保险库）**

- 新增核心模块 `core/vault.rs`（约 470 行，18 个单测）
- **FNV 派生 XOR 流加密**：64bit 块号作计数器，类 CTR 结构；`keystream(seed64, block_no, len)`
- 每 **4 KiB** 块后追加 **8 字节 MAC**（`block_mac`），做完整性校验
- 文件头 14 字节：`SMEV` 魔数(4) + 版本(1) + 模式(1) + 种子指纹(8)
- `read_auto` 自动识别明文/密文（看魔数），**向后兼容**：老明文文件照读

### 四、本次实测暴露并修复的 6 个真实 bug（最有价值的部分）

> 全部是"静态测试测不出、只有真跑才暴露"的问题。详细复盘见 `05_踩坑记录.md` #31–#36。
> 其中 **#31–#34 在开发/浏览器实测阶段暴露**，**#35–#36 在打包前逐场景手工核对阶段暴露**——
> 后两个尤其说明：**自动化全绿 ≠ 可以跳过人工按"用户真实用法"走一遍**。

1. **开发接口被普通口令鉴权拦住，形成"解锁死锁"**（致命）
   - 现象：带 `--password` 的实例上 `POST /api/dev/unlock` 返回 **401**，诊断页解锁按钮完全失效。
   - 根因：`dispatch_inner` 按 HTTP 方法判定，POST 即视为写操作拦截。
   - 修复：白名单加 `is_dev_endpoint = path.starts_with("/api/dev/")`；
     补对照测试 `dev_endpoints_bypass_password_auth_but_not_conditions`。
   - **教训**：与 #26 **同类错误的第二次发作**。方法粒度判断读写是反复踩的坑，
     需形成"任何 POST 先问它属哪一类"的条件反射。

2. **两层确认机制互相掩护，只放开一层仍然 428**（致命）
   - 现象：修完 #31 后解锁成功，但同个 DELETE 仍返回 428（带 `{preview:{...}}`）。
   - 根因：项目有**两套**确认机制——HTTP 层 `is_sensitive_path`（`confirm_kind: password`）
     与业务层 `delete_event(id, confirmed)` 的 `?confirm=1` 预检。
   - 修复：`confirmed = 查询参数 == Some("1") || req.dev_mode`，并写审计 `dev_bypass_confirm` 兜底。
   - **教训**：改确认逻辑前先全项目搜索有几个同名机制；同状态码不同语义必须能区分。

3. **自实现流加密"末块"边界：`% unit != 0` 判定是错的（死代码）**（中）
   - 现象：`vault::open` 里的 `if body.len() % unit != 0` 实际什么也没检查——
     末块长度是 `plain.len() % BLOCK_SIZE`，天然不整除；真正兜底的是循环里的 `checked_sub(8)`。
   - 修复：删掉误导性判定，改为显式 `if !body.is_empty() && body.len() < 8 { Truncated }`；
     补测试 `last_block_length_is_not_multiple_of_unit`（10000 B 明文，逐字节砍尾 1..=8 均须报错）、
     `body_shorter_than_one_mac_rejected`。
   - **教训**：「看起来在检查」的死代码比不检查更危险——它让人误以为边界已覆盖。

4. **放宽快捷键取值范围却没同步检查数组长度，<kbd>Ctrl+9</kbd> 静默失效**（中）
   - 现象：`PAGE_NAMES` 只有 8 项，`Ctrl+9` 取索引 8 → `undefined` →
     `$("page-undefined")` 为 `null` → `.classList` 抛 `pageerror`，
     且异常导致同一函数内**后续所有 `refresh*()` 全部不执行**。
   - 修复（两层防御）：快捷键加 `idx < PAGE_NAMES.length` 检查；`goPage` 首行 `if (!target) return;`。
   - **教训**：规则 17 升级为"前端交互三查"（事件绑定 / 数组下标 / 页签一致）；
     "控制台零错误"必须**硬断言**，不能靠肉眼扫一眼。

5. **加密落盘后必须"带着 `--encrypt-data` 才读得到"，忘记它数据像凭空消失**（中高）
   - 现象：`--encrypt-data` 加密落盘后，换个实例只带 `--devkey`（不带 `--encrypt-data`）
     启动 → 读回 **0 条**，而所有自动化测试**全绿**。
   - 根因：`--encrypt-data` 本是"写入开关"，却**隐式决定了读取行为**——
     "能否读到"取决于一个跟数据无关的启动参数。
   - 修复（两层）：`activate_vault` 自动探测（`.smev` 在且明文不在 → 自动进入加密读取模式）；
     `Core::new` 先设 `vault_detected` 再读盘；新增 `vault_enabled` / `vault_detected`
     两字段分开上报；诊断页三态显示。
   - **教训**：**写入配置不得隐式决定读取行为**；"用户要记住两个参数才能正常工作"就是隐患。
     测试全部由知晓实现的人编写，天然会"正确地"传参，因此**必须专门测"半省略调用"**。

6. **启动横幅的"密钥指纹前缀"是编译期常量，与实际密钥无关**（低中）
   - 现象：正确密钥 / 无密钥 / 错误密钥三种启动，横幅里的指纹前缀**都是 `35d0`**；
     无密钥时甚至出现"前半句说缺少密钥、后半句给出指纹"的自相矛盾。
   - 根因：横幅打印的是编译期内置的**演示密钥**常量 `LICENSE_FINGERPRINT[..4]`，
     而非本实例种子的真实指纹，且**无条件打印**。
   - 修复：改为**只在本实例确实有种子时**打印，且打印 `vault::seed_fingerprint(seed)`
     的真实值（实测 `482c`，与 `/api/dev/status` 的 `seed_fingerprint` 前四位吻合）。
   - **教训**：给使用者用来核对的信息必须是**本实例真实值**，不能是常量；
     **条件渲染要跟着条件走**——"前后矛盾的一句话"是最强的自检信号。

### 五、诚实声明（明示局限）

> 本版加密与慢哈希均基于 **FNV-1a 64 位自实现**，**不是密码学安全算法**。

- 它**显著提高**了直接读取数据文件、窥探源码明文密钥、随手改数据的门槛；
- 但**不能抵御**拥有充足算力、知晓算法的**定向破解者**；
- 密钥机制是「**提高门槛**」而非「**不可逾越**」；数据加密**默认关闭**；
- 完整强度分析、风险清单（R1–R7）与验收自测清单见 **`docs/12_密钥与防破解说明.md`**。

### 一、四项前沿技术落地

**① 实时赛况大屏（SSE，Server-Sent Events）**

- 新增扩展 `extensions/live_board.rs`（约 620 行，7 个单测）
- 核心 `core/http.rs` 新增流式响应能力：`Body::Bytes` / `Body::Stream` 双态枚举 +
  `Response::sse(producer)` + `StreamWriter`（`send` / `comment` / `is_closed`）
- HTTP/1.1 **chunked 分帧**传输；15 秒心跳（注释帧 `: ping`）保活；`MAX_VIEWERS=32` 并发上限
- 多屏广播：每观众一条 `mpsc` 通道，惰性清理断连（`retain` + `send().is_err()`）
- **新观众即时同步**：接入瞬间先推一帧 `snapshot`，无需等下一次成绩变动
- 路由：`/api/ext/live-board/stream`（SSE）/ `/snapshot`（纯 JSON 兜底）/ `/status`（在线数）
- 前端新增独立「实时大屏」页（`#board`）：`EventSource` 消费、指数退避重连、
  页面隐藏/离开自动断开、全屏投屏模式（`fs-mode` 字号按 `vh` 放大）
- **设计要点**：核心 `Extension::routes()` 的 handler 无法捕获 `self`，且核心 trait
  刻意不提供 `as_any()`；改用**扩展自持静态槽位**（`OnceLock<Arc<LiveBoard>>`）取回实例，
  **核心零改动**

**② 操作审计哈希链（tamper-evident audit log）**

- 新增核心模块 `core/audit.rs`（约 700 行，14 个单测）
- FNV-1a 64 位哈希，`prev_hash` 链式绑定；创世值 `0000000000000000`
- 落盘 `data/audit/audit-YYYY-MM-DD.jsonl`（O_APPEND 追加写，按日滚动）
- **字段边界消歧**：哈希时在每段前插入 `0x1f` 分隔符，避免 `("ab","c")` 与
  `("a","bc")` 碰撞（有专门单测）
- `verify()` 同时检出三类破坏：`bad_hash_at`（内容被改）/ `bad_link_at`（删中间条、换序）/
  `unparsable_lines`（坏行容忍，不中断校验）
- 跨天换文件时**链头延续**，不断链
- 已接入 10 类业务动作：project/student/registration/results/settings/undo/import + 令牌签发
- 接口：`GET /api/audit`（面板）、`GET /api/audit/verify`（校验）
- **完全无 `unsafe`**：初版用 `&mut *(a as *const Auditor as *mut Auditor)` 被
  `invalid_reference_casting` 拒绝（Rust deny by default），重构为
  `struct Auditor { dir, state: Mutex<AuditorState> }` 彻底消除

**③ 签名令牌鉴权（口令不再逐次明文回传）**

- 令牌格式 `<expire_unix>.<nonce>.<sig>`，`sig = H(secret ‖ expire ‖ nonce)`
- 进程内随机密钥（纳秒 + 栈/堆地址 ASLR + pid + tid + 原子计数 → 两轮 FNV-1a → 32 位 hex），
  **不落盘**；服务重启即失效
- TTL 12 小时；`POST /api/auth/token` 用口令换令牌，`GET /api/auth/check` 探测状态
- `is_authorized()` 先比口令（v1.4 旧客户端兼容）再验令牌（v1.5 推荐路径）
- 前端口令**只在校验那一刻存在内存**，不写 localStorage（v1.4 是直接存口令）
- **诚实说明局限**：基于 FNV-1a 而非标准 HMAC-SHA256，**不是密码学意义的 MAC**；
  它挡抓包重放与随手改 URL，挡不了有离线碰撞能力的对手（已写入接口文档注释）

**④ 可解释智能推荐 + 宽容成绩解析**

- 新增核心模块 `core/smart.rs`（约 830 行，26 个单测）
- 宽容解析：全角→半角（U+FF01..FF5E 减 0xFEE0、U+3000→空格）、中文时间单位
  （`1分23秒45`→`1:23.45`）、秒表式（`1:23.45`）、单位后缀、无效标记
  （弃权/退赛/DNS/DNF/`—`/`/` 等）→ 标 `void` 而非报错；**无法识别时明确返回
  `recognized:false` + `hint`，绝不猜测**
- 可解释推荐：`score = 0.70×成绩优势 + 0.20×稳定性 + 0.10×参与度`，每项生成中文 `reason`
  - 成绩优势：**组内归一化**（径赛倒序 / 田赛正序，同 `name`+`unit` 视为同项目历史）
  - 稳定性：变异系数 CV（0→1.0，≥0.15→0.0），单样本给中性 0.5 并说明
  - 参与度：已报项目越少越优先（让更多人上场）
- 权重可调：`?w_perf=&w_stability=&w_spread=`
- 接口：`POST /api/smart/parse`（解析预览，只读不落库）、`GET /api/smart/recommend`

### 五、本次实测暴露并修复的 5 个真实 bug（最有价值的部分）

     恰好绕开了 `"全部"` 这个取值。测试覆盖了"限定年级"，漏了"不限年级"这条**更常用**的路径。
   - 修复：`grade_unrestricted` 同时识别 `""` / `"全部"` / `"通用"`（与 `api.rs:1020`
     的报名校验口径对齐）；测试夹具默认值改为 `"全部"`，并补 3 个回归测试
   - **教训**：夹具默认值必须取**线上最常见**的值，而不是取"方便写测试"的值。

3. **`withBusy` 包装的函数忘记绑定 `onclick`**
   - `const smartParse = withBusy($("rs-smart-go"), …)` 之后漏了
     `$("rs-smart-go").onclick = smartParse;`，按钮完全不响应且**不报错**。
   - 修复：补上绑定；并写了个脚本**系统性扫描**所有 `withBusy` 变量与 `.onclick` 赋值，
     确认无同类遗漏（13 个 `withBusy` 函数全部已绑定）
   - **教训**：前端"静默失效"比报错更难查——绑定语句和定义语句分离时，肉眼极易漏看。

4. **令牌面板在未启用口令时误报错误**
   - 无口令模式下 `POST /api/auth/token` 返回 400"无需令牌"，前端却先弹输入框。
   - 修复：先 `GET /api/auth/check` 探测 `password_enabled`，未启用则直接提示并返回。
   - 顺带修正字段名：接口返回 `ttl`（秒）与**可读字符串** `expires_at`，
     而前端曾误用 `ttl_secs` 并把 `expires_at` 当 Unix 时间戳去减——两者都改了。

5. **「删除」按钮点击无反应 —— v1.2 起就存在的遗留 bug**（中，但影响面大）
   - 前端写 `const p = pv.preview;`，而后端 `delete_preview` 返回的是**扁平**对象
     `{ok, name, registrations, results}` —— 没有 `preview` 这层。
   - 后果：`pv.preview === undefined`，读 `.registrations` 抛 TypeError，
     确认框不弹出 → **通过 UI 删除项目/学生的功能从 v1.2 起一直不可用**。
   - **为什么两个版本没发现**：v1.4 的浏览器实测清单是按"本次改了什么"列的，
     删除按钮（v1.2 就有、本次没改）从未被点过；curl 测试只验后端，绕过前端渲染。
   - 修复：`const p = pv.preview || pv;` + 字段兜底 `?? 0`；
     并把「删除项目 → 第 1 层输项目名 → 第 2 层输口令 → 真正删除」列为**固定实测场景**（6 项断言）
   - **教训**：**验收清单要按"功能面"列，不能按"改动面"列**。没改过的老功能
     恰恰最容易缺测试——它们不在本次的注意力范围内，但用户天天在用。

6. **浏览器控制台 1 条 404**（低）
   - 原因：未提供 `favicon.ico`，浏览器自动请求 404。
   - 修复：`<link rel="icon">` 内联 data-URI SVG（保持"零外部资源"约束，
     不新增文件、不新增网络请求）。修复后控制台**完全洁净**。

## v1.8.0（服务端授权机制）

**目标**：为项目增加服务端校验密钥机制（持久 + 临时），支持离线降级，
密钥基于机器指纹与哈希，客户端→服务端走加密信道，产出三个包。

### 已完成

| 模块 | 文件 | 说明 |
| --- | --- | --- |
| 机器指纹 | `src/core/aim/hwid.rs` | 主板/磁盘/CPU 三项硬件特征，FNV 慢哈希 50 万轮 |
| 加密信道 | `src/core/aim/channel.rs` | 类 CTR 流密码 + 整包 MAC + 三重防重放；**与服务端同源** |
| 授权管理 | `src/core/aim/client.rs` | 激活 / 校验 / 离线降级 / 加密缓存（`SMAL`） |
| 服务端 | `aim-server` 包 | 零依赖 HTTP、密钥库、签发/吊销/续期、票据签名 |
| 集成 | `api.rs` / `http.rs` / `main.rs` | 4 条授权路由、门禁、CLI、启动横幅 |
| 测试 | `tests/wire.rs` / `tests/e2e.rs` | 双端契约 9 项 + 端到端 6 项 |
| 交付 | `build.sh` → `build_out/` | 源码包 / 发行包 / 服务器包 |

### 关键成果

- **370 个自动化测试全绿**（客户端 327 + 服务端 43）
- e2e 测试**抓到 2 个会流入生产的严重缺陷**（漏传票据、自死锁）
- 发行包**零源码**、符号剥离、盐字符串混淆，`strings`/`nm` 均查无敏感信息
- 离线降级满足用户核心诉求："不能联网时，查历史持久密钥、时效内即允许使用"

### 遗留 / 后手

| 项 | 说明 | 计划 |
| --- | --- | --- |
| 纯客户端校验可被逆向 | 所有此类方案的共同宿命；发行包只提高成本 | 如需更强，须把核心逻辑上云（架构级） |
| 管理接口明文 HTTP | 默认只监听 127.0.0.1；公网需前置 TLS | 部署文档已明示 |
| PSK 为共享密钥 | 一群客户端共用一个 PSK；泄露可自造客户端帧（但伪造不了服务端票据） | 可按客户群分 PSK |
