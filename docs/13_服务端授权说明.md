# 13 · 服务端授权机制说明（v1.8.0）

> 本文档面向**部署者、管理员与后续维护者**，回答四个问题：
> ① 这套授权怎么装、怎么用？② 密钥算法到底怎么保护的？
> ③ 它真实的安全强度在哪、**哪里挡不住**？④ 改了协议要注意什么？
>
> **第三点是本文档存在的首要理由。我们不夸大安全性。**
> 请先读第七节"诚实评估"，再决定是否把它当作唯一的防护手段。

---

## 一、为什么需要服务端授权

v1.7.0 及之前的版本带的是**本地开发者密钥**（见 `12_密钥与防破解说明.md`）：
校验完全在客户端做，密钥哈希写死在二进制里。它的作用只是"拦住手滑误操作"，
**拦不住任何有意绕过的人** —— 把绕过判断的跳转指令改掉即可。

v1.8.0 新增的 `aim` 模块解决的是另一类问题：**授权需要由你自己签发与撤销**。

| 场景 | v1.7.0 本地密钥 | v1.8.0 服务端授权 |
|---|---|---|
| 把软件发给别人用，想控制"谁能用" | ✗ 做不到 | ✓ 一机一码 |
| 授权到期后自动失效 | ✗ 做不到 | ✓ 签发时定天数 |
| 发现被滥用后**远程**收回 | ✗ 做不到 | ✓ 吊销即时生效 |
| 完全断网也要能用 | ✓ 可以 | ✓ 离线降级（见第五节） |

**两者并存、互不干扰**：`aim` 关闭时，程序行为与 v1.7.0 **逐字节一致**。

## 二、三个包分别是什么

交付物分三个包，职责严格分离：

```
┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐
│   源码包         │   │   发行包         │   │  服务器包        │
│  (source)       │   │  (release)      │   │  (server)       │
├─────────────────┤   ├─────────────────┤   ├─────────────────┤
│ 全部 .rs 源码    │   │ 只有可执行文件    │   │ Linux 服务端     │
│ 含 aim 模块      │   │ 无任何 .rs       │   │ 源码 + 部署脚本  │
│ 给维护者/审计    │   │ 给最终用户       │   │ 给管理员         │
│ cargo build 即用 │   │ 混淆 + 加密      │   │ systemd 托管     │
└─────────────────┘   └─────────────────┘   └─────────────────┘
        │                     │                     │
        └────────── 同一份 aim 协议 ────────────────┘
                （线格式契约，见第八节）
```

**发行包绝不包含源码**，并且做了混淆与符号剥离：
- 编译期 `strip = true` 去除全部调试符号（函数名、变量名不可读）
- `panic = "abort"` 减小体积、去掉栈回溯字符串
- 常量字符串（salt、魔数）以字节数组形式散落在 `.rodata`，不集中出现

> **但请注意**：这些措施**只提高逆向成本，不构成"算法不可泄露"的保证**。
> 见第七节。

## 三、快速上手

### 3.1 服务端部署（Linux）

```bash
# ① 解压服务器包
tar -xzf aim-server-1.8.0-linux-x86_64.tar.gz
cd aim-server-1.8.0

# ② 生成配置（自动生成强随机 PSK 与管理口令）
./aim-server --gen-config server.json
# 输出示例：
#   PSK        = k7F2...（48 字符随机）
#   管理口令    = a9X3...（32 字符随机）
#   ⚠ 请立即抄录保存，此文件是唯一凭据来源

# ③ 启动
./aim-server --config server.json
# 授权服务已启动，监听 http://0.0.0.0:8766
# PSK 指纹前缀：0ee2bc3f（客户端须配置同一 PSK）
```

安装为 systemd 服务（开机自启、崩溃自拉）：

```bash
sudo ./deploy/install.sh          # 交互式：询问端口、数据目录、是否启用管理接口
systemctl status aim-server       # 查看状态
journalctl -u aim-server -f       # 实时日志
```

### 3.2 签发密钥

```bash
# 签发一把持久密钥（绑定机器指纹，365 天）
curl -X POST http://127.0.0.1:8766/v1/admin/issue \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"kind":"persistent","hwid":"<机器指纹>","days":365,"note":"初一(3)班"}'
# 返回：{"key":"THZX-P-81841175589886186B835EEF", ...}
# ⚠ 明文密钥只返回这一次，服务端不存明文，请立即抄录

# 签发一把临时密钥（24 小时、限 3 次激活，不绑定机器）
curl -X POST http://127.0.0.1:8766/v1/admin/issue \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"kind":"temporary","days":1,"max_uses":3,"note":"裁判笔记本"}'

# 查看全部密钥
curl http://127.0.0.1:8766/v1/admin/keys -H "X-Admin-Token: $ADMIN_TOKEN"

# 吊销
curl -X POST http://127.0.0.1:8766/v1/admin/revoke \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"prefix":"THZX-P-8184"}'

# 续期
curl -X POST http://127.0.0.1:8766/v1/admin/renew \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"key":"THZX-P-...","days":365}'
```

### 3.3 客户端配置

先取本机机器指纹（发给管理员，用于绑定）：

```bash
sports-meet --hwid
# 机器指纹：7f3a91c2...
# （脱敏展示，完整值见 data/.hwid）
```

然后配置授权服务地址与 PSK（写在 `config.json`）：

```json
{
  "license_server": {
    "host": "授权服务器IP或域名",
    "port": 8766,
    "psk": "与服务端 server.json 中的 PSK 完全一致"
  },
  "aim_enforce": true
}
```

启动后程序会自动尝试联网激活，首次成功即写入本地加密缓存，之后断网也能用。

## 四、密钥与指纹算法

### 4.1 机器指纹（HWID）

指纹由**三项硬件特征**组合而成，顺序固定：

```
fingerprint = "board=<主板UUID>|disk=<磁盘序列号>|cpu=<CPU标识>"
```

| 特征 | 采集方式（Linux / Windows） |
|---|---|
| 主板 UUID | `/sys/class/dmi/id/product_uuid` / `wmic csproduct get uuid` |
| 磁盘序列号 | `/sys/block/*/device/serial` / `wmic diskdrive get serialnumber` |
| CPU 标识 | `/proc/cpuinfo` 的 `model name`+`vendor_id` / `wmic cpu get processorid` |

**为什么不用 MAC 地址**：网卡是最容易被更换、也最容易在虚拟机里伪造的部件。
MAC 地址**参与采集但不参与指纹计算** —— 它只作为容错时的辅助提示。

**容错设计**：任一特征缺失（虚拟机、精简系统）时填 `<absent>` 而非报错，
指纹仍然可用（只是区分度下降）。程序启动横幅会提示"降级"状态。

### 4.2 密钥哈希

服务端**从不保存密钥明文**，只保存它的慢哈希：

```
key_hash = FNV1a64_slow(key, rounds=200_000)
```

慢哈希的构造（`store::slow_hash`）：

```
h₀ = FNV1a64(offset_basis, key)
hᵢ = FNV1a64(FNV1a64(FNV1a64(hᵢ₋₁, salt), i_le), key)     for i in 0..rounds
```

特点：**盐与轮序号都参与运算**，所以"预计算彩虹表"必须针对每个轮序号
单独建表，成本被拉平到与暴力破解相近。200,000 轮在一般 CPU 上约 30 ms ——
正常校验感觉不到，但离线爆破每个候选密钥都要付这 30 ms。

> **诚实说明**：FNV 不是密码学哈希（非抗碰撞），自实现的 KDF 也**不如
> Argon2/scrypt** 那样有内存硬化。这里选它是为了"零额外依赖 + 跨端一致"。
> 真正的防线是**密钥的随机性**（24 位十六进制 ≈ 96 bit），而不是这个 KDF。
> 见第七节。

### 4.3 密钥格式

```
THZX-P-81841175589886186B835EEF
     │  └── 24 位随机十六进制（96 bit 熵）
     └── P = persistent（持久） / T = temporary（临时）
```

前缀的两个作用：**人眼可辨类型**（避免临时密钥被当持久密钥用）、
**便于管理员按前缀吊销**（`{"prefix":"THZX-P-8184"}`）。

## 五、加密信道与离线降级

### 5.1 为什么不能直接发 HTTPS

用户的原始要求是"发送至服务端时需要用加密协议传输"。可以选 TLS，
但那会引入一整个 TLS 依赖树（`rustls`/`openssl` + 证书管理），
与项目"最小依赖"原则冲突，且自签证书在客户现场部署门槛很高。

因此实现了**自有的加密信道**：不替代 TLS 的通用性，但**针对本场景足够** ——
它保护的是"密钥明文 + 机器指纹"在最后一跳不被抓包。

### 5.2 帧格式

每一条请求/应答都是一帧，布局如下（**网络字节序**）：

```
┌───────┬─────┬────────┬─────────┬───────────┬────────┬───────────┬─────────┐
│ MAGIC │ VER │  SEQ   │ TS(ms)  │ NONCE_LEN │ NONCE  │  C_LEN    │ CIPHER  │ MAC  │
│ 4字节 │ 1字节│ 8字节  │ 8字节   │  1字节    │ n字节  │  4字节    │ m字节   │16字节│
│"SMAF" │  1  │ 递增   │ 时间戳  │           │随机数  │           │ 密文    │ 校验 │
└───────┴─────┴────────┴─────────┴───────────┴────────┴───────────┴─────────┘
```

### 5.3 加密

密文 = 明文 XOR 密钥流，密钥流由**块号参与运算**的伪随机序列生成：

```
keystream(key, block) = FNV1a64(FNV1a64(offset_basis, key), block.to_le_bytes())
```

**块号参与运算是关键** —— 否则相同明文段会产生相同密文段（ECB 式泄露）。
整个包再算一个 16 字节 MAC，覆盖 `SEQ ‖ CIPHER`（**MAC 先于解密校验**）。

### 5.4 会话密钥双端派生

```
初始密钥：  k₀ = H("aim::session::v1",      psk ‖ nonce_c)
升级密钥：  k₁ = H("aim::session::pair::v1", nonce_c ‖ nonce_s ‖ k₀)
```

服务端在应答里回带自己的随机数 `nonce_s`，客户端据此把密钥从
`H(psk‖nonce_c)` 提升为 `H(psk‖nonce_c‖nonce_s)`。**这样即使客户端随机数
被预测（弱随机源），服务端随机数仍能保障会话密钥不可预测。**

### 5.5 防重放（三重检查）

| 检查 | 规则 | 拦住什么 |
|---|---|---|
| 序号单调 | `SEQ` 必须严格大于已见最大值 | 重发旧帧 |
| 时间窗 | `|now - TS| ≤ 300s` | 延迟重放 |
| nonce 去重 | 最近 4096 个 nonce 不得重复 | 序号重置后的重放 |

三项**全部通过**才接受，任一失败即拒绝。

### 5.6 离线降级（核心需求）

用户明确要求："如果不能联网，转为离线模式，查看以前是否使用过持久性密钥，
如果时效期还在，那就允许使用。"

`client::offline_decision()` 的判定顺序：

```
① 本地有持久密钥缓存 → 检查 expire_at → 未过期则放行（LicenseKind::Persistent）
② 否则看临时密钥缓存 → 未过期则放行（LicenseKind::Temporary）
③ 有记录但都已过期 → 拒绝，并**如实告知**"授权已于 X 到期"
④ 从没有过记录   → 拒绝（AuthState::OfflineNoCache）
```

**持久密钥优先于临时密钥** —— 即使临时密钥还剩 2 小时，只要持久密钥有效就用持久的。

本地缓存在 `data/.license`，**加密落盘**（魔数 `SMAL`），
密钥由机器指纹派生（换台机器复制缓存文件也用不了）。

## 六、数据结构与存储

### 6.1 服务端密钥库 `keys.json`

```json
{
  "version": 1,
  "saved_at": 1794575081,
  "keys": [
    {
      "key_hash": "a1b2c3...",       ← 慢哈希（无明文）
      "key_prefix": "THZX-P-8",       ← 前 8 位（人工核对）
      "kind": "persistent",
      "hwid": "7f3a91c2...",          ← 空 = 不绑定机器
      "issued_at": 1794575081,
      "expire_at": 1826111081,        ← 0 = 永不过期（仅持久密钥）
      "max_uses": 0,                  ← 0 = 不限次
      "used_count": 3,
      "note": "初一(3)班",
      "revoked": false
    }
  ]
}
```

**落盘是原子的**：临时文件 → `fsync` → `rename`，断电不会写坏密钥库。

### 6.2 客户端缓存 `data/.license`

```
SMAL ‖ 版本 ‖ 加密的 JSON{ kind, expire_at, ticket, hwid_hash, activated_at }
```

缓存内容与机器指纹绑定，拷贝到别的机器无法解密。

### 6.3 审计日志

服务端所有管理操作与授权请求都追加写入 `audit/aim-YYYYMMDD.log`：

```
[2026-10-14 13:05 UTC] [ADMIN] 签发 persistent：THZX-P-8…（绑定 指定机器，365 天）
[2026-10-14 13:05 UTC] POST /v1/admin/issue -> 200 (127.0.0.1)
[2026-10-14 13:06 UTC] [DENY] 请求解密失败：MAC 不符（203.0.113.7）
```

## 七、诚实评估：这套机制挡得住什么、挡不住什么

> **这一节最重要。我们不打折扣地写出来。**

### ✅ 真实有效的部分

1. **一机一码**。密钥绑定硬件指纹，把授权目录整个复制到另一台机器**没用**。
   这是最实在的一条防线，且已由 `e2e_machine_binding_enforced` 测试验证。
2. **远程吊销即时生效**。每台机器联网校验时都会查到最新吊销状态。
3. **密钥明文不回传**。服务端存的是哈希，应答里也不含密钥明文 ——
   即使服务端数据文件泄露，攻击者拿不到可用密钥。已由 e2e 断言。
4. **传输层防篡改**。改一个字节、重放一次都会被拒。已由 `wire.rs` 验证。
5. **离线可用**。断网不影响正常使用（在有效期内）。

### ⚠️ 挡不住的部分（请务必知悉）

1. **客户端可被逆向**。发行包做了混淆与符号剥离，但 Rust 程序的字符串常量
   与"比较结果"的跳转是**可以被定位的**。有足够耐心的人（IDA/Ghidra + 时间）
   能让客户端"永远返回已授权"。
   > **这是所有纯客户端校验的共同宿命，不是本实现的缺陷。**
   > 真正的强保护需要把**核心业务逻辑**也搬到服务端，那是架构级改造，超出本次范围。

2. **FNV 不是密码学哈希**。若攻击者拿到服务端 `keys.json`，可以用它离线验证
   猜测；虽然 200,000 轮慢哈希拖慢了速度，但比 Argon2 弱。不过 ——
   前提是他**先**拿到文件，而密钥熵是 96 bit，穷举不现实。

3. **PSK 是共享密钥**。所有客户端用同一个 PSK 派生会话密钥。PSK 一旦泄露，
   攻击者可以自造客户端帧（但**仍无法伪造服务端票据** —— 票据由服务端 PSK 签名）。
   因此 PSK 必须强随机，且不同客户群建议用不同 PSK。

4. **DNS/中间人**。信道加密防的是"抓包看到内容"，但**不防中间人替换服务端**：
   攻击者可以架一个假服务端返回"已授权"。要防这个只能上 TLS + 证书固定。
   本场景（校园内网）风险可接受。

5. **管理接口是明文 HTTP**。`/v1/admin/*` 走明文 + 口令。生产环境**必须**
   只监听内网/127.0.0.1，或用 Nginx 加 TLS 反代。默认不启用管理接口。

### 一句话结论

> **这套机制足以拦住"普通用户复制软件分发"与"授权到期不续费"，
> 但拦不住有耐心的逆向工程师。** 把它当作"提高滥用成本"的商业授权手段，
> 而不是"绝对防盗版"的技术保障。

## 八、维护者须知：改动协议的红线

### 8.1 两份 `channel.rs` 是同一份代码

客户端与服务端**各自持有一份 `channel.rs` 副本**（编译期互不可见）。
改动任一份后：

```bash
# 1. 以客户端为准，同步到服务端（唯一真源）
cp sports-meet/src/core/aim/channel.rs aim-server/src/aim/channel.rs

# 2. 跑两端测试
(cd sports-meet && cargo test)
(cd aim-server  && cargo test)

# 3. 跑双端契约测试（关键！）
(cd sports-meet && cargo test --test wire --test e2e)
```

### 8.2 三条跨端契约（改一处必须两端同步）

| 契约 | 位置（两端各一份） | 改了会怎样 |
|---|---|---|
| **派生盐** | `channel.rs` 的 `"aim::session::v1"` / `"pair::v1"` | 双端派生同一把密钥失败 → MAC 不符 |
| **密钥哈希盐/轮数** | 客户端 `license::slow_hash` / 服务端 `store::slow_hash` | 服务端算不出客户端密钥的哈希 → 永远"密钥不存在" |
| **帧布局** | `channel.rs` 的 `seal`/`open` | 客户端解不开应答 |

`tests/wire.rs` 会**直接读磁盘上服务端的源码文件**来比对这三条契约，
所以分叉在 CI 就会被抓到，不会等到客户现场才发现。

### 8.3 已知设计取舍

- **nonce 不参与 MAC 覆盖**（它必须在派生密钥后才能校验）。
  这是刻意的：nonce 一旦被改，MAC 自然不符。`channel.rs` 里有测试
  `nonce_tampering_breaks_open` 固化这个契约。
- **格式检查长度 <4 的特征按缺失处理**（`<absent>`）。
  由 `short_features_fall_back_to_absent` 测试固化。

## 九、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 客户端报"请求解密失败" | 两端 PSK 不一致 | 对比启动横幅里的"PSK 指纹前缀"，应相同 |
| 客户端一直"无法连接授权服务" | 地址/端口错，或防火墙 | `curl http://<host>:8766/v1/health` |
| "密钥不存在" | 密钥抄错，或服务端 `rounds` 与签发时不同 | 重新核对密钥；确认未改 `--kdf-rounds` |
| "与本机指纹不匹配" | 密钥绑定的是别的机器 | 用本机 `--hwid` 的指纹重新签发 |
| "授权已被吊销" | 管理员吊销了 | 正常，需重新签发 |
| 断网后无法使用 | 本地无有效缓存 | 至少联网激活过一次即可离线 |
| 管理接口 401 | 口令错 | 核对 `X-Admin-Token` 与启动时的 `--admin-token` |
