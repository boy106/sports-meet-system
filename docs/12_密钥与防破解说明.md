# 12 · 密钥机制与防破解说明（v1.5.1）

> **v1.6.0 说明**：本版为**接口机制增强 + 前端重构**，与密钥/加密机制**互不影响**。
> 三重条件准入、数据加密封闭环、静默降级、审计留痕等行为**与 v1.5.1 完全一致**。
> 两处需要留意的新增交互（**均不削弱安全边界**）：
> 1. **敏感档限流**：`/api/auth/token`、`/api/dev/*` 归入 `Sensitive` 档，
>    10 秒内本机上限 30 次。这**不改变**鉴权逻辑，只是给暴力猜口令加了速率上限——
>    与既有的"错误密钥静默降级"形成互补（前者拖慢枚举，后者不泄露信息）。
> 2. **统一信封携带错误码**：口令错误返回 `E_AUTH`、二次确认缺失返回 `E_CONFIRM`。
>    需注意 `E_AUTH` 的语义与 v1.5.1 的"静默降级"一致——**仍不给具体原因**
>    （不区分"口令错"与"令牌过期"），以防被用于枚举。
>
> 另：v1.5.2 语音输入同样与密钥机制无关（详见本节历史说明）。

> **v1.5.2 说明**（历史）：本版新增**语音输入**（浏览器 Web Speech API），与密钥/加密机制**互不影响**。
> 语音能力**完全在浏览器侧**，不经过后端密钥路径、不改动任何鉴权与加密逻辑，
> 因此本文档描述的三重条件、数据加密封闭环、静默降级等行为**与 v1.5.1 完全一致**。
> 唯一相关改动是 `api.rs` 中查询参数的空串归一化（踩坑 #37），属独立缺陷修复。

> 本文档面向**部署者**与**后续维护者**，回答三个问题：
> ① 密钥怎么用？② 开发者模式会改变什么？③ 这些措施的**真实强度**在哪、
> 局限在哪？——第三点是本文档存在的首要理由。**我们不夸大安全性。**

## 一、一句话总览

v1.5.1 新增三层与"密钥"相关的能力：

| 能力 | 开关 | 默认 | 作用 |
|---|---|---|---|
| **开发者模式** | `--devkey <密钥>` + `--i-know-the-risk` | 关闭 | 调试时跳过危险操作的二次确认 |
| **数据加密** | `--encrypt-data` | **关闭** | 数据文件落盘为密文（`.smev`） |
| **资源内嵌** | 无需开关 | 已启用 | 前端页面编入 exe，安装目录无 html 明文 |

三者共用**同一把** `--devkey` 派生（密钥校验通过才启用其余两者）。

## 二、快速上手

### 2.1 启用开发者模式

```bash
# Linux / macOS
./sports-meet --devkey THZX-2026-DEV --i-know-the-risk

# Windows
sports-meet.exe --devkey THZX-2026-DEV --i-know-the-risk
```

启动后应看到**红色横幅**：

```
[开发者模式可用] 密钥校验通过，已具备解锁能力（需在诊断页签手动解锁）。
  注意：解锁后将跳过危险操作二次确认，所有动作写入审计（actor=devmode）。
  请勿在面向学生的生产环境中解锁。
```

注意此时**仍是锁定态**。需进入「诊断」页签 → 点击「解锁开发者模式」
（会弹出风险确认框），解锁才真正生效。

### 2.2 启用数据加密

```bash
./sports-meet --devkey THZX-2026-DEV --i-know-the-risk --encrypt-data
```

数据文件变为 `data/sports_meet.json.smev`，且**同名明文会被自动删除**。
未带正确密钥启动时，读到的会是**空库**（并输出 ERROR 日志），
不会静默给出错误数据。

### 2.3 更换密钥（重要）

源码里只存**指纹**，不存明文。更换步骤：

```bash
# 1) 计算新密钥的指纹
./sports-meet --devkey-fingerprint "我的新密钥"
# 输出：密钥指纹：a1b2c3d4e5f60718（KDF_ROUNDS=200000）

# 2) 编辑 src/core/license.rs，替换 LICENSE_FINGERPRINT 常量
# 3) 重新编译
cargo build --release
```

> **务必**在交付前把默认演示密钥换掉。`THZX-2026-DEV` 是公开的，
> 任何人照抄本文档就能解锁开发者模式。

### 2.4 旧密钥加密的数据怎么办

数据加密的密钥来自 `--devkey`。**换密钥后，旧密文无法解密**。
若已有加密数据，换密钥前必须先导出：

```bash
# 用旧密钥启动，导出全量 JSON（明文）
./sports-meet --devkey <旧密钥> --i-know-the-risk --encrypt-data
# 网页 → 系统设置 → 导出全量数据（JSON）
# 然后换密钥重新编译，再用新密钥启动并「从 JSON 恢复」
```

## 三、开发者模式到底改了什么

### 3.1 会改变的行为（**仅此两项**）

| 路径 | 平时 | 解锁后 |
|---|---|---|
| `DELETE /api/events/{id}` | 需 `X-Confirm-Password`（否则 **428**）+ 需 `?confirm=1` | **两层都跳过** |
| `DELETE /api/students/{id}` | 同上 | **两层都跳过** |
| `POST /api/results/clear` | 需 `X-Confirm-Password`（否则 428） | 跳过口令确认 |
| `POST /api/import/json` | 需 `X-Confirm-Password`（否则 428） | 跳过口令确认 |

### 3.2 **不会**改变的行为（逐条列出，避免误解）

- ❌ 口令鉴权本身（写接口仍要 `Authorization`）
- ❌ 签名令牌的有效期与校验
- ❌ CSRF 缓解（POST 仍必须 `Content-Type: application/json`）
- ❌ 静态文件路径穿越防护
- ❌ 请求体 / 请求头大小上限
- ❌ 扩展路由前缀校验
- ❌ 任何读取接口的行为

**换句话说：解锁只是"少输一次口令"，不是"关掉登录"。**

### 3.3 解锁的代价：审计留痕

解锁后每一次越界动作都会写入**哈希链审计**，`actor` 标记为 `devmode`：

```json
{"seq":3,"time":"2026-09-25 23:16:31","actor":"devmode",
 "action":"dev_bypass_confirm",
 "detail":"开发者模式跳过删除预检：项目 #1",
 "prev":"d66e5409742c64d8","hash":"a739001c9bb56092"}
```

诊断页签底部有专门区块列出全部 `actor=devmode` 记录。
**便利是用可追溯换来的** —— 这是本设计的核心权衡。

## 四、三重条件：为什么"知道密钥"还不够

解锁需要**同时**满足：

| 条件 | 含义 | 由谁保证 | 能否被伪造 |
|---|---|---|---|
| ① 密钥匹配 | 持有 `--devkey` 明文 | `license.rs`（20 万轮慢哈希） | 需知明文 |
| ② 本机来源 | TCP 对端是 `127/8`、`::1` 或 IPv4-mapped 回环 | `http.rs::is_loopback` | **不能** |
| ③ 风险确认 | 启动时带 `--i-know-the-risk` | `main.rs` | 需改启动命令 |

**条件 ② 是关键**：它把"知道密钥"与"坐在机器前"绑定在一起。
即使密钥泄漏到聊天记录里，远端也无法解锁。

**判定来源时只认 TCP 对端地址**：`X-Forwarded-For` / `X-Real-IP`
之类的请求头**一概不看**，因为它们可由客户端任意伪造。

诊断页签会**逐条显示**三个条件的满足状态，卡在哪一条一目了然。

## 五、密钥的存储与比对

### 5.1 只存指纹，明文用完即弃

```rust
// src/core/license.rs
pub const LICENSE_FINGERPRINT: &str = "35d041df2b141b66";  // 仅哈希值
```

密钥从命令行进入 → 立即求 `slow_hash` → 与常量做**常量时间比较**
→ 明文随即 `drop`。**源码、日志、审计、接口响应中均不出现明文密钥。**

### 5.2 慢哈希：给爆破加一道计算税

```
hash = FNV1a(hash ‖ 盐 ‖ 轮序号 ‖ 输入)，迭代 200,000 轮
```

- 实测约 **30 ms/次**（`-O` 构建），使用者几乎无感；
- 每轮都依赖上一轮**全部输出**，无法预计算中间表；
- 轮序号参与运算，打散轮次间的结构相似性。

### 5.3 常量时间比较

```rust
fn const_time_eq(a: &str, b: &str) -> bool {
    if a.len() != b.len() { return false; }
    a.bytes().zip(b.bytes()).fold(0u8, |acc, (x, y)| acc | (x ^ y)) == 0
}
```

避免"逐字节比较、遇差异提前返回"导致的时间侧信道。

### 5.4 状态接口绝不泄漏敏感信息

`GET /api/dev/status` 只返回布尔量与**指纹前 4 位**：

```json
{"key_present":true,"risk_acked":true,"can_unlock":true,
 "dev_mode":"locked","fingerprint_prefix":"35d0","kdf_rounds":200000,
 "from_loopback":true,"encrypt_data":false,
 "seed_fingerprint":"482ce20432d43d9c"}
```

指纹前 4 位用于运维核对"装的是不是同一把密钥"，**不足以反推明文**。
明文密钥与完整种子已被单元测试
（`status_fields_never_leak_secret`）断言绝不出现。

## 六、数据加密的**真实强度**（必读）

### 6.1 它做什么

| 项目 | 实现 |
|---|---|
| 密钥派生 | `--devkey` 明文 → 慢哈希 → 16 位十六进制种子 → 64 bit |
| 流密码 | 以 64 bit 块号为输入反复调用 FNV-1a 生成伪随机流（类 CTR 结构） |
| 完整性 | 每 4 KiB 明文块后追加 8 字节 MAC `FNV1a(seed ‖ 块号 ‖ 密文)` |
| 文件头 | `SMEV` 魔数 + 版本(1) + 模式(1) + 种子指纹(8) |
| 落盘 | 临时文件 → `fsync` → `rename`（原子替换） |

### 6.2 它**不能**做什么（诚实声明）

> **这不是密码学意义上的强加密。**
>
> FNV-1a 是**非密码学哈希**，不具备抗碰撞性与伪随机性证明。
> 本模块的设计目标是**提高"拷走数据文件后的可用性门槛"**：
>
> - ✅ 挡住"用记事本打开"—— 打开是乱码
> - ✅ 挡住"用 Excel 导入 CSV"—— 格式不符
> - ✅ 挡住"全文搜索学生姓名"—— 密文中搜不到
> - ✅ 检出任何字节级篡改（逐块 MAC）
> - ❌ **挡不住**有针对性的密码分析
> - ❌ **挡不住**拿到 `--devkey` 的人
> - ❌ **挡不住**反编译后提取 `LICENSE_FINGERPRINT` 做离线爆破

**数据确属敏感时，请叠加操作系统级磁盘加密**
（Windows BitLocker / Linux LUKS / macOS FileVault）—— 那才是真正的边界。
本模块是**纵深防御中的一层，不是唯一防线**。

### 6.3 为什么不用成熟密码库

项目坚持「最小依赖」（规则 10）：全部功能自实现，唯一例外是
`rust_xlsxwriter`（xlsx 二进制格式实现成本过高）。

**这是个有代价的取舍，值得说清楚：**

| 方案 | 强度 | 依赖 | 本项目选择 |
|---|---|---|---|
| 自实现 FNV 流加密 | 弱 | 0 | ✅ v1.5.1 采用 |
| `aes-gcm` | 强 | +3~5 crate | ❌ |
| `chacha20poly1305` | 强 | +2~3 crate | ❌ |

若部署环境对数据机密性有**实际要求**（而非"防顺手翻看"），
建议自行引入 `chacha20poly1305` 替换 `vault.rs` —— 接口已按
`seal(seed, plain) -> Vec<u8>` / `open(seed, sealed) -> Result<Vec<u8>>`
收窄，替换成本很低。

### 6.4 完整性校验的强度

8 字节 MAC 意味着**随机篡改的检出率约 1 - 2⁻⁶⁴**，
但**非随机**篡改（了解算法的人精心构造）可能绕过。
它防的是"磁盘位翻转"与"随手改一个字节"，不是主动攻击。

## 七、防破解措施清单

| 措施 | 实现方式 | 有效阻挡 | 挡不住 |
|---|---|---|---|
| 密钥只存哈希 | 20 万轮慢哈希 + 常量时间比较 | 源码泄漏明文密钥 | 离线爆破指纹常量 |
| 错误密钥静默降级 | 无任何反馈提示 | 在线试错爆破 | 离线逐位逼近 |
| 本机来源限制 | TCP 对端地址（不看请求头） | 远程解锁 | 已控制本机者 |
| 资源内嵌 | `include_str!` 编入 exe | 直接改 html 改界面 | 反编译后改二进制 |
| 数据文件加密 | 流加密 + 逐块 MAC | 直接读数据文件 | 拿到密钥 / 反编译 |
| 哈希链审计 | FNV-1a + `prev_hash` 链式绑定 | 事后篡改审计记录 | 整份替换 + 重算 |
| 原子落盘 | 临时文件 + `fsync` + `rename` | 断电产生半个密文 | 磁盘物理损坏 |

### 7.1 可选：UPX 加壳

> **默认不启用**。加壳会显著增加杀毒软件误报率，校园环境下
> 可能被安全软件拦截，反而影响可用性。**仅在前述措施不足时考虑。**

```bash
# 1) 安装 UPX（各发行版不同）
sudo apt install upx-ucl     # Debian/Ubuntu
brew install upx             # macOS

# 2) 压缩（Linux）
upx --best --lzma target/release/sports-meet

# 3) Windows 交叉编译产物
upx --best --lzma target/x86_64-pc-windows-gnu/release/sports-meet.exe
```

**加壳的利与弊：**

| 利 | 弊 |
|---|---|
| 二进制体积减小 50~70% | 杀毒误报率显著上升 |
| 静态字符串（含指纹常量）被压缩，`strings` 不易直接读出 | 启动稍慢 |
| 普通反编译工具直接失效 | UPX 本身有成熟脱壳工具，**不构成实质保护** |

**结论**：UPX 主要价值是**减小体积**与**干扰随手 `strings`**，
不是安全措施。若只为"改一个字节就能改行为"，真正该做的是
**签名校验**（本项目未实现）。

### 7.2 建议的生产环境配置

```bash
# 面向学生的生产环境：不开开发者模式、不开数据加密
./sports-meet --password <强口令> --log-level WARN

# 仅在本机调试时：
./sports-meet --password <强口令> --devkey <密钥> --i-know-the-risk

# 数据确需加密时（且已接受第六章声明的强度局限）：
./sports-meet --password <强口令> --devkey <密钥> --i-know-the-risk --encrypt-data
```

## 八、风险清单（自行评估）

| # | 风险 | 影响 | 缓解措施 | 残留风险 |
|---|---|---|---|---|
| R1 | 默认演示密钥公开 | 任何人可解锁 | **交付前必须更换**（§2.3） | 若忘记更换则完全失效 |
| R2 | 指纹常量在二进制中 | 可离线爆破 | 20 万轮慢哈希 | 弱密钥可被秒破，**须用强密钥** |
| R3 | 自实现加密强度有限 | 数据可被分析 | 叠加磁盘加密 | 无法完全消除 |
| R4 | 解锁后免二次确认 | 误删风险 | 审计留痕 + 需本机 + 手动确认框 | 误操作仍可能发生 |
| R5 | 资源内嵌可被反编译提取 | 界面可被改 | 无实质措施 | 可接受（界面非机密） |
| R6 | 审计文件可被整体替换 | 追溯失效 | 哈希链自洽性校验 | 能检出**改动**，不能阻止**替换** |
| R7 | 密钥在命令行历史中残留 | 泄漏给本机其他用户 | 无自动清理 | 建议用 shell 变量或包装脚本 |

### R7 的具体建议

```bash
# 不推荐：密钥进入 shell 历史
./sports-meet --devkey secret --i-know-the-risk

# 推荐：先入变量，并在历史中隐藏
export SM_DEVKEY="$(cat ~/.sports-meet-devkey)"
./sports-meet --devkey "$SM_DEVKEY" --i-know-the-risk
unset SM_DEVKEY
```

## 九、验收自测清单

部署后建议按此清单逐条验证（全部为**只读**操作）：

```bash
# 1) 未带密钥：应显示 locked，且不含敏感字段
curl -s http://127.0.0.1:8765/api/dev/status | python3 -m json.tool
#    期望：key_present=false, dev_mode=locked，无明文密钥/完整种子

# 2) 带错误密钥：应与"未带密钥"表现完全一致（无任何错误提示）
#    这是特性，不是 bug —— 无反馈信道才能抗爆破

# 3) 带正确密钥但不加 --i-know-the-risk：应 can_unlock=false

# 4) 三重条件齐备：can_unlock=true，此时仍未解锁（需手动点按钮）

# 5) 远端访问（用另一台机器 curl 本机 IP）：from_loopback 应为 false

# 6) 加密模式：确认 data/ 下只有 .smev，无同名明文残留
ls -la data/
```
