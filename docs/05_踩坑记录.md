## 1. `model::Result` 遮蔽 `std::result::Result`（最坑）
- **现象**：全文件报 `struct takes 0 generic arguments but 2 were supplied`。
- **原因**：`use crate::core::model::*` 把领域结构 `Result`（成绩）带入
  作用域，遮蔽了标准库 `Result`。
- **解法**：显式导入 `use crate::core::model::{Result as DomainResult, ...}`，
  构造与类型标注处全部改用 `DomainResult`。
- **教训**：与 std 常用类型同名的领域模型，禁止 glob 导入。

## 2. 链式 `Json::set()` 返回 `&mut Self`
- **现象**：`Json::obj().set(...)` 直接当 `Json` 值传参 → E0308。
- **解法**：链式后必须 `.clone()`，或先 `let mut o = Json::obj(); o.set(..);`。

## 3. `?` 与闭包返回类型不匹配
- **现象**：`self.read(|d| { ...?... o })` 报「closure should return Result」。
- **解法**：凡闭包体内使用 `?`，闭包需标注 `-> Result<T, ApiErr>` 且
  结尾 `Ok(...)`；外层调用点相应加 `Ok(...?)` 包裹。

## 4. `MutexGuard` 上直接调 `&self` 方法与借用冲突
- **现象**：持有 `d = data.lock()` 的 `&mut Event` 同时再 `&d` 只读借用 → E0502。
- **解法**：进锁后先 `clone()` 需要的数据（如 `grades.clone()`），再做可变操作。

## 5. 本地模块名 `core` 与 `extern crate core` 歧义
- **现象**：`use core::api::Core` 产生歧义（Rust 2018+）。
- **解法**：一律 `use crate::core::...`。

## 6. OSS/网络挂载盘上的工程陷阱
- `cargo` 增量编译目录在 OSS 挂载上损坏 → 必须 `CARGO_INCREMENTAL=0`。
- OSS 上解压上万小文件（mingw 头文件）极慢且常被会话超时打断。
- **教训**：构建产物与工具链放本地盘；只解压必需文件（ld/库/编译器）。
- 会话超时（504）会杀死前台 curl/tar/nohup 子进程 → 长任务拆小步 +
  断点续传（`curl -C -`）。

## 7. 官方源不可用时的镜像方案
- rustup 官方下载极慢：`RUSTUP_DIST_SERVER=https://mirrors.ustc.edu.cn/rust-static`
  + `RUSTUP_UPDATE_ROOT=https://mirrors.ustc.edu.cn/rust-static/rustup`。
- Windows 交叉编译：`rustup target add x86_64-pc-windows-gnu` + 本地解压
  mingw-w64 四件套（binutils/dev/gcc-posix/runtime）+
  `.cargo/config.toml` 指定 `linker = "x86_64-w64-mingw32-gcc-posix"`。
- deb 包可能下载不完整（unexpected EOF），用 `dpkg-deb -c` 校验、curl 重下。

## 8. String 字段与 `&str` 的逐一纠缠
- `get_str().unwrap_or_default()` 返回 `&str`，赋给 String 字段需
  `.to_string()`；为此在 json.rs 增加 `get_string()` 快捷方法统一处理。

## 9. 工具输出层可能显示失真
- 曾把正确的 `sorted[hi]` 显示为 `sortedi]`，折腾数轮。
- **教训**：疑似"改不掉"的字符问题时，用 `od -c` 字节级验证再下结论。

## 10. v1.1 新增踩坑
- **环境重置**：两天后容器工具链消失（rustup/mingw 全没了）→ 写 `scripts/setup_build_env.sh`
  一键恢复（镜像源），mingw deb 永久留存于 tmp/mingw。
- **元组返回全局替换误伤**：把 parse_score_import 改成返回 `(Vec,Vec<String>)` 时，
  连带把 parse_student_import 的返回类型也改了（两处 `Ok(Vec::new())` 同文本）。
  **教训**：对多函数共有的相同代码文本做 replace，必须带函数级上下文。
- **字段名假设**：event_registrations 的 entry 键是 `student_id` 不是 `id`，
  姓名映射前必须先 rg 实际 JSON 字段。
- **.cargo/config.toml 被打包清理误删** → 交叉编译报 `linker not found`；
  linker 配置属于构建基础设施，打包前应保留或写进 README。
- **release 测试很慢**（cargo test --release 全量重编依赖）——功能验证用
  debug 测试即可，release 只需 `cargo build --release` 端到端冒烟。

# v1.2 迭代新增（第 11-18 条）

## 11. crates.io 直连被阻断（构建前置阻塞）

- **现象**：`cargo build` 报
  `failed to load source for dependency rust_xlsxwriter` →
  `SSL connect error (unexpected eof while reading)`。
  注意错误是 **SSL 层**而非 DNS，容易误判为"网络正常"。
- **原因**：沙箱/企业网络直连 crates.io 被中间设备重置 TLS 连接。
- **解法**：配置 `~/.cargo/config.toml` 使用稀疏索引镜像：
  ```toml
  [source.crates-io]
  replace-with = "rsproxy-sparse"
  [source.rsproxy-sparse]
  registry = "sparse+https://rsproxy.cn/index/"
  [net]
  git-fetch-with-cli = true
  ```
- **教训**：
  1. 见到 `SSL connect error` 先想"镜像"，别急着怀疑网络不通；
  2. 镜像配置应写入**全局** `~/.cargo/config.toml`（而非项目内），
     便于所有工程复用；
  3. 依赖拉取（`cargo fetch`）与编译应分两步，便于区分是"拉不到"
     还是"编不过"。

## 12. `/api/ext/extensions` 存在两处实现（静默覆盖）

- **现象**：新增的 `extensions_json()`（含健康统计）明明实现了，
  接口返回却**只有 name/description**，新字段全部消失。
  无编译错误、无运行时警告。
- **原因**：核心路由里**早已存在**一个内联的
  `r("GET", "/api/ext/extensions", |c, _| {...})`，
  与新方法**同名路径重复注册**。路由匹配是"先命中先用"，
  旧实现（注册在前）永远胜出。
- **解法**：删掉旧的内联实现，改为调用 `c.extensions_json()`。
- **教训**：
  1. **同名路由重复注册不会报错**，是静默陷阱；
  2. 重构时若新增了"更完整的实现"，必须**全局搜索该路径字符串**
     确认没有旧实现残留；
  3. 建议后续给路由注册加**重复检测**（启动时若发现同 method+path
     重复，打印 WARN）。

## 13. `ExtRoute` 未派生 `Clone` 导致测试无法复用

- **现象**：测试中构造带路由的假扩展时，
  `self.routes.clone()` 报
  `the method clone exists ... but its trait bounds were not satisfied`。
- **原因**：`ExtRoute` 含 `Arc<dyn Fn ...>`，`Arc<T>` 本身可 Clone，
  但结构体**没有 `#[derive(Clone)]`**，所以整体不可 Clone。
- **解法**：给 `ExtRoute` 加 `#[derive(Clone)]`。
- **教训**：含 `Arc<dyn Trait>` 的结构体，只要其余字段可 Clone，
  就应该派生 `Clone`——`Arc` 的存在正是为了廉价共享。
  设计扩展接口时就该预见"测试需要构造并复用路由"。

## 14. `Arc<Core>` 无法直接改字段（测试装置设计问题）

- **现象**：测试里 `core.undo_keep = 3;` 报
  `cannot assign to data in an Arc`。
- **原因**：`Core` 被包在 `Arc` 里，`Arc<T>` 只提供不可变借用
  （除非 `T: Clone` 用 `Arc::get_mut`，或内部可变性）。
- **解法**：构造时先设好再包 Arc：
  ```rust
  let core = {
      let mut c = Core::new(&dir, Path::new("web"));
      c.undo_keep = 3;
      Arc::new(c)
  };
  ```
- **教训**：
  1. 凡是"通过 Arc 共享的配置项"，要么**构造时传入**，
     要么用 `AtomicUsize` 等内部可变性；
  2. 生产代码里 `main.rs` 也是同样模式（先 `mut core` 设值再 `Arc::new`），
     测试应与之保持一致；
  3. 这也说明 `Core::new()` 的签名**迟早要接受配置参数**
     （见目标文档：引入 `CoreConfig`）。

## 15. `unwrap()` 的"看似安全"与真实风险

- **现象**：审查发现 `api.rs` 有 3 类 unwrap：
  - `self.store.data.lock().unwrap()` ×13 —— 可接受
  - `e.get_i64("student_id").unwrap()` —— **有风险**
  - `self.store.db_path.parent().unwrap()` ×3 —— **有风险**
- **原因**：
  - **锁 unwrap**：仅在"锁中毒"（持锁线程 panic）时触发，
    本项目锁内无 panic 路径，可接受；
  - **字段 unwrap**：虽然上一行 `is_some()` 检查过，
    但**两次独立查询之间字段可能变化**，是典型 TOCTOU 味道的脆弱写法；
  - **`parent().unwrap()`**：当 `db_path` 是根路径（如 `--dir /`）时
    返回 `None`，直接 panic。
- **解法**：
  - 字段查询改为 `if let Some(sid) = e.get("student_id").and_then(|v| v.as_i64())`；
  - 路径改用已有的 `self.data_dir()`（内部已 `unwrap_or("data")` 兜底）；
  - 表头列改用 `ok_or_else(|| ApiErr::new("..."))?`。
- **教训**：
  1. "刚判断过所以不会 None" 是最常见的 unwrap 借口，
     正确做法是**用模式匹配把判断与取值合并**；
  2. 凡是从用户输入（JSON 字段、命令行路径）来的值，
     都不该 unwrap；
  3. 锁的 unwrap 可以接受，但应在注释中说明理由。

## 16. 函数签名改动引发的连锁编译错误

- **现象**：把 `parse_score_import` 中 `score_col` 从 `Option<usize>`
  改为 `usize`（消除 unwrap）后，连带报出 3 处类型不匹配：
  `name_col_is_idonly(name_col: usize, ...)` 与实际传入的
  `Option<usize>` 不符。
- **原因**：原代码为"省一次 unwrap"，用 `name_col.unwrap()` 把
  `Option` 提前解包，导致下游辅助函数签名也"跟着"用了 `usize`；
  我改成保留 `Option` 后，下游就炸了。
- **解法**：辅助函数签名同步改为 `Option<usize>`，内部
  `name_col == id_col` 语义等价且更安全。
- **教训**：
  1. **v1.1 的教训 #10「元组返回全局替换误伤」再次以新形式出现**：
     改一处类型，必须用 `cargo build` 立即暴露连锁影响，
     不能"改完一批再编"；
  2. 辅助函数应保持与调用处**相同的类型宽度**（都用 `Option`），
     而不是在下游偷偷 unwrap。

## 17. assert 断言类型写错（测试自身的坑）

- **现象**：新写的 `stats_and_meta_shapes` 测试失败：
  `assertion left == right failed`，但接口返回值肉眼看是对的。
- **原因**：我把 `Json::Bool(true)` 与字符串 `"true"` 比较：
  ```rust
  assert_eq!(s.get_str("ok"), Some("true").or(Some("")));  // 错
  ```
  `ok` 字段是 **Bool** 类型，`get_str()` 拿到的是 `None`。
- **解法**：改用类型正确的断言：
  ```rust
  assert_eq!(s.get("ok").and_then(|v| v.as_bool()), Some(true));
  ```
- **教训**：
  1. 自实现 JSON 有 `Bool`/`Int`/`Num`/`Str` 多种类型，
     **断言前先确认字段类型**，不要凭印象用 `get_str`；
  2. 写测试时若"应该通过却不通过"，先怀疑**测试本身写错**，
     而不是急着改被测代码（这次差点改错方向）。

## 18. 后台进程导致 shell 会话被 SIGTERM

- **现象**：用 `&` 启动服务后执行 `curl`，整条命令返回
  `Signal: SIGTERM`、无任何输出。反复重试均如此。
- **原因**：后台进程与当前 shell 同属一个进程组，
  工具在命令结束时向**进程组**发终止信号，连带杀掉了整个命令链。
- **解法**：用 `setsid` 让服务脱离会话，或把启动与验证**拆成两条命令**：
  ```bash
  # 第一条：只启动
  (setsid ./target/release/sports-meet --port 8802 ... &)
  # 第二条：只验证
  curl -s http://127.0.0.1:8802/api/stats
  ```
- **教训**：
  1. 在自动化环境里做"启动服务 + 立即验证"，**务必让服务脱离会话**；
  2. 一条命令里既启动长驻进程又做断言，是脆弱的写法；
  3. 与其在一条命令里硬凑，不如**拆成两条**，
     可读性与稳定性都更好。

# v1.3 新增（浏览器实测专题）

## 19. 前端 TDZ：const 定义前被引用 → 整个脚本静默中断 ★★★

- **现象**（v1.3 浏览器实测时发现）：点「进入系统」无反应，
  时钟不动、导航点击无效；`typeof el.onclick === "object"`（实际是 null）。
- **原因**：v1.1 起就写成了——
  ```js
  $("se-undo-page").onclick = doUndo;   // ← 先引用
  const doUndo = withBusy(...);          // ← 后定义
  ```
  `const` 有**暂时性死区（TDZ）**，执行到第一行即抛
  `ReferenceError: Cannot access 'doUndo' before initialization`。
  脚本顶层抛错 → **后续所有绑定全部不执行**，但页面上静态
  HTML 仍然渲染，看起来"基本正常"，极具迷惑性。
- **解法**：把绑定移到 `const doUndo` 定义之后。
- **教训**：
  1. **Rust 侧 57 个单测再绿，也覆盖不了前端一行 JS**——
     本次是项目第一次真实浏览器实测，一上来就抓到致命 bug；
  2. `typeof x === "object"` 对 `null` 也成立，排查时别被骗；
  3. 前端顶层代码应**先定义后引用**，或改用 function 声明（有提升）。

## 20. 缺 hashchange 监听：前进/后退键"失灵"

- **现象**：从 `#register` 到 `#results`（仅 hash 变化），页面内容不切换。
- **原因**：浏览器对同文档 hash 导航**不触发 reload**；
  代码只绑定了按钮点击，没有监听 `hashchange`。
  用户点浏览器后退键、手动改 URL、从历史记录进入都会踩中。
- **解法**：`window.addEventListener("hashchange", ...)` + 记录
  `CUR_PAGE` 防止重复刷新。
- **教训**：URL hash 当作路由用时，**hashchange 是路由的另一半**，
  只写 `location.hash = x` 不写监听等于只修了出口没修入口。

## 21. 占位符文案与后端协议不一致（帮助信息反而帮倒忙）

- **现象**：按输入框提示「每行一位学生：年级,班级,姓名,性别」批量导入，
  全部失败：`表头中未找到「姓名」列`。
- **原因**：后端批量导入协议要求**第一行必须是表头**
  （`姓名,学号,年级,班级,性别`），列名智能映射；
  前端占位符描述的是"想象中"的无表头格式，从未与后端核对过。
- **解法**：占位符改为带表头的真实示例。
- **教训**：
  1. **帮助文案是 UI 的一部分，必须按真实协议验证**——
     写完文案用真实数据走一遍；
  2. 错误提示「表头中未找到姓名列」其实已经说清了原因，
     但用户不知道"表头"是什么——错误信息要能映射到用户操作。

# 经验沉淀（跨迭代通用）

## A. 关于"重构"与"优化"的边界

v1.1 曾把「新增多格式导出」算作小版本，v1.2 把「拆分 api.rs」判为重构。
**判定标准**：是否改变模块结构或对外契约。
- 加功能、加校验、加日志、补测试 → **优化**（v1.x）
- 拆文件、改接口签名、换存储后端 → **重构**（v2.0）

## B. 关于"同名/重复"的静默陷阱

本项目两次踩到"重复实现静默覆盖"（v1.1 的全局替换误伤、
v1.2 的重复路由）。**通用对策**：
- 改代码前先 `rg` 目标字符串，确认出现次数与位置；
- 新增"更完整的实现"时，必须同时删除被替代的旧实现；
- 关键注册点（路由、事件订阅）应考虑加**重复检测告警**。

## C. 关于测试的价值排序

优先给**纯函数 + 高风险**的模块写测试：
1. `scoring.rs`（算错无人察觉）→ 最高优先
2. `json.rs`（数据进出通道）
3. 安全函数（路径校验等）
4. 状态机（撤销栈）
5. UI 渲染 → 最低优先（变化快、人工可发现）

> v1.3 修正：第 5 条不等于"UI 不需要测"。
> **单测不覆盖的部分，必须用真实浏览器走一遍主链路**——
> v1.1/v1.2 两轮"57 个单测全绿"的版本，前端带着致命 TDZ bug
> 上线而无人察觉。发布前的浏览器实测（桌面+移动双视口、
> 完整业务链路）应成为固定工序。

## D. 关于"升级 UI 不动逻辑"的改法

v1.3 重写前端时，JS 业务逻辑（API 调用、状态管理）**原样保留**，
只重写 CSS 与 HTML 骨架，并保证**所有控件 id 不变**。
这让 UI 大改的风险集中在"布局/样式"层，业务回归一次通过。
若要改 JS，也只加不改（主题块、hashchange 监听均为纯新增）。

## #22 cargo clippy --fix 会误删"仅测试使用"的导入（v1.4）

`cargo clippy --fix` 按**当前编译单元**分析 unused imports：主代码
（非 test）里 `use crate::core::ext::{CoreContext, ExtRoute}` 与
`use crate::core::store::Data` 看似无引用——但 `#[cfg(test)]` 模块
通过 `use super::*` 间接依赖它们。--fix 一删，`cargo test` 立刻
E0425/E0433 一片红。

**修法**：删掉的导入在测试模块内部显式补回
（`mod tests { use crate::core::ext::{...}; }`）。
**教训**：跑完 `--fix` 必须先 `cargo test` 再提交；测试专用导入
从一开始就该写在测试模块里，不要放主 use。

## #23 递归深度检查点必须放在"容器入口"（v1.4）

JSON 解析器加深度限制时，第一版把检查放在 `parse_value`：
`parse_value(depth)` 遇 `[` 递归到 `parse_array(depth+1)`。但
`[[[...]]]N 层的最内层是**空数组**（`]` 直接闭合），该层从不触发
"元素解析"路径上的 `parse_value`——129 层输入实际只走到
`parse_value(128)`，边界测试 `129 层应报错` 直接失败。

**修法**：检查点移到 `parse_array` / `parse_object` **入口**
（第 depth 层容器进入时即校验），`parse_value` 只传递 depth。
**教训**：递归深度计数器要以"容器层数"为语义，在容器构造点检查；
边界单测（n-1 / n / n+1）必须写，它精准抓住了这个语义偏差。

## #25 SSE 响应体被 TCP 分段截断，测试断言永远失败（v1.5）

**现象**：集成测试读 SSE 流，断言响应里含 `event: snapshot`，
但 `send_request` 只拿到响应头 `HTTP/1.1 200 ... \r\n\r\n` 就返回，
正文一个字都没有。

**排查过程（两层）**：

1. 第一层以为是 chunked 分帧头干扰（`cc\r\n` 把断言文本切开了）——
   写了 `dechunk()` 剥离分帧。**但问题依旧**。
2. 第二层才是真因：用 Python 手工复现测试助手，发现
   **单次 `read(65536)` 只拿到 162 字节（就是响应头）**。
   服务端先 `write_all(head)` + `flush()`，**之后**才写第一帧正文；
   只要 flush 过，内核立刻发包，**不会等待合并成一段**。
   于是正文在**另一个 TCP 段**里，一次 read 读不到。

**修法**：`send_request_raw` 改为**循环读取**——
先确认累积缓冲里出现 `\r\n\r\n`（头结束），再继续读到正文
（上限 256 KiB / 3 秒超时，读到即停）。

```rust
while buf.len() < 256 * 1024 {
    match stream.read(&mut chunk) {
        Ok(0) => break,
        Ok(n) => {
            buf.extend_from_slice(&chunk[..n]);
            // 头已完整且已收到正文 → 收工
            if let Some(pos) = find_subslice(&buf, b"\r\n\r\n") {
                if buf.len() > pos + 4 + 8 { break; }
            }
        }
        Err(_) => break,
    }
}
```

**教训**：
- "一次 read = 一个完整响应"是**错误的心智模型**。TCP 是字节流，
  分段位置取决于内核与 flush 时机，不取决于应用的 write 次数。
- 有 `flush()` 就必然可能拆包；想靠"攒一起再发"来规避是治标。
- 测试助手写错会**掩盖真实 bug**，也会**制造假 bug**——
  同一个根因让我在两层上各花了时间。

## #26 用 HTTP 方法判断"读写"会误伤只读 POST（v1.5，致命）

**现象**：浏览器实测时，在成绩录入页点「解析」**毫无反应**，
连报错都没有。

**排查**：在页面上下文直接 `fetch('/api/smart/parse', {method:'POST'})`
→ 返回 **401**：`需要管理员凭证：请先 POST /api/auth/token 换取令牌`。

**原因**：v1.5 的写鉴权规则是"`method == POST || DELETE` 就要令牌"。
`/api/smart/parse` 是 POST——但它**纯计算、不落盘、不改变任何状态**，
只是让前端"先看一眼解析结果"。相当于给只读能力上了锁。

**后果严重性**：启用口令的学校里，这个功能**对所有人永久不可用**，
而且表现是"点了没反应"，不是报错，极难被发现。

**修法**：加 `readonly_post` 白名单，与 GET 同等对待：

```rust
let readonly_post = matches!(path, "/api/smart/parse");
let needs_auth = is_write && self.core.password.is_some()
    && path != "/api/auth/token" && !readonly_post;
```

同时补 2 个集成测试：`smart_parse_needs_no_auth_even_with_password`
（正面：解析能通 + 对照：真写接口仍是 401）和
`readonly_exception_does_not_weaken_sensitive_confirmation`
（确认例外没开得过宽，敏感操作仍要二次确认）。

**教训**：
- **HTTP 方法 ≠ 是否改变状态**。POST 被大量用于"查询/计算/预览"。
  判断鉴权应基于**语义**，用显式白名单，不要用方法名启发式。
- 例外要配**对照组测试**：只测"例外生效"不够，还要测"别的没被放开"，
  否则下一次扩白名单时会把安全边界越开越大。

## #27 测试夹具的默认值绕过了最常用的代码路径（v1.5，致命）

**现象**：智能推荐接口对**默认预置项目**永远返回
`{"candidates":[], "count":0}`。`smart.rs` 的 26 个单测全绿。

**排查**：插桩打印（注意：集成测试的 `stderr(Stdio::null())`
会把插桩吞掉，得先改成 `inherit()`）：

```
DBG2 skip grade st=1 "初一" vs ev "全部"
DBG2 skip grade st=2 "初一" vs ev "全部"
DBG2 skip grade st=3 "初一" vs ev "全部"
```

**原因**：核心全项目用 **`"全部"`** 表示"不限年级"
（`api.rs:606/697/1020` 三处都是这个口径）。但我写推荐时
只把 **`"通用"`** 当作不限 —— 这是**臆测的契约**。
于是 `"全部"` 被当成一个具体年级名，`st.grade != ev.grade`
把所有学生全部过滤掉。

**为什么 26 个单测一个都没抓到**：`smart.rs` 的夹具 `ev()` 里写死了
`grade: "初一".into()`。测试**覆盖了"限定年级"**，
却**漏了"不限年级"这条线上更常用的路径**。
而默认预置的 17 个项目年级字段**全都是 `"全部"`** ——
也就是说推荐功能对**绝大多数**项目完全不可用。

**修法**：
1. `grade_unrestricted` 同时识别 `""` / `"全部"` / `"通用"`，
   并在注释里明确写出"与 `api.rs` 的报名校验口径对齐"；
2. 夹具默认值从 `"初一"` 改为 **`"全部"`**（对齐线上最常见的取值），
   另加 `ev_grade()` 构造器供"限定年级"用例使用；
3. 补 3 个回归测试：
   - `grade_all_means_unrestricted_and_yields_candidates`（正面）
   - `specific_grade_still_filters_candidates`（对照：限定仍然生效）
   - `gender_all_and_unrestricted_variants_are_open`（四种写法都放行）

**教训**：
- **夹具默认值要取"线上最常见"的值，不是"写测试最方便"的值。**
  默认值决定了测试默认覆盖哪条路径 —— 选错等于把主路径排除在测试之外。
- 涉及**跨模块共享的字符串枚举**（`"全部"`/`"通用"`/`"男子"`），
  要么抽成常量，要么在注释里交叉引用定义点，别凭印象写。
- 单测全绿不等于功能可用。**必须有一次真实数据 + 真实 HTTP 的端到端走查**，
  本次 6 个 bug 里有 3 个是这一步才现形的。

## #28 `withBusy(...)` 包装后忘记绑定 `onclick`，按钮静默失效（v1.5）

**现象**：智能解析按钮点了没反应，**控制台无任何报错**。

**排查**：Playwright 里检查按钮绑定的处理函数：

```js
const go = document.getElementById('rs-smart-go');
typeof go.onclick        // → "object"（null 的 typeof 也是 object！）
go.onclick               // → null    ← 真因
```

同时 `typeof smartParse` 是 `"function"` —— 函数**定义成功了**，
只是**从来没被挂到按钮上**。

**原因**：写法是两段式的

```js
const smartParse = withBusy($("rs-smart-go"), async () => { ... });
// ← 这里漏了 $("rs-smart-go").onclick = smartParse;
```

`withBusy` 返回一个**新函数**，光定义变量不会自动绑定。

**修法**：补上绑定，并用脚本**系统性扫描**确认无同类遗漏：

```python
names  = re.findall(r'(?:const|let)\s+(\w+)\s*=\s*withBusy\(', script)
bound  = set(re.findall(r'\.onclick\s*=\s*(\w+)\s*;', script))
missing = [n for n in names if n not in bound]   # → []
```

（13 个 `withBusy` 包装的函数全部已绑定。）

**教训**：
- **`typeof x === "object"` 对 `null` 也成立**，不能用它判断"是否绑定了
  函数"。要直接取 `x.onclick` 看是不是 `null`。
- 前端"静默失效"比抛异常更难查：抛异常至少会在控制台留痕，
  而漏绑定什么都不会说。**定义与绑定分离的写法是高危模式**，
  要么就近写 `$("#x").onclick = withBusy($("#x"), async () => {...})`，
  要么写完立刻用脚本扫一遍。
- 新增多个按钮时，**数一下按钮数 == 绑定语句数** 是最省事的自检。

## #29 接口字段名靠猜（`ttl` vs `ttl_secs`）/ 时间语义混淆（v1.5）

**现象**：换到令牌后，界面显示"令牌已过期，请重新获取"，
但令牌明明是刚签发的。

**原因**：前端凭印象写成 `d.ttl_secs` 和 `Number(d.expires_at)`。
实际接口返回：

```json
{"token":"...", "expires_at":"2026-09-26 09:04:38", "ttl":43200, "notice":"..."}
```

两个错误叠在一起：
1. 字段名是 **`ttl`**（秒），不是 `ttl_secs`；
2. **`expires_at` 是给人看的可读时间串**，不是 Unix 时间戳。
   拿它减 `Date.now()/1000` 得到 `NaN` → 判定为已过期。

**修法**：改用 `Number(d.ttl)` 推到期时刻，并把 `expires_at` 只用于显示；
对 `ttl` 缺失留 12 小时兜底：

```js
const ttl = Number(d.ttl);
const exp = Number.isFinite(ttl) && ttl > 0
  ? Math.floor(Date.now() / 1000) + ttl
  : Math.floor(Date.now() / 1000) + 12 * 3600;
```

**教训**：
- **写前端前先把接口 `curl` 一遍看真实响应**，不要照着自己的命名习惯写。
  本次 4 个前端问题里有 3 个（#26/#27/#29）都是"没先看真实响应"。
- 同一个概念给出**两种表示**（`ttl` 秒数 + `expires_at` 可读串）时，
  文档要写明哪个能参与计算（本次已在 `api.rs` 的 doc 注释里标注）。
- `NaN` 参与比较**永远为 false**，会让"过期判断"默默走错分支 ——
  这类"错误但不崩溃"的算术最容易埋。

## #30 `pv.preview` 多套了一层：删除按钮点了没反应，且**这是 v1.4 就存在的遗留 bug**（v1.5，中）

**现象**：
浏览器实测"敏感操作二次确认"时，点击项目卡片的「删除」按钮——
确认框不出现，控制台报：

```
PAGEERROR: Cannot read properties of undefined (reading 'registrations')
    at delEvent (index.html)
```

**定位**：
前端 `delEvent` / `delStudent` 写的是：

```js
const pv = await api(`/api/events/${ev.id}/delete_preview`);
const p = pv.preview;            // ← 这里
... html: `...${p.registrations} 条报名...`
```

而后端 `delete_preview_event()` 返回的是**扁平**对象：

```json
{"name":"待删项目X","ok":true,"registrations":0,"results":0}
```

**没有 `preview` 这一层**（`preview` 只在 428 响应的 `data` 里作为包装名出现，
前端把两种形态混为一谈了）。于是 `pv.preview === undefined`，
读 `.registrations` 立刻抛 TypeError。

**关键点：这是 v1.4 的遗留 bug，不是 v1.5 引入的。**
核对备份 `sports_meet_v1.4.0_20260925_2016_bak/web/index.html`：

```
1176:  const p = pv.preview;
1230:  const p = pv.preview;
```

后端 v1.4 的 `delete_preview_event()` 同样返回扁平对象。
**⇒ v1.4 及更早版本，通过 UI 删除项目/学生的功能一直是坏的。**
之所以此前没被发现：v1.4 的浏览器实测（5 场景）覆盖了 XSS / 401 弹窗 / 双端布局，
但**恰好没有点过"删除"按钮**；而 curl 直连测试只验证后端，绕过了前端渲染层。

**修复**（`web/index.html`）：

```js
// 兼容两种形态，并对缺失字段兜底
const p = pv.preview || pv;
html: `...<b>${p.registrations ?? 0}</b> 条报名...`
```

**教训**：
1. **HTTP 响应的嵌套层级必须靠 `curl` 实测确认**，不能凭"应该是
   `{preview:{...}}`"的直觉写。这与 #26/#27/#29 同源——本次 5 个前端
   bug 里有 4 个都是"没先看真实响应"。
2. **"删除"这类低频但高危的按钮必须进浏览器实测清单**。它平时没人点，
   一旦点就是"点了没反应"，用户会以为系统坏了。v1.5 已把
   「删除项目 → 两层确认 → 真正删除」列为固定实测场景（6 项断言）。
3. 需要识别**同一语义的两种响应形态**：正常 200 是扁平对象，
   428 是 `{...预览字段}` 包在 `err.data` 里。前端应当兼容，
   而不是把其中一个当成通用形态。
4. **历史文档里的"已实测通过"要看清测了什么**。v1.4 记录了 5 个场景全过，
   但没覆盖删除——这不代表删除是好的。验收清单要按**功能面**而非
   **改动面**来列，否则没改过的老功能会成为盲区。

## #31 开发接口被普通口令鉴权拦住，形成"解锁死锁"（v1.5.1，致命）

**现象**

带 `--password` 启动的实例上，点击诊断页的「解锁开发者模式」**毫无反应**：

```bash
$ curl -s -X POST -d '{}' http://127.0.0.1:18803/api/dev/unlock
{"auth_scheme":"token_or_password",
 "error":"需要管理员凭证：请先 POST /api/auth/token 换取令牌，或直接提供口令"}
```

HTTP 状态是 **401**，前端 `api()` 见 401 就弹"需要管理口令"。

**根因**

`dispatch_inner` 的鉴权判定是**按 HTTP 方法**做的：

```rust
let is_write = method == "POST" || method == "DELETE";
let needs_auth = is_write && self.core.password.is_some()
    && path != "/api/auth/token"
    && !readonly_post;
```

`POST /api/dev/unlock` 是 POST，于是被当成写操作拦下。

**为什么这是"死锁"而不是"多输一次口令就行"**

`/api/dev/unlock` 的设计前提是"**自带一套比口令更严的门槛**"
（密钥 + 本机 + 风险确认）。如果它还要口令，逻辑上就变成：

> 想解锁开发者模式 → 得先有口令 → 但解锁请求本身又要口令 → 回到起点

更糟的是：开发者模式的用途正是**绕过口令的二次确认**。一个"必须先输口令
才能打开的免口令开关"，本身就自相矛盾。

**修复**（`src/core/http.rs`）

```rust
// 例外三（v1.5.1）：/api/dev/* 是密钥机制的入口，自带更严的三重条件。
let is_dev_endpoint = path.starts_with("/api/dev/");
let needs_auth = is_write && self.core.password.is_some()
    && path != "/api/auth/token"
    && !readonly_post
    && !is_dev_endpoint;
```

**教训**

1. **这与 #26 是同一类错误的第二次发作**——#26 是"只读 POST 被误判为写"，
   本次是"自带更强鉴权的 POST 被误判为普通写"。规则 15 早已写明
   *"HTTP 方法 ≠ 是否改变状态"*，但**当时只补了 `readonly_post` 白名单，
   没有形成"任何 POST 都要先问一句它属于哪一类"的习惯**。
2. **白名单的每一条都要有对照组测试**。本次立刻补了
   `dev_endpoints_bypass_password_auth_but_not_conditions`：
   一边验证"设了口令也能解锁"，另一边验证"没有密钥的实例即使免鉴权也解不开"
   —— 两侧都测，才能证明**放开的是鉴权层、不是安全层**。
3. **新增接口时，第一件事是列出它要穿过哪几层拦截**。本项目现在有四层：
   鉴权 → 二次确认 → CSRF(Content-Type) → 路由。新接口必须逐层回答
   "我要不要过这一层、为什么"。这比事后 debug 便宜得多。

## #32 两层确认机制互相掩护，只放开一层仍然 428（v1.5.1，致命）

**现象**

修完 #31、成功解锁后，同一个 `DELETE` 依然被拦：

```bash
$ curl -X POST .../api/dev/unlock
{"dev_mode":"unlocked","ok":true}
$ curl -X DELETE -H "Authorization: Bearer $TOK" .../api/events/1
{"confirm_required":true,"error":"需要确认",
 "preview":{"name":"男子100米","ok":true,"registrations":0,"results":0}}   # 仍是 428
```

**根因：项目里有**两套**独立的"确认"机制**

| 机制 | 位置 | 触发条件 | 返回 |
|---|---|---|---|
| **HTTP 层二次确认** | `http.rs` `is_sensitive_path` | 设了口令 + 敏感路径 | 428 `confirm_kind: password` |
| **业务层防误触预检** | `api.rs` `delete_event(id, confirmed)` | `?confirm=1` 未带 | 428 `{preview:{...}}` |

我修 #31 时只让 devmode 跳过了**第一层**（HTTP 层），业务层的
`confirmed` 参数仍是从 `?query` 取，devmode 下自然是 `false`，
于是第二层接着拦。

**"两套同名机制"的危险性**

它们的**状态码相同（都是 428）、语义相近（都是"确认一下"）、
返回结构却不同**（一个带 `confirm_kind`，一个带 `preview`）。
调试时看到 428 会以为"第一层没修好"，于是反复检查已经修对的地方
—— 这是本次真正浪费时间的地方。

**修复**（`src/core/api.rs`）

```rust
r("DELETE", "/api/events/{id}", |c, req| {
    let id = path_i64(req, "id")?;
    // devmode 下跳过预检，但必须留痕
    if req.dev_mode && req.query_get("confirm").as_deref() != Some("1") {
        crate::core::audit::record("devmode", "dev_bypass_confirm",
            &format!("开发者模式跳过删除预检：项目 #{}", id));
    }
    Ok(Response::json(&c.delete_event(
        id,
        req.query_get("confirm").as_deref() == Some("1") || req.dev_mode,
    )?))
});
```

**设计决策：为什么"跳过"是正确的，而不是"仍然要求 confirm=1"**

- 业务层预检的目的是**防误触**（手滑点错）。devmode 的三重条件
  （本机 + 密钥 + 风险确认）已充分说明这是**有意为之**的调试动作。
- 若仍要求 `?confirm=1`，诊断页上的"清理测试数据"就形同虚设
  —— 而"便于调试"正是开发者模式存在的**全部理由**。
- **补偿措施**：跳过预检的同时写一条审计，把"谁在什么时候用
  开发者模式删了哪个项目"钉进哈希链。**便利是用可追溯换来的。**

**教训**

1. **改"确认/拦截"类逻辑前，先 grep 全项目有几个同名机制**
   （`grep -n "428\|需要确认\|confirm" src/`）。这与规则 16
   （枚举口径必须 grep 全项目）同源，只是对象从"字段取值"变成了
   "横切机制"。
2. **同状态码不同语义时，响应体必须能区分**。本项目两套 428
   分别带 `confirm_kind` 与 `preview`，事后看来是**幸运**而非设计。
   这次之后明确：新加 428 必须带一个可区分的判别字段。
3. **放行一个安全门时，必须同时问"谁替它兜底"**。本次的答案是
   "审计链"。没有补偿措施的放行，等于纯降级。

## #33 自实现流加密的"末块"边界：`% unit != 0` 的判定其实是错的（v1.5.1，中）

**现象**

`vault::open` 里我写了这段长度校验：

```rust
let unit = BLOCK_SIZE + 8;
if body.len() % unit != 0 {
    if body.len() < 8 { return Err(VaultError::Truncated); }
}
```

它**看起来**在检查对齐，实际上**什么也没检查** —— 因为
`chunks(BLOCK_SIZE)` 产出的末块长度是 `plain.len() % BLOCK_SIZE`，
密文体长度天然**不是** `BLOCK_SIZE + 8` 的整数倍。

**为什么没炸**

`while pos < body.len()` 循环里用的是动态的 `ct_len`：

```rust
let ct_len = if remain > BLOCK_SIZE + 8 { BLOCK_SIZE }
             else { remain.checked_sub(8).ok_or(VaultError::Truncated)? };
```

末块的 `ct_len = remain - 8`，恰好正确。**真正起作用的是循环里的
`checked_sub(8)`，而我精心写的那段 `% unit` 校验是死代码。**

**修复**

把误导性的 `% unit` 校验删掉，改为**显式的末块长度检查**：

```rust
// 每块必须是「密文 + 8 字节 MAC」，故剩余长度至少 8。
// 注意：**不能**用 `body.len() % (BLOCK_SIZE + 8) == 0` 来判定 ——
// 末块长度是 `plain.len() % BLOCK_SIZE`，不是整块，该式为假是正常的。
```

并补测试 `roundtrip_exact_block_boundary`，覆盖
`BLOCK_SIZE-1 / BLOCK_SIZE / BLOCK_SIZE+1 / BLOCK_SIZE*3` 四个边界，
以及 `truncated_rejected`（砍掉尾部 4 字节须报错）。

**教训**

1. **"看起来在检查"的死代码比不检查更危险**：它会让后来者（包括
   三周后的自己）以为这条边界已被覆盖，从而**不去写真正需要的测试**。
2. **写长度校验时，先手算一遍边界用例的字节数**。
   本次 `BLOCK_SIZE=4096`、明文 10000 字节 →
   块 0: 4096+8, 块 1: 4096+8, 块 2: 1808+8 = 1816。
   `10024 % 4104 = 1816 ≠ 0` —— 一眼可见原判定无意义。
3. **块边界值是压缩/加密/分帧类代码的头号雷区**（参见 #25 SSE 分段）。
   凡是 `chunks(n)`/`read_to_end`/分帧，测试必须显式覆盖 `n-1 / n / n+1`。

## #34 放宽快捷键取值范围却没同步检查数组长度，Ctrl+9 静默失效（v1.5.1，中）

**现象**

新增第 8 个页签「诊断」后，我"顺手"把快捷键范围从 `1~8` 放宽到 `1~9`：

```js
if (e.ctrlKey && e.key >= "1" && e.key <= "9") {
  e.preventDefault();
  goPage(PAGE_NAMES[+e.key - 1]);   // ← PAGE_NAMES 只有 8 个元素
}
```

`PAGE_NAMES` 长度是 **8**（索引 0–7），而 `Ctrl+9` 取索引 **8** → `undefined`。

**后果链条（这条最值得记）**

```text
goPage(undefined)
  → CUR_PAGE = undefined
  → $("page-undefined") 返回 null
  → null.classList 抛 TypeError
  → 异常发生在函数第 3 行
  → 后面所有 refresh*() 全部不执行
  → 页面看起来"按了没反应"，且**只有控制台的 pageerror 能看出来**
```

浏览器实测捕获到：

```text
pageerror: Cannot read properties of null (reading 'classList')
```

**为什么"控制台没报错"这个判据会骗人**

这条异常**是**报错的（`pageerror`），只是它：
- 不出现在页面任何位置；
- 不影响其他按钮（点导航按钮走的路径正常）；
- 不产生 HTTP 请求，网络面板也是干净的。

**若只看"页面能打开、其他页签能切"，会得出"诊断页正常"的错误结论。**

**修复（两层防御）**

```js
// 第一层：边界检查 —— 下标必须在数组范围内
if (e.ctrlKey && e.key >= "1" && e.key <= "9") {
  const idx = +e.key - 1;
  if (idx >= 0 && idx < PAGE_NAMES.length) {
    e.preventDefault();
    goPage(PAGE_NAMES[idx]);
  }
}

// 第二层：goPage 内部防御 —— 非法页名直接返回，不抛异常
function goPage(name) {
  const target = $("page-" + name);
  if (!target) return;        // ← 静默忽略，绝不半途炸掉整个切换流程
  CUR_PAGE = name;
  ...
}
```

**顺带修掉的既有错误**

修正过程中发现标签数字与数组下标**本来就对不上**（v1.5 遗留）：

| 页签 | 数组下标 | v1.5 标签 | 修正后 |
|---|---|---|---|
| 系统设置 | 5 | Ctrl+7 | **Ctrl+6** |
| 实时大屏 | 6 | Ctrl+8 | **Ctrl+7** |
| 诊断 | 7 | Ctrl+9 | **Ctrl+8** |

原因是 v1.5 曾移除过一个页签（原 Ctrl+6），标签**只改了被删的那个，
没动后面的** —— 典型的"改一处漏一片"。

**教训**

1. **放宽取值范围时，必须同步检查所有相关的边界**。
   `>= "1" && <= "9"` 这种字面量比较极易通过代码审查，
   因为"9 对应第 9 个"听起来天经地义 —— 但数组只有 8 项。
2. **键盘快捷键、下拉选项、页签序号这类"位置耦合"的代码，
   必须用下标而非字面量**。本次修正后，标签由人工核对改为
   "按键号 = 下标 + 1"的统一规则。
3. **扩展规则 17 的适用范围**：该规则原本只要求"校验事件绑定是否漏挂"。
   本次之后升级为**"前端交互三查"**：

   | 查什么 | 怎么查 | 本次结果 |
   |---|---|---|
   | 事件绑定 | 脚本扫描 `$("x").onclick` 的 id 是否都存在 | 48 处零缺失 ✓ |
   | 数组下标 | 键盘/序号类取值是否越界 | 发现 Ctrl+9 越界 ✗→✓ |
   | 页签一致 | `section` / 导航按钮 / `PAGE_NAMES` 三处是否齐平 | 发现标签错位 ✗→✓ |

4. **"控制台零错误"必须是硬断言**，不能只做人工扫一眼。
   本次脚本里 `pageerror` 与 `console.error` 被一并收集并断言为 0，
   才让这条静默失效暴露出来。**若没这条断言，#34 会漏到交付后。**

## #35 加密落盘后必须"带着 `--encrypt-data` 才读得到"——忘记它数据就像凭空消失（v1.5.1，中高）

**现象**

打包前逐场景手工验证时发现：用 `--encrypt-data` 加密落盘后，**换个实例、
只带 `--devkey` 而不带 `--encrypt-data`** 启动，数据读出来是 **空的**——
学生、项目全没了，日志只有一句"未提供密钥，无法解密"。
而所有自动化测试都是**绿**的。

**根因**

`--encrypt-data` 原本被设计成"**写入开关**"：只有它为真时，
`activate_vault` 才会武装保险库、去读 `.smev` 密文。
于是"**读取**"悄悄依赖了"**写入**配置"：

```
读得到数据  ⟺  （本次启动带了 --encrypt-data）  AND  （磁盘上其实是密文）
                              ↑
                    这一条与"数据本身是否加密"毫无关系
```

也就是说，**是否能读到数据，取决于一个跟数据无关的启动参数**。
用户视角看就是："我明明有密钥，数据却没了。"

**为什么测试没抓到**

| 测试 | 为什么漏过 |
|---|---|
| `encrypted_data_is_unreadable_without_key` | 它验证的是"**故意**不给密钥 → 读不出"，恰好符合当时的行为，测不出问题 |
| `encrypt_data_without_key_falls_back_to_plaintext` | 验证的是"给了 `--encrypt-data` 但没密钥"，方向相反 |
| 所有其它测试 | 要么不加密，要么**规规矩矩同时带了两个参数**——没有一条测"只带密钥" |

**共同盲区**：测试全部由**知晓内部实现的人**编写，天然会"正确地"传参；
而真实用户拿到的可能只是"**某个启动脚本**"，少一个参数极常见。

**修法（两层）**

1. **自动探测**：`activate_vault` 在未启用时不直接返回，而是先看
   数据目录里**是否存在 `.smev` 且不存在同名明文**——是则自动进入加密读取模式。
   判据刻意收紧为"密文在、明文不在"，避免把用户手工放回的旧明文文件误当密文。
2. **状态字段分开**：新增 `vault_detected`（磁盘上有密文）与
   `vault_enabled`（本次已武装并成功解密），在 `/api/meta` 与 `/api/dev/status`
   里**分开上报**，诊断页据此给出准确指引，而不是笼统的"未启用（明文）"。

**日志级别的一个额外考量**

修完后又发现：无密钥时日志级别该用 INFO 还是 ERROR？
最终**统一用 INFO**——因为如果"密钥错误"报 ERROR、"没给密钥"报 INFO，
就等于给爆破者开了一条**反馈信道**（能分清"猜错了"和"没猜"）。
两情形措辞完全一致，与 `License` 的静默降级原则保持同一思路。

**教训**

1. **写入配置不得隐式决定读取行为**。加密状态下，"能读"应当由
   **数据文件的实际形态**（有没有 `MAGIC`）加**密钥是否可用**决定，
   而不是由"本次有没有传某个写入开关"决定。
2. **凡是"用户要记住两个参数才能正常工作"的设计，都是隐患**。
   正确做法是让系统自己探测，或让第二个参数变为可选/可推导。
3. **验收清单按"用户可能怎么用"列**（规则 18）："只带 `--devkey`"这种
   **半省略调用**，是最容易被实现者忽略、却最接近真实使用的一种。
4. **补回归测试要覆盖"参数组合的省略形态"**，而非只测"全传"与"全不传"两端：
   新增 #35（只带密钥 → 自动解密）与 #36（有密文无密钥 → 不动原文件）。

## #36 启动横幅打印的"密钥指纹前缀"是**编译期常量**，与实际使用的密钥无关（v1.5.1，低中）

**现象**

收尾阶段逐场景手工核对启动横幅时发现，三种完全不同的启动方式，横幅里的
指纹前缀**一模一样**：

```
# 正确密钥
数据加密：已启用（.smev）（密钥指纹前缀 35d0）
# 没给密钥
数据加密：检测到密文但缺少密钥（请用 --devkey 提供正确密钥）（密钥指纹前缀 35d0）
# 错误密钥，且实际未武装
数据加密：检测到密文但缺少密钥（请用 --devkey 提供正确密钥）（密钥指纹前缀 35d0）
```

第三种情况尤其荒谬：**一行里前半句说"缺少密钥"，后半句却贴心地给出一个指纹**。

**根因**

`main.rs` 的横幅代码写的是：

```rust
"数据加密：{}（密钥指纹前缀 {}）",
vault_state,
&crate::core::license::LICENSE_FINGERPRINT[..4]     // ← 编译期常量
```

`LICENSE_FINGERPRINT` 是**编译期内置的演示密钥**（`THZX-2026-DEV`）的指纹常量，
和本次启动实际传入的密钥毫无关系。两个缺陷叠加：

1. **无条件打印**：不管有没有可用密钥，都把括号打出来；
2. **打印错了对象**：打的是常量，不是"本实例种子"的真实指纹。

于是使用者若想拿横幅里的前缀去核对"我传的密钥对不对"，会得到**错误结论**——
这比不打印更有害，因为它看起来像一条可信的校验信息。

**修法**

改为**只在本实例确实有种子时**打印，且打印**真实种子**的指纹：

```rust
match core.store.seed.as_deref() {
    Some(seed) => println!(
        "数据加密：{}（本实例密钥指纹前缀 {}）",
        vault_state,
        crate::core::vault::seed_fingerprint(seed).get(..4).unwrap_or("????")
    ),
    None => println!("数据加密：{}", vault_state),
}
```

修后实测：

| 场景 | 横幅 |
|---|---|
| 正确密钥并已武装 | `数据加密：已启用（.smev）（本实例密钥指纹前缀 482c）` ✅ |
| 没给密钥 | `数据加密：检测到密文但缺少密钥（请用 --devkey 提供正确密钥）` ✅ 无指纹 |
| 错误密钥 | 同上 ✅ 无指纹，且措辞与"没给密钥"**完全一致** |

`482c` 与 `/api/dev/status` 的 `seed_fingerprint = 482ce20432d43d9c` 前四位吻合。

**教训**

1. **"展示一条校验信息"和"展示一条看起来像校验信息的东西"是两回事**。
   凡是给使用者用来核对的信息，必须是**本实例的真实值**，不能是常量、
   不能是模板、不能是"上次算好的"。
2. **常量应当只用于它真正代表的东西**。`LICENSE_FINGERPRINT` 代表的是
   "内置演示密钥的指纹"，把它当成"当前密钥的指纹"来展示，是**语义挪用**。
3. **条件渲染要跟着条件走**。既然状态机已经能区分"有密钥/没密钥"，
   那么**依赖密钥才成立的那部分文案就该一起条件化**，而不是只换前半句、
   后半句照旧打印。
4. **"前后矛盾的一句话"是最好的自检信号**。当一行输出里
   "缺少密钥"和"指纹是 XXX"同时出现时，逻辑上已经自相矛盾——
   手工核对时不要因为它"看起来像正常日志"就滑过去。

## #37 空查询串被当成筛选条件：学生名单在"全部班级"下永远是空的（v1.5.1 起存在，v1.5.2 修复，中）

**现象**

做语音搜学生时，脚本报"没有找到与『王五』匹配的学生"。手工一看：
学生页在「全部年级 / 全部班级」下显示 **"暂无学生"**，
但接口 `GET /api/students`（不带参数）明明返回 3 人。
切到具体某个班才看得见人。

**根因**

前端 `refreshStudentsPage` 始终以带参数形式调用：

```js
api(`/api/students?grade=${encodeURIComponent(g)}&class_no=${encodeURIComponent(c)}`)
```

下拉框选"全部"时 `c` 是 **空串**，于是请求变成 `?grade=&class_no=`。
后端：

```rust
let class_no = req.query_get("class_no")      // → Some("")
    .and_then(|v| v.parse::<i64>().ok());     // "" 能解析成功 → Some(0)
```

`query_get` 对 `class_no=` 返回 `Some("")` 而不是 `None`；
`"".parse::<i64>()` 返回 `Ok(0)`。于是语义从"不筛选"变成了
**"筛选班级号等于 0 的学生"**，而班级号从 1 起 —— 结果恒为空。

同一份代码里 `/api/report_table` 也有同样写法（`grade` 空串 → `Some("")` →
匹配不到任何年级 → 空表），只是当前前端不传该参数，尚未暴露。

**为什么长期没被发现**

1. **测试全用不带参数的形式**（`/api/students`），恰好是**唯一正确**的那种调法；
2. 前端**从不发**不带参数的形式，真实路径 100% 命中缺陷分支；
3. 现象"列表为空"很容易被解释成"学生还没录入"，
   尤其在一个**新建即空库**的工具里，空列表太正常了。

**修法**

把"空白串"统一归一化为 `None`（= 不过滤）：

```rust
let grade = req.query_get("grade").filter(|v| !v.trim().is_empty());
let class_no = req.query_get("class_no")
    .filter(|v| !v.trim().is_empty())
    .and_then(|v| v.parse::<i64>().ok());
```

`/api/report_table` 一并修。补回归测试 `empty_query_strings_mean_no_filter`
（集成测试 #37），同时断言"明确筛选仍生效"，防止修成"所有输入都不过滤"。

**教训**

1. **"参数存在"≠"参数有值"**。只要区分"缺省"与"显式给空"的语义，
   就必须在**解析层**做归一化，不能依赖 `parse` 失败来兜底 ——
   因为空串解析 `i64` 是**会成功**的。
2. **测试参数形态要和真实调用形态一致**。测"正确写法"很舒服，
   但真正跑的是"前端写法"。这类缺陷只有**照着浏览器实际发出的请求抄**才测得出。
3. **空列表是极佳的伪装**。凡是"没有数据"与"筛选条件错了"表现一样的界面，
   都该在开发期用一个**非空初始数据集**过一遍，否则缺陷可以静默存在很久。
4. **发现一处空串缺陷后要全项目搜同构写法**。本例中 `report_table`
   就是同一个模子刻出来的，只是暂时没被触发。

## #38 建了按钮却没放进 DOM，且"防重复挂载"把它锁死成静默半成品（v1.5.2，中）

**现象**

语音输入开发中，`st-name`（学生姓名框）看起来一切正常：
父节点已经是 `class="mic-wrap"`、`dataset.micAttached` 也是 `"1"`，
**但页面上看不见任何麦克风按钮**，`.mic-btn` 计数为 0。

**根因**

`attachMic()` 里创建了按钮对象，却**漏了把它挂进父节点**：

```js
const btn = document.createElement("button");
btn.className = "mic-btn";
... // 设置 title / innerHTML / 事件
// ← 这里少了 wrap.appendChild(btn);
return btn;
```

更麻烦的是**前置的"防重复挂载"保护**：

```js
if (el.dataset.micAttached === "1") { return ...; }
el.dataset.micAttached = "1";     // ← 在真正挂载**之前**就打上了标记
```

标记先于成果被写下，于是"挂载失败"这件事被永久固化：
第二次调用会被当成"已经挂过了"直接返回，**永远没有机会修正**。

**为什么难发现**

- 没有异常、没有报错，控制台干净；
- 关键状态（`micAttached=1`、`mic-wrap` 存在）**看起来全对**，
  只有去数 `.mic-btn` 才发现是 0；
- 若不是写了"按钮存在性"这一条硬断言，很容易被"代码逻辑看着对"骗过去。

**修法**

1. 补上 `wrap.appendChild(btn)`；
2. 把"这件事必须发生"的注释写在代码旁边，防止后人再删；
3. **把标记下移到挂载成功之后**（更稳的写法）——
   凡是用"标记位"做幂等保护的，标记都应在**动作完成后**再落。

**教训**

1. **幂等标记必须在动作成功之后写**。写成 `if(done) return; done = true; work();`
   时，一旦 `work()` 失败（或被漏写），系统会进入"自认为已完成"的
   永久错误状态 —— 这类 bug 比崩溃更难查，因为它**没有任何信号**。
2. **"状态看起来对"不能当作"功能正常"**。断言要落在**可观测的结果**上
   （这里有按钮吗？点了有用吗？），而不是落在**中间状态变量**上。
3. **DOM 组装的每一步都值得一条硬断言**。createElement 成功不代表
   appendChild 被调用过，两者之间隔着一个很容易漏的步骤。

## #39 构造函数在模块加载时被"抓一次存死"，导致可测性与容错双双受损（v1.5.2，低中）

**现象**

用桩件替换 `window.SpeechRecognition` 后驱动语音流程，按钮进入了
`is-busy`，但假构造函数**一次都没被调用**（`started: 0`），
最终什么也没回填。

**根因**

模块加载时把构造函数取出来存成了常量：

```js
const SR = window.SpeechRecognition || window.webkitSpeechRecognition;
...
rec = new SR();          // 永远用加载那一刻抓到的构造函数
```

于是运行时替换 `window.SpeechRecognition` 完全无效。
这不只是"测试不好写"的问题，它同时意味着：

- 某些环境中该对象**晚于脚本挂载**时，本可以工作却会永久判为不支持；
- 无法做任何运行时的能力刷新（例如用户装了插件后再启用）。

**修法**

改为**惰性取用**：

```js
function getSR() { return window.SpeechRecognition || window.webkitSpeechRecognition; }
...
if (!getSR()) return { ok: false, reason: "unsupported" };
rec = new (getSR())();
```

属性读取开销可忽略，换来的是可测性与运行期容错。

**教训**

1. **不要过早"冻结"来自宿主环境的引用**。凡是 `window.*`、`navigator.*`
   这类**可能后到、可能变化、可能被替换**的对象，用时再取。
2. **"不好测"往往是设计问题的信号，而不是测试的问题**。
   当测试只能靠"反射/全局搜索"绕过某个常量时，该常量多半不该是常量。
3. **惰性化几乎没有代价**，却同时买到测试性、容错与可刷新性，
   在这类边界代码上应当成为默认选择。

## #40 「状态码说失败，状态短语说成功」：HTTP 状态短语兜底写成了 OK

- **等级**：中
- **现象**：对敏感接口压测触发限流后，响应第一行是

  ```
  HTTP/1.1 429 OK
  ```

  状态码 `429`（Too Many Requests，明确失败），但短语是 `OK`。
  严格遵循 RFC 的客户端、网关、抓包分析工具可能把这判为**畸形响应**。

- **原因**：`status_text()` 是一个手写的 `match`：

  ```rust
  fn status_text(code: u16) -> &'static str {
      match code {
          200 => "OK",
          201 => "Created",
          400 => "Bad Request",
          /* ... */
          503 => "Service Unavailable",
          _ => "OK",          // ← 兜底
      }
  }
  ```

  这个兜底在 v1.6.0 **之前就存在**，只是当时没有 429 这类新码，
  所以从未暴露。v1.6.0 引入 429 却**没同步加进 match**，
  于是新状态码直接落到 `_ => "OK"`。

  更值得警惕的是：**任何未列出的 4xx/5xx 都会被拼成 `OK`**。
  这不是 429 独有的问题，而是兜底值选错的长期隐患。

- **为什么测试没发现**：所有集成测试断言的都是**状态码数字**
  （`assert_eq!(st, 429)`），**没有一个用例读状态短语**。
  数字对，测试就全绿。这类缺陷对自动化测试天然"隐形"。

- **发现方式**：压测限流时顺手用 `curl -D -`（打印响应头）看了一眼，
  才注意到那行文字。**属于自省式发现，不是测试发现**。

- **解法**：补全状态码表，并且**把兜底值改对**——不能让未知码默认成功。

  ```rust
  // v1.6.0：限流返回 429。之前落到 `_` 分支会拼出 "HTTP/1.1 429 OK"，
  // 语义矛盾且会被严格的客户端 / 中间件判为异常。
  429 => "Too Many Requests",
  ...
  // 兜底：绝不返回 "OK"，避免非 2xx 被误读为成功短语
  c if c >= 500 => "Internal Server Error",
  _ => "Bad Request",
  ```

  顺带补齐了 `204 / 403 / 413` 三个此前缺失的常见码。

- **教训**：
  1. **`match` 的兜底值要按"最不可能误导"选，而不是按"看着顺眼"选**。
     `_ => "OK"` 是可读性最差的一种兜底——它让失败看起来像成功。
  2. **新增一个语义类别（新状态码 / 新错误类型 / 新枚举值）时，
     必须同步搜索所有以该类别为输入的 `match`**。
     漏一处，就会得到一个"表面能跑、语义错位"的结果。
  3. **自动化测试断言数字，人需要偶尔看一眼"呈现"**。
     状态行、日志格式、错误提示文案属于"呈现"，测试通常不覆盖，
     但用户天天在看。**打包前手工过一遍真实响应是有价值的一道工序。**

## #41 非法 URL hash：地址栏与界面各说各话

- **等级**：低中
- **现象**：把地址栏改成 `#不存在的页` 后：
  - 界面**停留在原来的页面**（内容不变）
  - 地址栏**保留** `#不存在的页`
  - 用户此时以为"我在看 X 页"，实际看的是上一页的数据

- **原因**：两处逻辑各自"防御"，合起来形成漏洞。

  1. `goPage(name)` 里有防御：

     ```js
     const def = PAGE_BY_NAME.get(name);
     const target = $("page-" + name);
     if (!def || !target) return;   // 静默忽略
     ```

     这条防御本身是**对的**——它是修踩坑 #34（`Ctrl+9` 抛异常中断整页）
     时加的，目的是"宁可静默忽略，也不要半途炸掉整个切换流程"。

  2. `hashchange` 监听器又过滤了一遍：

     ```js
     if (PAGE_BY_NAME.has(h) && h !== CUR_PAGE) { goPage(h); }
     else { /* 什么都不做 */ }
     ```

     非法值被 `has()` 挡掉，然后**没有 else 分支**。

  两边都"不处理"，于是地址栏的非法值与界面状态**永久不一致**。

- **为什么测试没发现**：这是"两种状态不匹配"的问题。
  单独看 hash 是合法的字符串，单独看界面是有效的页面，
  只有**把两者放一起对照**才看得出错位。

- **解法**：非法 hash **不再静默留着**，统一回落到默认页并纠正地址栏。

  ```js
  window.addEventListener("hashchange", () => {
    const h = location.hash.replace("#", "");
    if (PAGE_BY_NAME.has(h)) {
      if (h !== CUR_PAGE) goPage(h);
    } else {
      /* v1.6.0：非法 hash 不再静默留着——那会造成"URL 说 A、界面显示 B"的
         认知错位（用户以为在读数报告，其实看的是上一页）。
         统一回落到默认页，并把地址栏纠正回来。 */
      fallbackToDefaultPage(h);
    }
  });

  function fallbackToDefaultPage(bad) {
    if (bad) console.warn("[导航] 未知页面 " + bad + "，已回落到 " + DEFAULT_PAGE);
    const target = PAGE_BY_NAME.has(CUR_PAGE) ? CUR_PAGE : DEFAULT_PAGE;
    goPage(target);
  }
  ```

  同时把散落的 `"events"` 字面值收敛成**从注册表推导**的单一出处：

  ```js
  const DEFAULT_PAGE = PAGE_BY_ORDER.get(1);
  ```

- **教训**：
  1. **"防御性静默忽略"要配一个"状态修复"动作**。光忽略输入，
     系统会停在一个"输入与状态不一致"的中间态。
     正确姿势是：**拒绝非法输入 + 把状态拉回合法值 + 留一条日志**。
  2. **同一个概念（默认页）在多个地方各写一遍字面值，早晚会不一致**。
     让默认值**从数据推导**，而不是复制。
  3. **多个组件各自"做好自己的事"，不等于系统正确**。
     这里 `goPage` 和 `hashchange` 都没 bug，
     **bug 在两者的接缝上**。这类问题只能靠端到端走查发现。

## #42 默认页字面值散落两处（并入 #41 一并修复）

- **等级**：低
- **现象**：`"events"` 这个默认页名同时出现在
  启动段 `goPage(... ? hash : "events")` 与 `hashchange` 回落逻辑里。
- **原因**：v1.5.1 引入 `PAGE_NAMES` 数组后，默认页仍是硬编码字面值，
  没有跟着进注册表。改页面顺序/改首页时**极易漏改一处**。
- **解法**：

  ```js
  /** 默认落地页：注册表里 order 最小的那页，避免"默认页"字样散落多处。 */
  const DEFAULT_PAGE = PAGE_BY_ORDER.get(1);
  ```

  启动段与回落逻辑统一引用 `DEFAULT_PAGE`。

- **教训**：**"默认值"也是一种契约**，应当有单一出处。
  当某个字面值需要"在多处保持一致"时，它就该被提升为常量——
  尤其是当它已经和一张表（`PAGES`）语义相关的时候。

## #43 `system` 标签被"挂上"了，但从来没人"触发"它

- **等级：高**（会让用户看到过期状态，且**没有任何测试会失败**）
- **现象**：开发者模式下点"上锁"，界面上仍显示"已解锁"，最多持续 5 秒。

- **根因**：v1.6.0 给请求打了标签，但**标签体系是"两半"的**——
  - `CACHE_TAGS`（哪类请求属于哪个标签）
  - `INVALIDATE_RULES`（哪些写操作该失效哪些标签）

  我给 `/api/dev/status` 等打上了 `system` 标签，**却忘了在 `INVALIDATE_RULES` 里加
  任何一条"失效 `system`"的规则**。于是：

  ```js
  // 读侧：给 system 打标签 —— 只做了一半
  CACHE_TAGS = [{ re: /^\/api\/dev\//, tags: ["system"] }, …]
  // 写侧：没有任何一条规则提到 system
  INVALIDATE_RULES = [{ re: /^\/api\/students/, tags: ["students", "events"] }, …]
  //                                                  ↑ 没有 system
  ```

  另一层原因是 **`ttl` 是全局常量 5 秒**——所有读接口都一样长。
  这意味着即使标签失效做对了，"状态类"和"统计类"数据也享受着同样长的缓存窗口，
  而**状态类数据根本不该被缓存**。

- **修复**：不新增开关，而是引入**标签级 TTL 覆盖表**：

  ```js
  /** 标签级 TTL 覆盖：0 表示"不缓存"。 */
  const TAG_TTL = { system: 0, undo: 0 };

  function ttlFor(path) {
    const tags = tagsFor(path);
    let best = DEFAULT_TTL;
    for (const t of tags) {
      if (Object.prototype.hasOwnProperty.call(TAG_TTL, t)) {
        best = Math.min(best, TAG_TTL[t]);   // 取"最严格"的那个
      }
    }
    return best;
  }
  ```

   并把判定**收敛到唯一一处**（`request()` 里不再有第二份 `ttl` 逻辑）。
   同时补了一条 `INVALIDATE_RULES` 规则作**纵深防御**（万一以后 ttl 被改回去）：

  ```js
  { re: /^\/api\/dev\/(unlock|lock)/, tags: ["system"] },
  ```

- **为什么用 `TTL=0` 而不是新增 `nocache` 分支**：
  `expireAt > now` 在 `ttl=0` 时**恒不成立**，自然走真实请求——**不需要额外分支，
  也就少一个能写错的地方**。而且它仍然走 in-flight 合并路径，并发下依旧只发一个请求。

- **验证（行为级）**：

  | 实测 | 结果 |
  | --- | --- |
  | 连续两次 `GET /api/dev/status` | 后端计数 **3 → 4**（真发请求，不是缓存） |
  | 两次 `GET /api/meta`（普通读） | 计数只推进 2 → **普通缓存未被误伤** |

- **教训**（→ 写入 `docs/04` **规则 22**）：
  **标签体系必须成对检查。** 打标签和失效规则是同一件事的两端，
  只写一端等于没写——而且**编译器、类型系统、测试都帮不了你**，
  因为它是"两个数据结构之间的默契"，不是代码错误。

  > 更一般的表述：**凡是"靠两处约定保持一致"的机制，都必须有一处自检或测试**。
  > 这类 bug 的特征是"代码全对，但少写了一行没有语法错误的配置"。

## #44 第二个进程静默覆盖第一个进程的数据

- **等级：高**（**丢数据**，且完全无提示——用户不会发现，直到对不上账）
- **现象**：双击两次 exe（或旧窗口没关又开一个），两个进程同时写同一份数据文件。

- **根因**：我被自己 v1.6.0 文档里的一句话误导了——
  「持久化是**整文件原子写**，所以不会写坏」。

  这句话**本身没错，但它回答的不是这个问题**。原子写保证的是：

  > 单个文件的内容不会处于"写了一半"的状态。

  而两个进程并发写时的问题是：

  > A 读 v1 → B 读 v1 → A 写 v2 → B 写 v2（**B 的 v2 覆盖了 A 的 v2**）

  这叫 **lost update**，原子写**完全防不住**。我把"不会写坏"错当成了"不会丢"。

- **修复**：新增 `src/core/dirlock.rs`，数据目录级互斥。

  两阶段获取（**第一版这里还藏了一个 bug，见下方"修复中的二次踩坑"**）：

  ```
  ① 读已有锁 → 解析 (pid, since) → pid_alive()?
       活着   → Busy（拒绝启动，打印占用者 PID）
       死了   → 先 remove_file（关键！）再进 ②
       不可解析 → 先 remove_file 再进 ②
  ② File::create_new(lock)  ← O_EXCL，原子；失败说明有人抢先 → 复查后如实报错
     写入 (pid, now) → **写完后复查文件内容确实是自己的**（防极端竞态）
  ```

- **修复中的二次踩坑**（被我自己写的 `stale_lock_from_dead_pid_is_reclaimable` 抓到）：
  第一版**没有**步骤 ① 里的 `remove_file`，于是 `create_new` 因为"文件已存在"而失败，
  代码走到 `Err` 分支**谎报"被占用"**——**陈旧锁被永久误报为活锁，用户加 `--ignore-lock` 才能启动**。
  也就是说：**我为修一个 bug 写的第一版代码，本身就是个 bug**，而它被同一次改动里写的测试抓住了。
  > 这件事本身就是 #46（补测试）价值的**最好证据**。

- **`pid` 探活的三平台实现**：Linux `/proc/<pid>`；Windows `tasklist /FI "PID eq N" /NH`；
  其他平台**保守返回 `true`**（宁可误报占用，也不误放行导致丢数据）。

- **`--ignore-lock` 逃生开关**：pid 为 `0` 作哨兵，`Drop` 时直接返回（不删别人的锁文件）。

- **为什么不引 `flock`/`LockFileEx`**：`std` 没有跨平台文件锁，
  要做得引 `fs2`/`nix`/`winapi` 或写 `unsafe` FFI，**违反规则 10（最小依赖）**。
  本项目只需挡住"人手误操作"（双击两次），`pid` 探活**零依赖、跨平台、且人类可读**
  （能直接告诉用户是**哪个 PID** 占着——这对排障远比一个 `EWOULDBLOCK` 有用）。

- **为什么不自动清理陈旧锁**：自动清理会让"两个进程真在同时写"**更隐蔽**。
  宁可让使用者看到提示、再由**他自己**决定是否 `--ignore-lock`——决定权留在人手里。

- **为什么锁挂在 `main` 栈上而不是塞进 `Store`**：
  生命周期必须覆盖"**读数据 → 跑服务 → 写数据**"全程。
  绑在 `Store` 上会随 `Core` 的移动/重建而**意外 `Drop`**——这类 bug 极难复现，
  因为"什么时候重建 Core"取决于运行路径。

- **验证（真实双进程）**：

  | 实测 | 结果 |
  | --- | --- |
  | 第二进程指向同一目录 | **退出码 1** + 打印占用 PID/启动时间/锁路径 + `--ignore-lock` 提示 |
  | `--ignore-lock` | 服务正常起（`/api/meta` → **200**）+ `WARN` 留痕 |
  | 持锁进程退出后 | 锁文件残留但**不影响下次启动**（pid 探活发现已死即回收） |
  | 集成测试 | 3 个（含真实双进程）全绿 |

- **教训**（→ 写入 `docs/04` **规则 23**）：
  **"原子性"要问清是"哪个原子单元"。** 文件级原子写 ≠ 跨进程的读-改-写原子。
  当一句话（"整文件原子写，不会写坏"）被用来回答一个它**没有覆盖**的问题时，
  它比没有文档更危险——因为它会让人**放心地不去检查**。

## #45 一次 panic 毒化 Mutex，整个服务永久 500

- **等级：中高**（不会丢数据，但**必须重启进程**才能恢复；且是"偶发一次，永久瘫痪"）
- **现象**：某个请求触发了持锁期间的 panic，此后**所有**需要该锁的请求都失败。

- **根因**：Rust 的 `Mutex` 在**持锁线程 panic** 时会被标记为 `poisoned`，
  之后**每一次** `.lock()` 都返回 `Err`。项目里有 **37 处 `.lock().unwrap()`**——
  于是**第一次** `unwrap()` 在 panic 时炸掉，**之后每一次** `unwrap()` 都在同一个地方再炸一次。

  这是"**一次故障变成永久故障**"的典型结构：故障源只有一次，但**放大机制**让它永久化。

- **修复**：新增 `src/core/sync.rs`：

  ```rust
  pub trait LockExt<T> {
      fn lock_recover(&self) -> MutexGuard<'_, T>;
      fn lock_recover_as(&self, what: &str) -> MutexGuard<'_, T>;
  }

  impl<T> LockExt<T> for Mutex<T> {
      fn lock_recover_as(&self, what: &str) -> MutexGuard<'_, T> {
          match self.lock() {
              Ok(g) => g,
              Err(poisoned) => {
                  crate::log_warn!("sync", "检测到 mutex 已被毒化（{}），已自动恢复", what);
                  poisoned.into_inner()   // 取出数据继续用
              }
          }
      }
  }
  ```

  **37 处全量替换**（`store.rs` 3 处 / `api.rs` 21 处 / `main.rs` 1 处 / `live_board.rs` 9 处仅测试内 / `records_feed.rs` 3 处）。

- **为什么是"自恢复"而不是"快速失败"**：
  本项目是单机记分工具，内存里的数据是**完整快照**（不是"改到一半"的中间态），
  写入又是整文件原子写。因此：
  - 「继续服务」的价值 **>** 「严格一致性」
  - 最坏情况是**本次**这一个请求的结果可能不准确，**不会落盘成损坏数据**

  若这是一个金融类系统，选择应当相反（快速失败 + 人工介入）。

- **代码里的一处细节**：`let _ = m.lock_recover()` 会触发 `deny(let_underscore_lock)` lint
  （Rust 专门防的就是"以为拿到了锁其实立刻丢了"），必须写 `drop(m.lock_recover())`。

- **验证**：`lock_recover_works_on_healthy_mutex` / **`lock_recover_survives_poisoned_mutex`**（核心）/
  `poison_state_is_reported_every_time` / `lock_recover_as_is_equivalent`，4/4 通过。

- **教训**：**`unwrap()` 在锁上不是"断言"，而是"把本地故障升级为全局故障"**。
  凡是"`unwrap` 的位置决定了故障影响范围"的调用点，都应当先问：
  **这个故障应该只影响本次请求，还是应该让整个服务停？**
  默认答案通常是前者。

## #46 `store.rs` 是数据落盘的核心路径，却 0 个单测

- **等级：中**（不是 bug，是**发现 bug 的能力缺失**——而它立刻兑现了，见 #44 的二次踩坑）

- **根因**：历史欠账。早期测试都堆在 `api.rs`（17 个）和 `tests/integration.rs`（46 个），
  `store` 靠集成测试"顺带覆盖"。于是这些边界**一个都没测**：
  - 临时文件是否残留（原子写的另一半往往被忘掉）
  - 数据文件**损坏**、**空文件**时会怎样
  - 加密切换后能否往返
  - **错误密钥**时是"丢弃"还是"返回乱码"

- **修复**：新增 **11 个单测**：

  | 测试 | 覆盖 |
  | --- | --- |
  | `load_initializes_paths_and_empty_data` | 初始化 |
  | `save_then_load_roundtrip_is_lossless` | 存取往返无损 |
  | `save_leaves_no_temp_file_behind` | **原子写不残留临时文件** |
  | `load_from_disk_with_missing_file_falls_back_to_seeded_library` | 文件缺失 → 回退预置 |
  | `load_from_disk_with_corrupt_json_does_not_panic` | 损坏 JSON 不 panic |
  | `load_from_disk_with_empty_file_does_not_panic` | 空文件不 panic |
  | `enable_vault_refuses_encrypt_without_seed` | 无密钥拒绝加密 |
  | `enable_vault_with_seed_arms_the_vault` | 有密钥正常武装 |
  | `encrypted_save_and_load_roundtrip` | 加密往返 |
  | `encrypted_load_with_wrong_seed_discards_data_instead_of_garbling` | **错误密钥必须丢弃而非乱码** |
  | `data_mutex_is_usable_via_lock_recover` | 与 #45 的联动 |

- **写这 11 个测试时踩的坑（很有价值）**：

  **① 我假设错了 3 次"预期值"，而每一次都是"实现是对的、我的假设是错的"**
  - 我以为"文件不存在 → 空数据"，实际是 **回退到 `Data::default() + seed_events()` = 17 个预置项目**。
  - 空文件同理 → 也是 17 个。
  - **教训**：写测试时先**观察**实现的实际行为，再写断言；
    不要先写"我觉得应该是什么"，然后去改实现来迎合——那会把测试变成"实现说明书"。

  **② "等价类陷阱"——一个让正确实现失败的测试**

  错误密钥那条，我最初写成：

  ```rust
  assert_ne!(got, data.events.len());   // ❌ 反例！
  ```

  意图是"错误密钥不该读到真实数据"。但**真实数据 17 条、回退的预置也是 17 条**——
  于是 `17 != 17` 为假，**断言让正确的实现失败了**。
  这是一个**测试写法的等价类陷阱**：用"长度"这种**粗糙的等价类**去区分两种状态，
  而两种状态**恰好落在同一个等价类里**。

  修复方式：把测试数据改成"**清空后只放 1 条名为 `绝密测试项目` 的数据**"，
  然后断言**内容**：

  ```rust
  // 正确密钥：必须能读到那个名字
  assert!(names.iter().any(|n| n == "绝密测试项目"));
  // 错误密钥：不得包含该名字，且长度恰为回退后的 17
  assert!(!names.iter().any(|n| n == "绝密测试项目"));
  assert_eq!(names.len(), 17);
  ```

  **教训**：断言要选**能区分两个状态的维度**。当两个状态可能在某个维度上相同时
  （长度、数量、`is_empty()`），必须改用**内容/身份**维度。
  并且——**一个失败的测试，先怀疑测试自己**。

# 第十六节 · v1.7.0 踩坑（赛程编排 / 秩序册，#47–#50）

## #47 蛇形分组把"后半截人"算没了：17 人只排进 9 个组（v1.7.0，中）

`assign_lanes` 早期实现里，分组数 `gc` 与取列 `col` 两处对不齐：分组数用了错误的表达式，**只生成了前一半的组**，导致 `i >= 组数` 的学生根本没进任何组——17 人里只有 9 个被排进赛道，其余静默消失，且**不报错**。

修复三件事：
1. 分组数统一用 `gc = group_count`（由 `estimate_duration_min` 推出的每组人数反推），取列用 `col = i % gc`；
2. 加 `debug_assert_eq!(len(parts), 全部 lane 的 sum)`，把"总人数守恒"钉成编译期可触发的断言；
3. 单测 `assign_lanes_keeps_everyone`：故意喂 17 人，断言 17 人全进组、无遗漏。

> 共同教训（接 #43）：**"分组/分道"这类"把人分到格子"的逻辑，最容易在边界上静默丢人**。凡是 `i / n`、`i % n` 出现在同一函数，必须有一个断言守住"总数守恒"。

## #48 响应被包进 `data` 信封，测试脚本直接取顶层键 KeyError（v1.7.0，低）

`/api/schedule` 等端点返回的是统一信封 `{ ok, data:{...}, ts }`，`venues`/`sessions`/`slots`/`placed` 都**在 `data` 里**，不在顶层。早期实测脚本写成 `d["venues"]` 直接 KeyError，误以为"二进制是旧版本、端点没注册"——其实端点正常，只是取错层。

> 教训：**凡读本项目接口，先 `.data` 再取字段**（除非是错误信封 `ok:false`）。集成测试用 `serde_json_get_i64(body, "placed")` 搜整段 body 能命中，但它依赖字段名唯一；新写脚本务必走 `data` 信封，别再踩。

## #49 时长估算用 `.max(6)` 把中长跑"地板压平"，违反单调性（v1.7.0，中）

`estimate_duration_min(ev, n)` 早期用 `duration.max(6)` 兜底每人最少 6 分钟，导致人数从 8 涨到 16 时总时长**不增反平**（6 的下限盖住了真实增量）。中长跑测试断言 `n=16` 比 `n=8` 久，直接挂。

修复：下限改成 `.max(per_group)`（`per_group` 是该组真实所需时长），保证**总时长随人数单调不减**。

> 教训：`max(floor)` 这类"防零兜底"一旦盖过真实增量，就会破坏单调性，进而破坏贪心编排"长项目优先"的排序依据。**兜底只该兜"空"，不该兜"小"**。

## #50 默认只给 1 个场地，等于白做"并行"（v1.7.0，设计级）

用户原话"忘了几个场地"——场地数不确定。若默认只给 1 个场地，径赛田赛都得挤一条时间轴，编排毫无并行收益，且极易全部 `out_of_session`。

设计决策：**默认 2 个场地**（田径跑道 for_track + 田赛区 for_field），`auto_arrange` 按 `is_track()` 把项目分流到对应场地，等于免费获得"两条线并行调度"。场地可增删、天数可调 1–5，把"不确定"转成"可配置"。

> 教训：**默认值不是"最小可用"，而是"最能体现设计意图的样板"**。编排类功能，默认配置要让人一眼看懂"为什么这么排"。

# v1.8.0 · 服务端授权（aim）踩坑

## #51 revoke / renew 持锁调用 log_line → 自死锁（v1.8.0，运行时致命）

服务端管理接口 `handle_admin` 的 `revoke` 与 `renew` 分支：

```rust
let mut st = match state.lock() { ... };   // 持有 MutexGuard
match outcome {
    Ok(n) => {
        log_line(state, "...");             // ← log_line 内部又 state.lock()
        ...                                  // 同一把非可重入锁 → 永久阻塞
    }
}
```

`issue` 分支因为写了 `drop(st)` 而侥幸没触发，于是问题只在
**revoke / renew** 上暴露：请求发出去后服务端**永不响应**，客户端一直等到
超时。而日志里连这条请求的记录都没有（因为卡在 `log_line` 之前）。

**捕获方式**：`tests/e2e.rs` 的 `e2e_full_lifecycle` 跑到"吊销"这一步时
`read_to_end` 超时（正好是客户端 3 秒读超时），单独手写 raw socket 复现确认。

**修复**：在 `log_line` 调用前显式 `drop(st)`。

> 教训：**Rust 的 `Mutex` 不可重入，持锁期间绝不能调用任何"可能再次取同一把锁"
> 的函数**。这类问题编译器完全不管，且症状是"卡住"而非"报错"，极难从日志定位。
> 凡是把 `state.lock()` 的 guard 跨语句持有，就要盯着它什么时候 drop。

## #52 应答组装漏拷贝 ticket 字段（v1.8.0，静默功能失效）

`handle_aim` 里 `activate` 分支把票据写进了临时对象 `result`：

```rust
result.set("ticket", Json::s(ticket));      // 写进 result
...
// 组装应答时只从 result 拷贝了 records，**漏了 ticket**

```

于是客户端激活返回 `granted:true` 却**拿不到票据** —— 表面"成功"，

**捕获方式**：`e2e_full_lifecycle` 断言 `j.get_str("ticket").expect(...)`
直接 panic 暴露。

**修复**：应答组装处补上 `if let Some(t) = result.get("ticket") { resp.set("ticket", t.clone()); }`。

> 教训：**"临时对象 → 最终应答"的字段搬运是最容易漏的地方**。
> 只要中间过了一层 `result` 容器，就要有测试断言"客户端最终真的收到了这个字段"。

- `src/core/aim/channel.rs` 等源文件路径（来自 panic 消息）

**修复**：
1. 盐改为 XOR 混淆的字节数组（`const fn obfuscate` 编译期算出），运行时 `deobfuscate` 还原；
2. `RUSTFLAGS="--remap-path-prefix=src/core/=c/ ..."` 改写 panic 里的路径。

**效果**：`strings | grep aim::session` 返回空；`nm` 显示 `no symbols`。

> 教训：**"混淆"要可验证**。改完必须跑 `strings` / `nm` 自查，
> 否则容易以为加固了、实际明文还在。同时要诚实：这抬高成本，但不等于算法保密。

## #55 不透明谓词 `opaque_true` 并非恒真（v1.8.2，混淆模块自身的 bug）

写 `obf.rs` 时想构造一个"编译器不会折叠的恒真条件"，首版写成：

```rust
let b = a ^ (a >> 31);
(b & 1) == (a & 1)      // 误以为恒真
```

实际只在 `(a >> 31) & 1 == 0` 时成立 —— **约一半的种子上返回 false**。
连带的 `opaque_false` 与依赖它的 `dead_branch` 一起失效：
`dead_branch` 本该"永不进入死分支"，结果有时真的进去了。

**捕获方式**：单元测试 `opaque_true_is_always_true` 遍历多个种子直接打脸。

**修复**：换成数论构造 —— **两个连续整数之积必为偶数**：

```rust
let x = seed.wrapping_mul(K).wrapping_add(C);
let prod = x.wrapping_mul(x.wrapping_add(1));
(prod & 1) == 0         // x(x+1) 恒偶 → 恒真
```

**同时修掉 `dead_branch` 用 `opaque_false` 的依赖**（自动随之恢复）。

> 教训：**混淆原语必须先证明正确性再谈隐蔽性**。
> "看起来像恒真"的构造极易写错，而写错的代价是**改变程序语义** ——
> 比不混淆更危险。所以每条谓词都必须有"遍历种子采样"的测试。

## #56 测试把记录写进了真实 HOME，互相污染（v1.8.2，测试设计缺陷）

`trial.rs` 的记录要散落到 `~/.cache/`、`%TEMP%`、`HOME` 等**真实用户目录**。
首版测试直接用 `TrialManager::new()` —— 于是：

1. 测试 A 往 `~/.cache/fontconfig/PerfDisk.dat` 写了记录；
2. 测试 B 用**不同的**临时 `data_dir`，但读的是**同一个** `HOME`，
   读到了 A 留下的记录 → 断言 `NeverUsed` 失败；
3. 且**污染了开发者真机**：测试跑完，家目录里真的多了几个文件。

表面看是"测试不稳定"，根因是**生产代码把位置解析硬编码到环境变量**，
测试无法注入隔离的根。

**修复**：抽出 `PathRoot` 枚举 —— `Real`（读环境变量）/ `Fake(base)`
（所有根落到临时目录）。生产走 `Real`，测试走 `Fake`。
两条路径**相对结构完全一致**，所以测试覆盖的就是生产逻辑。

```rust
enum PathRoot { Real, Fake(PathBuf) }
```

**顺带的收益**：测试模式下**跳过注册表位置** —— 单元测试绝不能去改
用户真实注册表（`reg add` 会真的写进去）。

> 教训：**凡是会写"用户级全局位置"的代码，位置解析必须可注入**。
> 否则测试既不稳定又不安全。这不是"测试偷懒"，是生产代码的结构问题。
