# 08 · 依赖清单

> 迭代版本：**v1.6.1**　|　更新时间：2026-09-26
> 原则：**最小依赖**。HTTP 服务器、JSON 解析、持久化存储、日志系统、**SSE 流式响应、哈希链审计、签名令牌、智能推荐、密钥慢哈希 KDF、数据流加密**全部自实现，**v1.6.0 新增的统一响应信封、错误码体系、滑动窗口限流也全部自实现**，仅 XLSX 二进制格式因实现成本过高引入一个第三方 crate。

## 〇之一、v1.6.1 依赖结论（最新）

| 问题 | 结论 |
| --- | --- |
| v1.6.1 是否新增依赖？ | **❌ 没有。仍是 1 个直接依赖：`rust_xlsxwriter = "0.79"`** |

**这是刻意的设计约束，不是巧合。** v1.6.1 新增的两个模块本身就是"**如何在不引依赖的前提下解决问题**"的示范：

| 需求 | 常见做法（会引依赖） | 本项目做法（零依赖） | 为什么可以这么做 |
| --- | --- | --- | --- |
| 跨进程文件互斥 | `fs2` / `nix` / `winapi` 的 `flock` / `LockFileEx`，或 `unsafe` FFI | `core/dirlock.rs`：`pid` 探活 + `File::create_new`（`O_EXCL`） | 需求只是"挡人手误操作"，不需要内核级锁语义；pid 方案还能给出**人类可读**的占用者信息 |
| 检测进程存活 | 平台 API / 依赖库 | Linux `/proc/<pid>`、Windows `tasklist`、其他保守 `true` | 三平台分支加起来不到 20 行 |
| Mutex 毒化恢复 | 引 `parking_lot`（无 poison 概念） | `core/sync.rs`：`poisoned.into_inner()` | `std` 的 `PoisonError` 本身就提供 `into_inner()`，**不需要第三方库** |

**规则 10 的判定**：以上三项均可用 `std` 在 20 行内实现，
因此**引入依赖的收益明确低于成本**（编译时间、供应链风险、跨平台编译复杂度）。

> `serde` + `serde_json` 会显著增大二进制（本项目单 exe 约 4.5 MB 是硬约束之一），

> 限流同理：`tower` / `governor` 这类库功能远超所需，引入即违背规则 10（最小依赖）。
> **本次 187 个测试全绿，是在"零新增依赖"前提下达成的。**

## 〇·附、v1.5.1 依赖结论

| 问题 | 结论 |
| --- | --- |

| 密钥慢哈希（KDF）用了什么？ | 自实现 FNV-1a 64 位迭代 20 万轮 + 盐（`core/license.rs`）。**标准库** |
| 开发者模式状态机用了什么？ | `AtomicBool` + TCP 对端地址判定。**标准库** |
| 数据加密用了什么？ | 自实现 FNV 派生 XOR 流 + 分块 MAC（`core/vault.rs`）。**标准库** |
| 资源内嵌用了什么？ | `include_str!` 编译期宏。**编译器内置** |
| 传递依赖是否有变化？ | **无变化**，`Cargo.lock` 依赖树与 v1.5 一致（22 个包） |
| MSRV 是否需提高？ | **否**，仍为 `rust-version = "1.70"` |

> ⚠️ **诚实声明（v1.5.1 新增）**：本版的密钥慢哈希与数据加密同样基于 **FNV-1a 64 位自实现**。
> - **慢哈希**是**弱 KDF**：迭代 20 万轮把单次猜测代价从 ~1 ns 提到 ~30 ms（差 7 个数量级），
>   但**不是** argon2/bcrypt 级别的内存硬 KDF——GPU 仍可高速枚举。
> - **XOR 流加密不是流密码**：密钥流由 FNV 派生，**可预测**，不具备语义安全性；
>   分块 MAC 能检出**意外损坏与非恶意篡改**，但**不能防蓄意伪造**。
> - 结论：**显著提高门槛，但不可逾越**。数据加密**默认关闭**。
> - 若需真正的密码学强度，应引入 `sha2` + `hmac` + `argon2` + `chacha20poly1305`，
>   已列为 `03_目标文档.md` **目标 12（v1.6）**。详见 **`12_密钥与防破解说明.md`**。

### 为什么只有这一个

| 常规做法 | 本项目做法 | 原因 |
|---|---|---|
| `axum` / `actix-web` / `hyper` | 自实现 `core/http.rs`（约 950 行，`std::net`，每连接一线程） | 校运会场景并发极低（<10 人同时操作），用框架属过度工程；自实现零依赖、零升级风险 |
| `serde` / `serde_json` | 自实现 `core/json.rs`（493 行，手写词法+递归下降解析器） | 避免 proc-macro 编译期开销与版本漂移；JSON 结构固定可控 |
| `log` / `env_logger` / `tracing` | 自实现 `core/log.rs`（314 行，`OnceLock<Mutex<Logger>>` 单例） | 需求仅为「分级落盘 + 按日轮转」，标准库足够 |
| `chrono` / `time` | 自实现 Howard Hinnant `civil_from_days` 算法 | 仅需 UTC+8 本地时间格式化，200 行内解决，避免时区库体积 |
| `rusqlite` / `sled` | 单文件 JSON + 原子落盘（临时文件 + `fs::rename`） | 数据量小（千人级），JSON 可直接人工查看/修复，利于校园场景运维 |
| `zip` / `calamine` | 仅 XLSX **写**（读用自实现） | 读 Excel 已有自研实现，写因 OOXML 压缩包结构复杂，成本不划算 → **唯一例外** |
| **`tungstenite` / `axum::extract::ws`**（v1.5 新增行） | 自实现 SS**E**（`core/http.rs` 的 `Body::Stream` + `StreamWriter`，约 120 行） | 大屏是**单向推送**，SSE 复用现有 HTTP 栈即可；WebSocket 需握手升级 + 自定义帧协议，属过度工程（已列入 Non-Goals） |
| **`sha2` / `hmac`**（v1.5 新增行） | 自实现 FNV-1a 64 位（`core/audit.rs`，约 20 行） | 目标是**可检测篡改**而非密码学强度；换来零依赖。**代价已明确标注**，如需防伪见目标 9 |
| **`argon2` / `bcrypt`**（v1.5.1 新增行） | 自实现 `slow_hash`（`core/license.rs`，FNV 迭代 20 万轮 + 盐） | 项目硬约束「零新依赖」；20 万轮迭代已把暴力枚举代价提高 7 个数量级。**弱 KDF，已明示**，升级见目标 12 |
| **`chacha20poly1305` / `aes-gcm`**（v1.5.1 新增行） | 自实现 FNV 派生 XOR 流 + 4 KiB 分块 MAC（`core/vault.rs`） | 同上；**明确不自行实现标准密码学原语**（Non-Goals），故用"门槛型"方案而非"伪密码学"方案 |
| **`rust-embed` / `include_dir`**（v1.5.1 新增行） | `include_str!("../../web/index.html")`（编译器内置宏） | 只需内嵌一个 117 KB 文件；引入 crate 属过度工程 |

> 如需彻底零依赖：移除 `Cargo.toml` 中的 `rust_xlsxwriter`，并删除 `src/core/export.rs` 中的 xlsx 分支（CSV/JSON/TXT 导出不受影响）。

### v1.5.1 安全声明（与依赖相关）

| 项 | 说明 |
|---|---|
| 审计哈希算法 | FNV-1a 64 位（自实现，非密码学哈希）。**用途为"篡改可检测"，非"篡改不可能"** |

| **服务端全部依赖** | — | **0（纯 std）** |

### 为什么坚持零新增

v1.8.0 需要 HTTP 服务、JSON、加密、随机数、时间格式化 —— 这些若引入
`tokio`/`serde`/`ring`/`rand`/`chrono` 会带来**数十个传递依赖**。
本项目的"最小依赖"原则（规则 10）要求尽量自实现，因此：

| 能力 | 自实现位置 | 通常会用 |
| --- | --- | --- |
| HTTP 服务 | `server.rs`（`TcpListener` + 手写解析） | axum / hyper |
| JSON | `json.rs` | serde_json |
| 加密信道 | `channel.rs` | ring / aes-gcm |
| 随机数 | `system_random_bytes`（`/dev/urandom`） | rand |
| 时间格式化 | `civil_from_days`（Hinnant 算法） | chrono |
| base64 | `b64_encode` / `b64_decode` | base64 |

### 代价（如实记录）

- **FNV 不是密码学哈希**，自实现流密码也不如 AES-GCM 强 —— 见 `docs/13` 第七节。
- 自实现 HTTP 只覆盖本项目所需子集（无 chunked 请求、无 HTTP/2）。
- 换来的是：**依赖面极小、无供应链风险、编译快、二进制小**。

> 这是**有意识的取舍**：在校运会内网场景下，"可控、可审计、依赖少"比
> "用最强的现成库"更重要。若将来需要更高安全等级，应优先引入经过审计的
> 密码学库，而不是继续加固自实现方案。
